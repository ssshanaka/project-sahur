# Module 0 — Introduction

## Lesson 0.3 — Pretraining vs Continued Pretraining vs Fine-Tuning vs Alignment vs Inference

In the AI world, technical terms get thrown around constantly:

> *"We are fine-tuning a model on our company docs."*

> *"Should we do Continued Pretraining or RAG?"*

> *"Is DPO better than RLHF for alignment?"*

> *"Our inference latency is too high."*

If you mix up these terms, you will waste time and compute. For example, trying to teach a model new factual knowledge using basic fine-tuning often leads to severe hallucinations, when you should have used **Continued Pretraining** or **RAG (Retrieval-Augmented Generation)**.

In this lesson, we will demystify the **5 foundational phases of the LLM life cycle**.

---

# 🎯 Goal

By the end of this lesson, you will be able to clearly distinguish between:

1. **Pretraining**
2. **Continued Pretraining (CPT)**
3. **Fine-Tuning (SFT / LoRA)**
4. **Alignment (DPO / RLHF)**
5. **Inference**

You will know exactly when to use each approach, what data format each requires, and which weights get updated.

Let's examine each pillar in depth.

---

# Pillar 1: Pretraining

### What is it?
Pretraining is building a model from absolute scratch. 

You initialize all model weights randomly, feed trillions of tokens of raw unstructured text (books, code, web pages), and train the model using **next-token prediction**.

### Key Characteristics:
- **Data Format**: Raw text (`"The capital of France is Paris. In 1789..."`)
- **Weight Updates**: 100% of all parameters are modified.
- **Compute Cost**: Millions of dollars (Thousands of GPUs for weeks/months).
- **Goal**: Teach the model grammar, syntax, world knowledge, and reasoning capabilities.

---

# Pillar 2: Continued Pretraining (CPT)

### What is it?
Suppose you take an existing pretrained Base Model (like Qwen3-Base) and feed it 50 Gigabytes of raw medical textbooks, clinical trial reports, and medical journals using the exact same next-token prediction loss.

You aren't starting from scratch—you are **continuing the pretraining process** on a specific domain.

### Key Characteristics:
- **Data Format**: Raw domain text (unstructured text, no Q&A required).
- **Weight Updates**: All or large portions of base model parameters.
- **Compute Cost**: Moderate to High ($1,000 – $50,000+).
- **Goal**: Inject dense domain vocabulary and factual knowledge into the model's core representation (e.g., legal, medical, corporate internal docs).

---

# Pillar 3: Fine-Tuning (Supervised Fine-Tuning / SFT)

### What is it?
Fine-tuning takes a model that already possesses knowledge and adapts its **behavior, persona, output format, or task execution**.

Instead of raw text, fine-tuning uses **structured instruction data** (User prompt ➔ Assistant response).

When we use Parameter-Efficient Fine-Tuning (PEFT) like **LoRA** or **QLoRA**, we freeze the original model weights and only train a tiny set of new adapter weights (often < 1% of the total parameters).

### Key Characteristics:
- **Data Format**: Structured JSONL / conversation pairs (`{"messages": [{"role": "user", "content": "..."}, {"role": "assistant", "content": "..."}]}`)
- **Weight Updates**: Adapter weights only (LoRA) or selected layers.
- **Compute Cost**: Low ($0 on Colab / single GPU).
- **Goal**: Teach the model a specific voice, style, output schema (e.g., JSON), or specialized instruction behavior.

> 💡 **Crucial Rule**: Fine-tuning is fantastic for teaching **STYLE, FORMAT, and PERSONA**. It is unreliable for forcing a model to memorize new facts (use RAG or CPT for facts!).

---

# Pillar 4: Alignment (RLHF / DPO / GRPO)

### What is it?
Once a model is fine-tuned, it might still give overly wordy answers, refuse safe requests (over-refusal), or sound robotic.

Alignment techniques steer the model's outputs towards human preferences by comparing multiple candidate responses.

- **RLHF (Reinforcement Learning from Human Feedback)**: Uses a Reward Model and PPO/GRPO reinforcement learning.
- **DPO (Direct Preference Optimization)**: Directly penalizes rejected answers and rewards chosen answers using mathematical log-odds.

### Key Characteristics:
- **Data Format**: Preference Pairs (`{"prompt": "...", "chosen": "...", "rejected": "..."}`)
- **Weight Updates**: Adapter or fine-tuning parameters.
- **Compute Cost**: Moderate.
- **Goal**: Maximize helpfulness, safety, conciseness, and tone consistency.

---

# Pillar 5: Inference

### What is it?
Inference is when you actually **use** the model to generate responses.

When you send a prompt to ChatGPT, Ollama, or run a local Python script with `model.generate()`, you are executing **Inference**.

### Key Characteristics:
- **Data Format**: User Prompts (`"Explain CUDA in simple terms"`)
- **Weight Updates**: **ZERO (0)**. The weights are completely frozen.
- **Compute Cost**: Low per request (depends on batch size and latency requirements).
- **Goal**: Process input tokens, compute attention and logits, sample probabilities, and generate output tokens efficiently.

---

# Summary Comparison Table

| Phase | Data Format | Weights Modified | Primary Objective |
| :--- | :--- | :--- | :--- |
| **1. Pretraining** | Unstructured Raw Text | All Weights (100%) | Learn general language & world facts |
| **2. Continued Pretraining** | Unstructured Domain Text | Most Base Weights | Inject heavy domain-specific knowledge |
| **3. Fine-Tuning (SFT / LoRA)** | Instruction Pairs `(Q & A)` | Adapter Weights (< 1%) | Change style, persona, format & task behavior |
| **4. Alignment (DPO/RLHF)** | Preference Pairs `(Chosen / Rejected)` | Adapter / Policy Weights | Refine safety, helpfulness & tone |
| **5. Inference** | User Input Prompt | **None (0% - Frozen)** | Predict and output next tokens |
