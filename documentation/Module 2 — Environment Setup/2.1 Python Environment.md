# Why Not Install Everything Globally?

Let's say you have two projects.

```
Project A

↓

Transformers 4.55
```

```
Project B

↓

Transformers 4.42
```

If both use your global Python installation...

Eventually one project breaks.

This is called **dependency conflict**.

---

# Think of Apartments

Imagine Python packages are furniture.

Global installation means

```
One giant apartment

↓

Everyone shares

the same furniture.
```

Chaos.

Instead,

every project gets

its own apartment.

```
Project Sahur

↓

Own furniture

↓

Own packages

↓

Own Python
```

That's a virtual environment.

---

# What is a Virtual Environment?

A virtual environment is an isolated Python installation.

Instead of

```
Windows Python

↓

Everything installed together
```

You get

```
Python

↓

Project Sahur

↓

Own packages
```

Every serious ML engineer uses this.

# Choosing Python Version

Current recommendation

```
Python 3.11
```

Why?

Because nearly every modern AI library supports it well, and it's widely used in the ecosystem.

Avoid bleeding-edge versions (like a brand-new Python release) until the libraries you need officially support them.

---

# Creating the Virtual Environment

Open a terminal inside your project folder.

```bash
python -m venv .venv
```

What happened?

Python copied a minimal runtime into

```
.venv/
```

Nothing magical.

Just isolation.

---

# Activating It

### Windows

```powershell
.venv\Scripts\activate
```

---

### macOS / Linux

```bash
source .venv/bin/activate
```

When activated,

your terminal usually changes.

Example

```bash
(.venv)

PS C:\Project-Sahur>
```

That little

```
(.venv)
```

means

You're safe.

Packages won't pollute your global Python installation.

---

# Upgrading pip

Always do this.

```bash
python -m pip install --upgrade pip
```

Why?

New pip versions:

- install faster
- resolve dependencies better
- avoid many installation bugs

# requirements.txt

Save the environment.

Generate it with:

```bash
pip freeze > requirements.txt
```

Now anyone can recreate your environment.

```bash
pip install -r requirements.txt
```

Reproducibility is a core part of ML engineering.

---

# .gitignore

Never upload your virtual environment or model weights to Git.

Create a `.gitignore` like this:

```gitignore
.venv/
__pycache__/
*.pyc

models/
checkpoints/
logs/

.env
```

Your repository stays lightweight, while anyone can recreate the environment from `requirements.txt`.

# Local vs Google Colab

For **Project Sahur**, we'll use both.

### Google Colab (Free)

Perfect for:

- Learning
- Small experiments
- Qwen3-0.6B LoRA training
- Testing datasets

Pros:

- Free GPU
- No local GPU setup required

Cons:

- Session time limits
- Limited storage
- Slower than a dedicated machine

---

### Your Local Machine

Your laptop is ideal for:

- Running inference
- Inspecting models
- Testing prompts
- Benchmarking
- Quantized GGUF models

Large-scale fine-tuning will be challenging on 4 GB VRAM, so we'll mainly use Colab for training and your local machine for development and testing.
