# The Problem `transformers` Solved

Before Hugging Face released `transformers` in 2018, every research team published models using custom code structures:

```text
Google BERT repo ──► Custom TensorFlow code
Meta LLaMA repo  ──► Custom PyTorch scripts
OpenAI GPT-2 repo ──► Custom Python wrappers
```

If you wanted to compare BERT against GPT-2, you had to learn two completely different codebases, data loaders, and model interfaces.

The `transformers` library unified the entire field under **one standard Python API**:

```text
Qwen3    ──┐
Llama 3  ──┼──► [ transformers API ] ──► Standard PyTorch Model
Gemma 2  ──┤
DeepSeek ──┘
```

Now, switching from a 600M parameter model to a 70B parameter model requires changing **only one line of code**: the model string!

# The AutoClass Design Pattern

The heart of the `transformers` library is the **AutoClass** system.

When you pass a repository name like `"Qwen/Qwen3-0.6B"` to an AutoClass, Hugging Face automatically:
1. Downloads the repository files (`config.json`, `model.safetensors`, etc.).
2. Inspects `config.json` to identify the model architecture (`model_type: "qwen2"`).
3. Instantiates the exact PyTorch neural network class required to run that model.

There are four key AutoClasses every AI engineer must know:

```text
┌───────────────────────────┬────────────────────────────────────────────────────────┐
│ AutoClass                 │ Purpose                                                │
├───────────────────────────┼────────────────────────────────────────────────────────┤
│ AutoConfig                │ Loads metadata & hyperparameters (No weights downloaded)│
│ AutoTokenizer             │ Loads the matching text-to-token converter             │
│ AutoModel                 │ Loads the core Transformer (outputs hidden states)     │
│ AutoModelForCausalLM     │ Loads the Transformer + LM Head (outputs next tokens)  │
└───────────────────────────┴────────────────────────────────────────────────────────┘
```

Let's examine the crucial difference between `AutoModel` and `AutoModelForCausalLM`.

---

# `AutoModel` vs `AutoModelForCausalLM`

This distinction trips up almost every beginner.

### 1. `AutoModel` (Base Feature Extractor)
`AutoModel` loads the core Transformer layers, but **stops before the final classification head**.

```text
Tokens ──► [ Embeddings ] ──► [ 28 Transformer Layers ] ──► Hidden States (Vector Array)
```

- **Output**: A tensor of shape `(batch_size, sequence_length, hidden_size)` containing dense vector representations (hidden states).
- **Use Case**: Feature extraction, sentence embeddings, semantic search, or building custom heads.
- **Can it generate text?**: ❌ No. It does not output probabilities over vocabulary tokens.

---

### 2. `AutoModelForCausalLM` (Causal Language Model)
`AutoModelForCausalLM` loads the core Transformer layers **PLUS the Language Model (LM) Head**.

```text
Tokens ──► [ Embeddings ] ──► [ 28 Transformer Layers ] ──► [ LM Head ] ──► Logits (Vocab Scores)
```

- **Output**: A tensor of shape `(batch_size, sequence_length, vocab_size)` containing raw scores (logits) for every token in the vocabulary.
- **Use Case**: Text generation, chatbots, code completion, and next-token prediction.
- **Can it generate text?**: ✅ Yes! This is the class we use for **Project Sahur**.

# Understanding Model Precision & Data Types

When loading weights into GPU VRAM, the data type (**precision**) determines both **memory footprint** and **numerical stability**.

Let's calculate the VRAM required for **Qwen3-0.6B** (600 Million parameters) across different precision modes:

```text
┌─────────────────┬───────────────────┬─────────────────┬────────────────────────────┐
│ Precision       │ PyTorch Dtype     │ Bytes / Weight  │ Qwen3-0.6B Weight Footprint│
├─────────────────┼───────────────────┼─────────────────┼────────────────────────────┤
│ Full (32-bit)   │ torch.float32     │ 4 Bytes         │ ~ 2.4 GB VRAM              │
│ Half (16-bit)   │ torch.float16     │ 2 Bytes         │ ~ 1.2 GB VRAM              │
│ Brain (16-bit)  │ torch.bfloat16    │ 2 Bytes         │ ~ 1.2 GB VRAM              │
│ 8-bit Quantized │ bitsandbytes int8 │ 1 Byte          │ ~ 0.6 GB VRAM              │
│ 4-bit Quantized │ bitsandbytes int4 │ 0.5 Bytes       │ ~ 0.35 GB VRAM             │
└─────────────────┴───────────────────┴─────────────────┴────────────────────────────┘
```

### FP16 vs BF16 (Which should you use?)
- **`torch.float16` (FP16)**: Standard 16-bit floating point. Supported by almost all GPUs (including GTX 10-series and RTX 20-series like your RTX 2050).
- **`torch.bfloat16` (BF16)**: Brain Floating Point developed by Google. It has a much wider exponent range than FP16, preventing underflow/overflow during fine-tuning gradients. Supported natively on NVIDIA Ampere (RTX 30-series, A100) and newer GPUs.

```python
import torch
from transformers import AutoModelForCausalLM

# Loading Qwen3 in 16-bit precision for lower VRAM usage
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen3-0.6B",
    torch_dtype=torch.float16,  # Or torch.bfloat16 on supported GPUs
    device_map="auto"
)
```

# Layer Offloading with `device_map="auto"`

What happens if a model is too large to fit in your GPU VRAM?

In older versions of PyTorch, the script would crash instantly with `CUDA out of memory`.

With the `transformers` library (powered by `accelerate`), you simply pass:

```python
device_map="auto"
```

Hugging Face inspects your system's hardware (GPU VRAM, System RAM, Disk space) and automatically splits the model's layers:

```text
Layer 0  ── Layer 18  ──► GPU VRAM (Fastest execution)
Layer 19 ── Layer 27  ──► CPU RAM  (Slower fallback)
Disk Cache             ──► NVMe Storage (Emergency fallback)
```

This allows you to load and test large models locally even if your GPU VRAM is limited!

# The High-Level `pipeline()` API vs Low-Level `generate()`

The `transformers` library provides two distinct ways to run models:

### 1. `pipeline()` (Fastest Prototyping)
If you want to run quick text generation in 3 lines of code:

```python
from transformers import pipeline

generator = pipeline("text-generation", model="Qwen/Qwen3-0.6B", device_map="auto")
response = generator("Yo Sahur, what's the plan today?", max_new_tokens=50)
print(response[0]['generated_text'])
```

### 2. Direct `model.generate()` (Full Engineering Control)
For **Project Sahur**, we use direct `model.generate()` because it gives us full control over tokenization, sampling temperature, top-p, attention masks, and device streams:

```python
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

model_id = "Qwen/Qwen3-0.6B"

# 1. Load Tokenizer & Model
tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    torch_dtype=torch.float16,
    device_map="auto"
)

# 2. Tokenize Input Text
prompt = "Explain quantum computing in one sentence."
inputs = tokenizer(prompt, return_tensors="pt").to("cuda")

# 3. Generate Output Tokens
with torch.no_grad():
    output_tokens = model.generate(
        **inputs,
        max_new_tokens=40,
        temperature=0.7,
        top_p=0.9,
        do_sample=True
    )

# 4. Decode Tokens back to Text
response = tokenizer.decode(output_tokens[0], skip_special_tokens=True)
print(response)
```

# Common Gotchas & Best Practices

### ❌ 1. Forgetting `torch.no_grad()` during inference
If you run `model.generate()` without `with torch.no_grad():`, PyTorch will build and store gradient computation graphs for every token generated. This consumes gigabytes of extra VRAM and will crash your script!

### ❌ 2. Missing Padding Token (`pad_token`)
Many Causal LM tokenizers (like Llama or Qwen) do not define a default padding token. When batching prompts together, you must explicitly set:

```python
if tokenizer.pad_token is None:
    tokenizer.pad_token = tokenizer.eos_token
```

### ❌ 3. Mixing Devices (`CPU` vs `CUDA`)
If your model is on GPU (`device="cuda"`) but your input tensors are on CPU, PyTorch will crash with `RuntimeError: Expected all tensors to be on the same device`. Always ensure inputs are moved to the GPU:

```python
inputs = inputs.to("cuda")
```

# 🛠 Mini Lab: Write Your First Model Inspector Script

Create a new file in your `scripts/` directory called `load_qwen.py`:

```python
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

MODEL_ID = "Qwen/Qwen3-0.6B"

print(f"Loading {MODEL_ID}...")

tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)
model = AutoModelForCausalLM.from_pretrained(
    MODEL_ID,
    torch_dtype=torch.float16 if torch.cuda.is_available() else torch.float32,
    device_map="auto" if torch.cuda.is_available() else "cpu"
)

print("\n--- MODEL METRICS ---")
print("Model Architecture:", model.config.architectures)
print("Vocabulary Size:", model.config.vocab_size)
print("Hidden Layer Dimension:", model.config.hidden_size)
print("Total Transformer Layers:", model.config.num_hidden_layers)
print("Total Attention Heads:", model.config.num_attention_heads)

prompt = "Hello Sahur, tell me a quick tech joke!"
inputs = tokenizer(prompt, return_tensors="pt")

if torch.cuda.is_available():
    inputs = inputs.to("cuda")

with torch.no_grad():
    outputs = model.generate(**inputs, max_new_tokens=30, temperature=0.7, do_sample=True)

print("\n--- MODEL OUTPUT ---")
print(tokenizer.decode(outputs[0], skip_special_tokens=True))
```

Run your script:
```bash
python scripts/load_qwen.py
```

Verify that it downloads Qwen3-0.6B, prints its architecture parameters, and outputs a response!
