# The VRAM Math Crisis: Why Full Fine-Tuning Fails

To understand why PEFT exists, we must look at the mathematical memory footprint of deep learning training.

When you run **Inference**, your GPU VRAM only needs to store the base model weights:

$$\text{VRAM}_{\text{inference}} = \text{Parameters} \times \text{Bytes per Parameter}$$

For **Qwen3-0.6B** (600 Million parameters) in 16-bit precision:

$$\text{VRAM}_{\text{inference}} = 600{,}000{,}000 \times 2 \text{ bytes} \approx 1.2 \text{ GB VRAM}$$

That easily fits inside a 4 GB consumer GPU.

---

### What Happens During Full Fine-Tuning?

During training, PyTorch must store four distinct memory components for **every single parameter**:

1. **Model Weights (FP16)**: 2 Bytes / param
2. **Gradients ($\nabla W$) (FP16)**: 2 Bytes / param
3. **AdamW Optimizer States (FP32)**:
   - FP32 Master Weight Copy: 4 Bytes / param
   - First Moment Vector ($m$ — Momentum): 4 Bytes / param
   - Second Moment Vector ($v$ — Variance): 4 Bytes / param

That's **16 bytes per parameter** just for the fixed training state — and we haven't even counted activation memory yet.

Think of it like this:

```text
Inference ➔ Carrying a backpack with your textbook (1.2 GB)
Training  ➔ Carrying the textbook + a notebook + 3 reference binders + a calculator (9.6 GB)
```

Even for our lightweight 0.6B model, Full Fine-Tuning requires **9.6 GB of VRAM**.

On a 4 GB consumer GPU? Instant crash.

This is why Parameter-Efficient Fine-Tuning was invented.

# What is PEFT?

**PEFT (Parameter-Efficient Fine-Tuning)** is an umbrella term for techniques that adapt large pretrained models without updating all their parameters.

Instead of retraining the entire neural network, PEFT:

1. **Freezes** all base model weights ($W_0$).
2. **Attaches** a tiny set of new trainable parameters (adapters).
3. **Passes** gradients only through the new adapter parameters during backpropagation.

```text
Full Fine-Tuning ➔ 100% of Weights Active ➔ 16 Bytes/Param ➔ Massive VRAM
PEFT             ➔ 99.7% Frozen           ➔ Gradients on < 0.3% ➔ Tiny VRAM
```

Because base weights are frozen, no gradients or optimizer states are stored for them. Memory consumption drops by over **75%**.

# Deep Dive: LoRA (Low-Rank Adaptation)

In 2021, Edward Hu and researchers at Microsoft published:

> _"LoRA: Low-Rank Adaptation of Large Language Models"_

### The Intrinsic Rank Hypothesis

The core discovery behind LoRA is elegant:

> When fine-tuning an LLM for a specific task or persona, the change in weight matrices ($\Delta W$) has a very low **intrinsic rank**.

Think of it like handwriting. You learned to write all 26 letters as a child. If someone asks you to write in cursive instead of print, you're not relearning the alphabet. You're making a small directional adjustment to your existing motor skills.

Similarly, a 1024×1024 weight matrix contains over a million numbers. But the actual shift needed to teach the model a new persona lies in a tiny, low-dimensional subspace. Instead of updating the full matrix, we can factorize the weight update into two much smaller matrices.

---

### The Mathematical Formula

During standard fine-tuning, the updated weight matrix $W$ is:

$$W = W_0 + \Delta W$$

LoRA decomposes $\Delta W$ into two smaller matrices, $B$ and $A$:

$$\Delta W = B \cdot A$$

Where:

- $W_0 \in \mathbb{R}^{d \times k}$ — Base Model Weight Matrix (**FROZEN**)
- $B \in \mathbb{R}^{d \times r}$ — LoRA Matrix B (**TRAINABLE**)
- $A \in \mathbb{R}^{r \times k}$ — LoRA Matrix A (**TRAINABLE**)
- $r \ll \min(d, k)$ — The **Rank** parameter

---

### Visualizing LoRA Matrix Factorization

```text
                  INPUT VECTOR x (Dimension k)
                               │
            ┌──────────────────┴──────────────────┐
            │                                     │
            ▼                                     ▼
   BASE WEIGHT MATRIX W₀                   LORA MATRIX A
      Shape (d × k)                        Shape (r × k)
       [ FROZEN ]                           [ TRAINABLE ]
            │                                     │
            │                                     ▼
            │                              LORA MATRIX B
            │                              Shape (d × r)
            │                               [ TRAINABLE ]
            │                                     │

            │                               Scaling (α / r)
            │                                     │
            └──────────────────┬──────────────────┘
                               │
                               ▼
                        SUMMATION ( + )
                               │
                               ▼
                 OUTPUT VECTOR y (Dimension d)
```

---

### The Parameter Reduction Math

Let's work through the numbers.

Suppose we have a linear layer where input dimension $k = 1024$ and output dimension $d = 1024$.

**Full Fine-Tuning**: $1024 \times 1024 = 1{,}048{,}576$ parameters.

**LoRA with Rank $r = 16$**:

- Matrix $A$: $16 \times 1024 = 16{,}384$ parameters
- Matrix $B$: $1024 \times 16 = 16{,}384$ parameters
- Total: $32{,}768$ parameters

$$\frac{32{,}768}{1{,}048{,}576} \approx 3.1\%$$

We reduced trainable parameters for that layer by **96.9%**. That's like replacing a full house renovation with swapping out the light switches.

---

### Why LoRA Starts at Zero ($\Delta W = 0$)

When initializing LoRA:

- **Matrix $A$** is initialized with random Gaussian values.
- **Matrix $B$** is initialized to **all zeros**.

Because $B = 0$:

$$\Delta W = B \cdot A = 0 \cdot A = 0$$

At step 0, the LoRA update is exactly zero. The model starts training with the **exact performance of the base model**, with no sudden degradation. Training gradually builds $\Delta W$ from nothing.

# Mastering LoRA Hyperparameters

When configuring LoRA, you will tune four key parameters:

```text
┌───────────────────┬───────────────────────────────┬────────────────────────────────┐
│ Hyperparameter    │ Description                   │ Recommended Value              │
├───────────────────┼───────────────────────────────┼────────────────────────────────┤
│ Rank (r)          │ Inner matrix bottleneck size  │ r = 8 or r = 16                │
│ Alpha (α)         │ LoRA scaling multiplier       │ α = 2 × r (e.g., α = 32)       │
│ Dropout           │ Regularization probability    │ lora_dropout = 0.05            │
│ Target Modules    │ Layers receiving LoRA         │ ["q_proj", "k_proj", "v_proj"] │
└───────────────────┴───────────────────────────────┴────────────────────────────────┘
```

### 1. Rank ($r$)

The rank defines the inner dimension of matrices $A$ and $B$.

- **$r = 4$ or $8$**: Lightweight. Great for simple style shifts or classification tasks.
- **$r = 16$**: The sweet spot for persona tuning and instruction following. **This is what we use for Project Sahur.**
- **$r = 32$ or $64$**: Heavy. Used for complex domain shifts like biomedical reasoning. Diminishing returns and higher overfitting risk.

### 2. Alpha ($\alpha$)

Alpha scales the LoRA output: $\frac{\alpha}{r} \cdot (B \cdot A \cdot x)$.

When you experiment with different ranks, this scaling keeps update magnitudes consistent.

**Golden Rule**: Always set $\alpha = 2 \times r$. If $r = 16$, set $\alpha = 32$.

### 3. Dropout

Randomly zeroes out a fraction of LoRA activations during training (e.g. 5%). This prevents the adapter from memorizing exact training sentences, forcing it to learn generalized style patterns.

### 4. Target Modules

In a Transformer, linear projections exist in two main areas:

```text
ATTENTION MODULES:
  q_proj ──► Controls context search focus
  k_proj ──► Controls token key representations
  v_proj ──► Controls token value extraction
  o_proj ──► Controls attention output mixing

FEED-FORWARD (FFN) MODULES:
  gate_proj ──► SwiGLU gate activation
  up_proj   ──► Expands hidden dimension
  down_proj ──► Compresses back
```

Modern research shows that attaching LoRA to **all linear layers** produces higher quality fine-tunes with minimal extra VRAM. For Project Sahur, we adapt all attention and FFN projections.

# QLoRA: Quantized Low-Rank Adaptation

In 2023, Tim Dettmers introduced **QLoRA**, which takes PEFT efficiency one step further by combining **4-bit base model quantization** with **LoRA adapters**.

```text
Base Model Weights ──► Quantized to 4-bit NF4 (Frozen, 0.5 bytes/param)
LoRA Adapters       ──► Kept in 16-bit FP16 (Trainable on GPU)
```

Think of it like vacuum-sealing your suitcase (4-bit compression) and then slipping a small guidebook into the side pocket (LoRA adapter).

With QLoRA, fine-tuning **Qwen3-0.6B** consumes less than **2.5 GB of VRAM** — fully achievable on a consumer GPU or free Google Colab!

# Adapter File Management: Saving & Merging

One of the greatest advantages of LoRA is file portability.

```text
Full Base Model Weights (Qwen3-0.6B) ──► ~ 1.2 GB
LoRA Adapter Folder (sahur-lora-v1)   ──► ~ 6.0 MB
```

Instead of uploading 1.2 GB checkpoints after every training run, you only save and transfer a tiny **6 MB adapter folder**. It's like emailing a Word document instead of shipping an entire library.

The adapter folder contains just two files:

- `adapter_config.json` — Hyperparameters (r, alpha, target modules)
- `adapter_model.safetensors` — Binary weights of Matrices A and B

When you're ready to deploy, you **merge** the adapter permanently back into the base model using `merge_and_unload()`. Once merged, the model runs as a standalone model without needing the `peft` library at all.

# How PEFT Powers Project Sahur

```text
Base Model ──► Qwen3-0.6B (Frozen in 4-bit)
Dataset    ──► sahur_genz_v1.jsonl (Gen Z conversation pairs)
PEFT       ──► LoRA (r=16, alpha=32, all-linear targets)
```

By decoupling base knowledge from persona adapters, we can easily train multiple personalities (e.g., `Sahur-GenZ`, `Sahur-Coder`, `Sahur-Tutor`) on the exact same base model without duplicating gigabytes of storage.
