# The VRAM Math Crisis: Why Full Fine-Tuning Fails

To understand why PEFT exists, we must look at the mathematical memory footprint of deep learning training.

When you run **Inference**, your GPU VRAM only needs to store the base model weights:

$$\text{VRAM}_{\text{inference}} = \text{Parameters} \times \text{Bytes per Parameter}$$

For **Qwen3-0.6B** (600 Million parameters) in 16-bit precision (`FP16` / `BF16` = 2 bytes per parameter):

$$\text{VRAM}_{\text{inference}} = 600,000,000 \times 2 \text{ bytes} \approx 1.2 \text{ GB VRAM}$$

That easily fits inside your laptop's 4 GB RTX 2050 GPU.

---

### What Happens During Full Fine-Tuning?

During training, PyTorch must store four distinct memory components for **every single parameter**:

1. **Model Weights (FP16)**: 2 Bytes / param
2. **Gradients ($\nabla W$) (FP16)**: 2 Bytes / param
3. **AdamW Optimizer States (FP32)**:
   - FP32 Master Weight Copy: 4 Bytes / param
   - First Moment Vector ($m$ - Momentum): 4 Bytes / param
   - Second Moment Vector ($v$ - Variance): 4 Bytes / param
4. **Activation Tensors**: Intermediate layer outputs stored in VRAM for backpropagation gradients.

Let's add up the memory footprint per parameter:

```text
┌────────────────────────────────────────────────────────────────────────┐
│ VRAM MEMORY FOOTPRINT PER PARAMETER (FULL FINE-TUNING)                 │
├────────────────────────────────────────────────────────────────────────┤
│ Base Weights (FP16)        : 2 Bytes                                   │
│ Gradients (FP16)          : 2 Bytes                                   │
│ AdamW Master Copy (FP32)  : 4 Bytes                                   │
│ AdamW Momentum m (FP32)   : 4 Bytes                                   │
│ AdamW Variance v (FP32)   : 4 Bytes                                   │
├────────────────────────────────────────────────────────────────────────┤
│ TOTAL FIXED MEMORY        : 16 Bytes per Parameter                    │
└────────────────────────────────────────────────────────────────────────┘
```

Notice that the AdamW optimizer alone requires **12 bytes per parameter**!


This is why Parameter-Efficient Fine-Tuning was invented.

# What is PEFT?

**PEFT (Parameter-Efficient Fine-Tuning)** is an umbrella term for techniques that adapt large pretrained models to specific tasks without updating all base parameters.

Instead of retraining the entire neural network, PEFT:

1. **Freezes** all base model weights ($W_0$).
2. **Attaches** a tiny set of new trainable parameters (adapters).
3. **Passes** gradients only through the new adapter parameters during backpropagation.

```text
┌────────────────────────────────────────────────────────────────────────┐
│ FULL FINE-TUNING                                                       │
│ 100% of Weights Active ➔ Gradients on All Layers ➔ 16 Bytes/Param      │
└────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────┐
│ PEFT (PARAMETER-EFFICIENT FINE-TUNING)                                 │
│ 99.7% Weights Frozen ➔ Gradients on < 0.3% Parameters ➔ Low VRAM       │
└────────────────────────────────────────────────────────────────────────┘
```

Because base weights are frozen:
- No gradients are computed for the base weights.
- No AdamW optimizer states are stored for the base weights.
- Memory consumption drops by over **75%**!

While there are several PEFT approaches, one method dominates modern LLM fine-tuning: **LoRA**.

# Deep Dive: LoRA (Low-Rank Adaptation)

In 2021, Edward Hu and researchers at Microsoft published the seminal paper:

> *"LoRA: Low-Rank Adaptation of Large Language Models"*

### The Intrinsic Rank Hypothesis

The core discovery behind LoRA is simple yet profound:

> When fine-tuning an LLM for a specific task or persona, the change in weight matrices ($\Delta W$) has a very low **intrinsic rank**.

Although a projection matrix in Qwen3 might have a dimension of $1024 \times 1024$ (over 1,000,000 numbers), the actual directional shift needed to teach the model a new persona lies in a tiny, low-dimensional subspace.

Instead of updating the full high-dimensional matrix, we can factorize the weight update into two low-rank matrices!

---

### The Mathematical Formula

During standard fine-tuning, the updated weight matrix $W$ is:

$$W = W_0 + \Delta W$$

Where $W_0$ is the initial pretrained weight matrix of shape $(d \times k)$, and $\Delta W$ is the weight update matrix of shape $(d \times k)$.

LoRA decomposes $\Delta W$ into two smaller matrices, $B$ and $A$:

$$\Delta W = B \cdot A$$

Where:
- $W_0 \in \mathbb{R}^{d \times k}$ (Base Model Weight Matrix — **FROZEN**)
- $B \in \mathbb{R}^{d \times r}$ (LoRA Matrix B — **TRAINABLE**)
- $A \in \mathbb{R}^{r \times k}$ (LoRA Matrix A — **TRAINABLE**)
- $r \ll \min(d, k)$ (The **Rank** parameter)

---

### Visualizing LoRA Matrix Factorization

```text
                  INPUT VECTOR x (Dimension k)
                               │
            ┌──────────────────┴──────────────────┐
            │                                     │
            ▼                                     ▼
   BASE WEIGHT MATRIX W₀                   LORA MATRIX A
      Shape (d × k)                        Shape (r × k)
       [ FROZEN ]                           [ TRAINABLE ]
            │                                     │
            │                                     ▼
            │                              LORA MATRIX B
            │                              Shape (d × r)
            │                               [ TRAINABLE ]
            │                                     │
            │                                     ▼
            │                               Scaling (α / r)
            │                                     │
            └──────────────────┬──────────────────┘
                               │
                               ▼
                        SUMMATION ( + )
                               │
                               ▼
                 OUTPUT VECTOR y (Dimension d)
```

---

### Linear Algebra & Parameter Reduction Math

Let's work through the linear algebra step-by-step to see how the numbers add up.

Suppose we have a linear layer in Qwen3 where:
- Input dimension $k = 1024$
- Output dimension $d = 1024$

**Full Fine-Tuning Parameter Count**:
$$\text{Params}_{\text{Full}} = d \times k = 1024 \times 1024 = 1,048,576 \text{ parameters}$$

Now let's compute the parameter count using LoRA with Rank $r = 16$:

- **Matrix $A$** has shape $(r \times k) = 16 \times 1024 = 16,384 \text{ parameters}$
- **Matrix $B$** has shape $(d \times r) = 1024 \times 16 = 16,384 \text{ parameters}$

$$\text{Params}_{\text{LoRA}} = 16,384 + 16,384 = 32,768 \text{ parameters}$$

Let's compute the parameter reduction ratio:

$$\text{Reduction Ratio} = \frac{32,768}{1,048,576} \approx 0.03125 \quad (3.125\%)$$

By using LoRA with rank $r=16$, we reduced the number of trainable parameters for that layer by **96.875%**!

---

### Why LoRA Starts at Zero ($\Delta W = 0$)

When initializing LoRA matrices:
- **Matrix $A$** is initialized with random Gaussian values $\mathcal{N}(0, \sigma^2)$.
- **Matrix $B$** is initialized to **all zeros**.

Because Matrix $B = 0$:

$$\Delta W = B \cdot A = 0 \cdot A = 0$$

At the very first step of training, the LoRA update is exactly zero! 

This ensures that the model starts training with the **exact performance and predictions of the base model**, without any sudden performance drops or random noise at step 0.

# Mastering LoRA Hyperparameters

When configuring LoRA in Python, you will tune four key parameters:

```text
┌───────────────────┬───────────────────────────────┬────────────────────────────────┐
│ Hyperparameter    │ Description                   │ Standard Recommended Value     │
├───────────────────┼───────────────────────────────┼────────────────────────────────┤
│ Rank (r)          │ Inner matrix bottleneck size  │ r = 8 or r = 16                │
│ Alpha (α)         │ LoRA scaling multiplier       │ α = 2 × r (e.g., α = 32)       │
│ Dropout           │ Regularization probability    │ lora_dropout = 0.05            │
│ Target Modules    │ Layers receiving LoRA         │ ["q_proj", "k_proj", "v_proj"] │
└───────────────────┴───────────────────────────────┴────────────────────────────────┘
```

Let's break down each hyperparameter in detail.

---

### 1. Rank ($r$)
The rank $r$ defines the inner dimension of the low-rank matrices $A$ and $B$.

- **$r = 4$ or $8$**: Lightweight adaptation (great for classification, simple formatting, or sentiment tuning).
- **$r = 16$**: The sweet spot for instruction tuning, chat personas, and style adaptation (**Used in Project Sahur**).
- **$r = 32$ or $64$**: High-rank adaptation (used for complex domain shifts like biomedical code or multi-turn reasoning).

> 💡 **Key Insight**: Increasing $r$ beyond 16 yields diminishing returns for personality tuning while increasing VRAM usage and risk of overfitting.

---

### 2. Alpha ($\alpha$)
Alpha is a scaling factor applied to the output of the LoRA matrices:

$$\text{Output} = W_0 \cdot x + \left(\frac{\alpha}{r}\right) \cdot (B \cdot A \cdot x)$$

Why do we need $\alpha$?
- When you experiment with different values of rank $r$ (e.g., testing $r=8$ vs $r=16$), scaling by $\frac{\alpha}{r}$ keeps the relative magnitude of the weight updates consistent.
- **Golden Rule**: Always set $\alpha = 2 \times r$. If $r=16$, set $\alpha=32$.

---

### 3. Dropout (`lora_dropout`)
Dropout randomly zeroes out a fraction of LoRA activations during training (e.g. `0.05` = 5%).

This prevents the adapter from memorizing exact training sentences, forcing it to learn generalized style patterns.

---

### 4. Target Modules (`target_modules`)

In a Transformer architecture, linear projection matrices exist in two main sections:

```text
1. ATTENTION MODULES:
   - q_proj (Query projection  ──► Controls context search focus)
   - k_proj (Key projection    ──► Controls token key representations)
   - v_proj (Value projection  ──► Controls token value extraction)
   - o_proj (Output projection ──► Controls attention output mixing)

2. FEED-FORWARD NETWORK (FFN) MODULES:
   - gate_proj (SwiGLU gate    ──► Controls activation gating)
   - up_proj (Up projection    ──► Expands hidden dimension)
   - down_proj (Down projection──► Compresses back to hidden dimension)
```

In early LoRA implementations, adapters were attached only to `q_proj` and `v_proj`.

Modern research shows that attaching LoRA adapters to **all linear projection layers** (`"all-linear"`) produces higher quality fine-tunes with minimal extra VRAM footprint.

# QLoRA: Quantized Low-Rank Adaptation

In 2023, Tim Dettmers and the University of Washington introduced **QLoRA**.

QLoRA takes PEFT efficiency one step further by combining **4-bit base model quantization** with **LoRA adapters**.

```text
┌────────────────────────────────────────────────────────────────────────┐
│ QLORA ARCHITECTURE                                                     │
├────────────────────────────────────────────────────────────────────────┤
│ Base Model Weights ──► Quantized to 4-bit NormalFloat (NF4)            │
│                       (Frozen in VRAM at 0.5 bytes / param)            │
│                                                                        │
│ LoRA Adapters      ──► Kept in 16-bit Precision (FP16 / BF16)         │
│                       (Trainable on GPU)                               │
└────────────────────────────────────────────────────────────────────────┘
```

### Key QLoRA Innovations:

1. **NF4 (NormalFloat 4)**: An information-theoretically optimal 4-bit data type for normally distributed neural network weights.
2. **Double Quantization**: Quantizes the quantization constants themselves, saving an additional 0.37 bits per parameter.
3. **Paged Optimizers**: Uses CUDA Unified Memory to automatically page optimizer memory spikes to CPU RAM if GPU VRAM fills up.

With QLoRA, fine-tuning **Qwen3-0.6B** consumes less than **2.5 GB of VRAM**, making training fully achievable on a single consumer GPU or free Google Colab instance!

# Beyond LoRA: Understanding DoRA (Weight-Decomposed Low-Rank Adaptation)

In 2024, researchers from NVIDIA introduced **DoRA (Weight-Decomposed Low-Rank Adaptation)**.

DoRA improves upon standard LoRA by decomposing the weight matrix into two components:
1. **Magnitude ($m$)**: A directional scalar vector controlling weight magnitude.
2. **Direction ($V$)**: A directional matrix updated using standard LoRA ($V = W_0 + B \cdot A$).

```text
Weight W = Magnitude (m)  ×  Normalized Direction ( V / ||V|| )
```

### Why DoRA Matters:
- Standard LoRA alters weight magnitude and direction proportionally.
- Full fine-tuning alters magnitude and direction independently.
- DoRA mimics Full Fine-Tuning learning dynamics more accurately than standard LoRA without adding significant training overhead.

In Hugging Face `peft`, enabling DoRA requires just one extra line:

```python
peft_config = LoraConfig(
    r=16,
    lora_alpha=32,
    use_dora=True,  # Enables DoRA weight decomposition
    target_modules=["q_proj", "v_proj"]
)
```

# Hands-On: Using Hugging Face `peft`

Hugging Face provides the `peft` library to inject LoRA adapters into any `transformers` model with clean Python syntax.

### Step 1: Install `peft` and `bitsandbytes`

```bash
pip install peft bitsandbytes
```

---

### Step 2: Configure and Attach LoRA in Python

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training, TaskType

# 1. Configure 4-bit QLoRA Quantization
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.float16,
    bnb_4bit_use_double_quant=True
)

# 2. Load Base Model in 4-bit
model_id = "Qwen/Qwen3-0.6B"
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    quantization_config=bnb_config,
    device_map="auto"
)

# 3. Prepare Model for k-bit Training
model = prepare_model_for_kbit_training(model)

# 4. Define LoRA Configuration
peft_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,                                        # Rank
    lora_alpha=32,                               # Scaling factor
    lora_dropout=0.05,                           # Dropout rate
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"] # Target layers
)

# 5. Inject PEFT Adapter into Base Model
peft_model = get_peft_model(model, peft_config)

# 6. Print Parameter Audit
peft_model.print_trainable_parameters()
```

### Output Breakdown:

```text
trainable params: 1,572,864 || all params: 601,572,864 || trainable%: 0.2614%
```

Out of **601 Million total parameters**, only **1.57 Million** are trainable!

Over **99.73% of the network is frozen**, cutting VRAM and compute drastically.

# Adapter File Management: Saving, Loading & Merging

One of the greatest advantages of LoRA is file portability.

```text
┌────────────────────────────────────────────────────────────────────────┐
│ CHECKPOINT STORAGE COMPARISON                                          │
├────────────────────────────────────────────────────────────────────────┤
│ Full Base Model Weights (`Qwen3-0.6B`)  ──► ~ 1.2 GB                  │
│ LoRA Adapter Folder (`sahur-lora-v1`)   ──► ~ 6.0 MB                  │
└────────────────────────────────────────────────────────────────────────┘
```

Instead of uploading 1.2 GB checkpoints after every training run, you only save and transfer a tiny 6 MB adapter folder!

---

### 1. Saving an Adapter

```python
# Saves only the LoRA adapter weights and config file
peft_model.save_pretrained("checkpoints/sahur-lora-v1")
```

Inside `checkpoints/sahur-lora-v1/`, two files are generated:

```text
checkpoints/sahur-lora-v1/
├── adapter_config.json      ◄── Hyperparameters (r=16, alpha=32, target_modules)
└── adapter_model.safetensors ◄── Binary weights of Matrices A and B (~6 MB)
```

---

### 2. Loading an Adapter onto a Base Model

```python
from transformers import AutoModelForCausalLM
from peft import PeftModel

# 1. Load Original Base Model
base_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-0.6B")

# 2. Attach Trained LoRA Adapter
model = PeftModel.from_pretrained(base_model, "checkpoints/sahur-lora-v1")

# The model is now ready for inference with the fine-tuned Sahur persona!
```

---

### 3. Merging Adapters for GGUF Export

When fine-tuning is finished and you want to export your model to **GGUF format** for local deployment (Ollama / `llama.cpp`), you must merge the adapter weights permanently back into the base model.

```python
# Merges Matrix (B * A) directly into base weights W0
merged_model = model.merge_and_unload()

# Saves the complete merged model as a standalone 1.2 GB model folder
merged_model.save_pretrained("models/Sahur-v0.1-Merged")
```

Once merged, the model no longer requires the `peft` library to run!

# Debugging & Troubleshooting Common PEFT Errors

When working with PEFT and LoRA in production, you may encounter a few common errors. Here is how to diagnose and fix them:

### 1. `RuntimeError: element 0 of tensors does not require grad`
- **Cause**: All parameters in the model are frozen and no trainable adapters were attached properly.
- **Fix**: Ensure you call `get_peft_model(model, peft_config)` and verify that `model.print_trainable_parameters()` shows $>0$ trainable parameters.

### 2. `Loss is NaN or Inf` During Training
- **Cause**: Learning rate is set too high for FP16 training, causing numerical overflow.
- **Fix**: Use `bf16=True` on supported GPUs, or lower the learning rate from `5e-4` to `2e-4`.

### 3. Model Output Ignores Fine-Tuned Persona
- **Cause**: LoRA scaling factor ($\alpha$) is set too low relative to rank $r$, making adapter weight updates too weak.
- **Fix**: Ensure $\alpha = 2 \times r$ (e.g. $r=16, \alpha=32$).

### 4. High VRAM Overhead During Quantized Training
- **Cause**: Forgot to call `prepare_model_for_kbit_training(model)` before wrapping with PEFT.
- **Fix**: Always call `prepare_model_for_kbit_training()` when using 4-bit `bitsandbytes` models.

```python
    )
    test_model = get_peft_model(model, config)
    trainable_params = sum(p.numel() for p in test_model.parameters() if p.requires_grad)
    pct = (trainable_params / base_params) * 100
    
    print(f"\n--- LoRA RANK r={r_val} (alpha={r_val*2}) ---")
    print(f"Trainable Parameters: {trainable_params:,}")
    print(f"Percentage of Base Model: {pct:.4f}%")

print("\nAudit Complete!")
```

Run the script:
```bash
python scripts/test_peft_ranks.py
```

Observe how changing the rank scales the trainable parameter footprint from $r=4$ to $r=64$!
