Welcome to **Lesson 2.6**.

In **Lesson 2.5**, you learned how to load and inspect full LLMs using the Hugging Face `transformers` library.

Now, we face the central engineering problem of AI fine-tuning: **Full Fine-Tuning is wildly expensive.**

If you try to fine-tune 100% of the weights in a model, storing the model weights, gradients, and optimizer states requires up to 16 bytes of VRAM per parameter. A 7B parameter model would require over 110 GB of VRAM just to train!

Enter **PEFT (Parameter-Efficient Fine-Tuning)** and **LoRA (Low-Rank Adaptation)**.

PEFT allows us to freeze 99%+ of the base model weights and train a tiny fraction of new adapter parameters (< 1%), cutting VRAM requirements by over 75% while achieving identical fine-tuning quality.

# The VRAM Math Problem: Why Full Fine-Tuning Fails

Why does fine-tuning a model require so much more VRAM than just running inference?

During **Inference**, you only store the model weights in 16-bit precision:
$$\text{VRAM}_{\text{inference}} = 2 \text{ bytes} \times \text{Parameters}$$

For **Qwen3-0.6B** (600M params), inference takes **~1.2 GB VRAM**.

However, during **Full Fine-Tuning**, PyTorch must store:
1. **Model Weights** (16-bit): 2 bytes / param
2. **Gradients** ($\nabla W$) (16-bit): 2 bytes / param
3. **AdamW Optimizer States** (32-bit FP32 Master Copy + Momentum $m$ + Variance $v$): 12 bytes / param
4. **Activation Tensors**: Stored in VRAM for backpropagation

```text
┌────────────────────────────────────────────────────────────────────────┐
│ VRAM COST PER PARAMETER (FULL FINE-TUNING)                             │
├────────────────────────────────────────────────────────────────────────┤
│ Weights (FP16)     : 2 Bytes                                           │
│ Gradients (FP16)   : 2 Bytes                                           │
│ AdamW States (FP32): 12 Bytes (Master Copy + Momentum + Variance)       │
├────────────────────────────────────────────────────────────────────────┤
│ TOTAL              : ~ 16 Bytes per Parameter                          │
└────────────────────────────────────────────────────────────────────────┘
```

```text
Qwen3-0.6B (600M Params) ──► Full Fine-Tuning requires ~ 9.6 GB VRAM
Llama-3-8B (8B Params)    ──► Full Fine-Tuning requires ~ 128 GB VRAM
```

Your RTX 2050 has **4 GB VRAM**. Full fine-tuning would crash instantly with a `CUDA out of memory` error.

# The Solution: LoRA (Low-Rank Adaptation)

In 2021, researchers at Microsoft published a paper: *"LoRA: Low-Rank Adaptation of Large Language Models"*.

They made a key discovery: **When fine-tuning an LLM for a new task or persona, the weight updates ($\Delta W$) have a low "intrinsic rank".**

You don't need to modify all 600 million weights. You can represent the weight change using two small, low-rank matrices.

### The LoRA Formula

Instead of updating the frozen base weight matrix $W_0$ directly:

$$W = W_0 + \Delta W$$

LoRA factorizes $\Delta W$ into the product of two small matrices $A$ and $B$:

$$\Delta W = B \cdot A$$

```text
                 BASE WEIGHT MATRIX (Frozen)
                         W₀ (d × k)
                       ┌───────────┐
                       │           │
                       │  FROZEN   │
                       │           │
                       └───────────┘
                             +
                 LORA ADAPTER MATRICES (Trainable)
             Matrix B (d × r)   ×   Matrix A (r × k)
               ┌───┐             ┌───────────┐
               │   │      ×      │  TRAIN    │
               └───┘             └───────────┘
```

- **$W_0$**: Base model matrix of shape $(d \times k)$. **FROZEN** (No gradient storage).
- **Matrix $A$**: Low-rank matrix of shape $(r \times k)$. **TRAINABLE**.
- **Matrix $B$**: Low-rank matrix of shape $(d \times r)$. **TRAINABLE**.
- **$r$ (Rank)**: A very small integer (e.g., $r = 8$ or $r = 16$).

Because $r \ll \min(d, k)$, the number of trainable parameters drops by **99%+**!

---

# Key LoRA Hyperparameters Explained

When configuring LoRA in code, you will set four primary hyperparameters:

### 1. Rank ($r$)
- **What it is**: The inner dimension of the low-rank matrices $A$ and $B$.
- **Common values**: $4, 8, 16, 32, 64$.
- **Rule of thumb**: 
  - $r=8$ or $r=16$ is ideal for style, persona, and instruction fine-tuning (**Project Sahur** uses $r=16$).
  - Higher rank ($r=64$) is only needed for complex domain adaptation (e.g., teaching medical math).

### 2. Alpha ($\alpha$)
- **What it is**: A scaling factor applied to the LoRA weights ($\frac{\alpha}{r} \cdot \Delta W$).
- **Rule of thumb**: Set $\alpha = 2 \times r$ (e.g., if $r=16$, set $\alpha=32$). This stabilizes learning rates across different rank experiments.

### 3. Dropout (`lora_dropout`)
- **What it is**: Dropout probability applied to LoRA layers for regularization.
- **Common values**: `0.05` or `0.1` (prevents overfitting on small datasets).

### 4. Target Modules (`target_modules`)
- **What it is**: Specifies which linear projection matrices inside the Transformer get LoRA adapters.
- **In Attention**: `q_proj`, `k_proj`, `v_proj`, `o_proj`.
- **In FFN**: `gate_proj`, `up_proj`, `down_proj`.
- **Rule of thumb**: Applying LoRA to all linear layers (`"all-linear"`) yields the best fine-tuning quality.

# Using Hugging Face `peft` in Python

Hugging Face provides the `peft` library to attach LoRA adapters to any `transformers` model in just a few lines of code:

```python
import torch
from transformers import AutoModelForCausalLM
from peft import LoraConfig, get_peft_model, TaskType

# 1. Load Base Model
model_id = "Qwen/Qwen3-0.6B"
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    torch_dtype=torch.float16,
    device_map="auto"
)

# 2. Define LoRA Configuration
peft_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,                         # Rank
    lora_alpha=32,                # Scaling factor
    lora_dropout=0.05,            # Dropout
    target_modules=["q_proj", "v_proj", "k_proj", "o_proj"]
)

# 3. Wrap Model with PEFT
model = get_peft_model(model, peft_config)

# 4. Print Parameter Reduction
model.print_trainable_parameters()
```

### Output Example:
```text
trainable params: 1,572,864 || all params: 601,572,864 || trainable%: 0.2614%
```

Notice that **99.74% of the parameters are frozen**! You are only training **1.5 Million parameters** instead of 601 Million!

# Saving, Loading, and Merging LoRA Adapters

One of the best features of LoRA is file size.

- **Base Model Weights (`Qwen3-0.6B`)**: ~1.2 GB
- **LoRA Adapter Weights (`sahur-adapter`)**: **~6 MB**!

Instead of saving a 1.2 GB model checkpoint after every training epoch, you only save a tiny 6 MB adapter folder!

### 1. Saving an Adapter
```python
model.save_pretrained("checkpoints/sahur-lora-v1")
```

Inside `checkpoints/sahur-lora-v1/`, you will find:
- `adapter_config.json` (Hyperparameter settings)
- `adapter_model.safetensors` (~6 MB binary weights)

### 2. Loading an Adapter onto a Base Model
```python
from peft import PeftModel

# Load Base Model
base_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-0.6B")

# Attach Trained LoRA Adapter
model = PeftModel.from_pretrained(base_model, "checkpoints/sahur-lora-v1")
```

### 3. Merging Adapters for GGUF / Export
When you are ready to export your final model for local inference (Ollama / llama.cpp), you merge the adapter back into the base model weights:

```python
# Fuses LoRA weights into base weights and unloads adapter overhead
merged_model = model.merge_and_unload()
merged_model.save_pretrained("models/Sahur-v0.1-Merged")
```

Think of a Base LLM as a grand piano:

```text
Base Model (Qwen3)   ➔ The Grand Piano (Heavy, fixed, cast-iron frame)
LoRA Adapter (Sahur)  ➔ A Mute Pedal / Sound Modifier (Lightweight clip-on accessory)

```

You don't rebuild the piano to change its acoustic tone; you attach a tiny modifier pedal.
