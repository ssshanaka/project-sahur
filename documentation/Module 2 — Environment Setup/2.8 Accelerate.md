# The Multi-GPU Problem

Imagine you write a simple PyTorch training loop on your laptop's single GPU. It works perfectly.

Now imagine you get access to a cloud server with 4 NVIDIA A100 GPUs. You want to run the same script across all 4 GPUs to train 4x faster.

In raw PyTorch, you'd need to:

1. Initialize distributed process groups
2. Assign each GPU a unique rank index
3. Bind each Python process to its specific GPU
4. Wrap the model in `DistributedDataParallel`
5. Split your dataset across GPUs using `DistributedSampler`
6. Manage mixed-precision gradient scaling manually
7. Prevent every GPU from printing duplicate output 4 times
8. Clean up process groups on exit

That's **50+ lines of fragile distributed code**. If you make a single indexing mistake, your training deadlocks or crashes with cryptic error messages.

It's like trying to conduct an orchestra by individually telling each musician when to play every single note — exhausting and error-prone.

---

# The Accelerate Solution: 3 Lines of Code

`accelerate` replaces all of that boilerplate with three simple concepts:

```text
1. Initialize       ──► accelerator = Accelerator()
2. Prepare           ──► model, optimizer, dataloader = accelerator.prepare(...)
3. Replace backward  ──► accelerator.backward(loss)
```

That's it.

The exact same Python script will now run seamlessly on:

- A CPU
- A single GPU (your RTX 2050)
- A multi-GPU server (4x A100s)
- A TPU cluster
- A DeepSpeed or FSDP distributed environment

You write clean code once. Accelerate handles hardware dispatch automatically.

Think of `accelerate` as a universal power adapter. You plug in your device (your PyTorch code), and it figures out the right voltage and socket type (CPU, GPU, multi-GPU) for wherever you are.

# Distributed Training Architectures

When scaling LLM training across multiple GPUs, there are three primary strategies. You don't need to master their internals right now — but understanding what they do at a high level will help you make sense of the ecosystem.

### 1. DDP (Distributed Data Parallel)

```text
GPU 0: [ Full Model Copy ] ──► Processes Data Batch A
GPU 1: [ Full Model Copy ] ──► Processes Data Batch B
GPU 2: [ Full Model Copy ] ──► Processes Data Batch C
GPU 3: [ Full Model Copy ] ──► Processes Data Batch D
                    │
                    ▼
         Average gradients across all GPUs, then update weights
```

Every GPU holds a **complete copy** of the model. Each one processes a different slice of data. At the end of each step, gradients are averaged across GPUs.

**Best for**: Models that fit entirely on one GPU (like Qwen3-0.6B).

**Limitation**: If the model is too large for one GPU, DDP can't help.

### 2. FSDP (Fully Sharded Data Parallel)

Instead of copying the full model onto every GPU, FSDP **splits** (shards) the model weights, gradients, and optimizer states across GPUs.

```text
GPU 0: [ 1/4 of Model ] [ 1/4 of Gradients ] [ 1/4 of Optimizer ]
GPU 1: [ 1/4 of Model ] [ 1/4 of Gradients ] [ 1/4 of Optimizer ]
GPU 2: [ 1/4 of Model ] [ 1/4 of Gradients ] [ 1/4 of Optimizer ]
GPU 3: [ 1/4 of Model ] [ 1/4 of Gradients ] [ 1/4 of Optimizer ]
```

When a GPU needs a layer that lives on another GPU, it fetches it temporarily, uses it, then discards it.

**Best for**: Large models (8B–70B) that can't fit on a single GPU.

### 3. DeepSpeed ZeRO (by Microsoft)

DeepSpeed ZeRO is similar to FSDP but offers three progressive levels of memory optimization:

```text
ZeRO-1 ──► Shards Optimizer States only        (4x VRAM saving)
ZeRO-2 ──► Shards Optimizer States + Gradients  (8x VRAM saving)
ZeRO-3 ──► Shards Everything (Weights + Grads + Optimizer) (16x+ saving)
```

With ZeRO-3, a 70B model whose weights alone require 140 GB can be distributed across four 48GB GPUs — making training possible for models that would otherwise be completely impossible.

### Which One Do We Use?

For **Project Sahur** with Qwen3-0.6B on a single GPU, we use the simplest setup — single-GPU with `accelerate` handling `device_map="auto"` for us. But it's valuable to know these architectures exist for when you scale to larger models.

```text
┌──────────────────────┬──────────────────────┬────────────────────────────┐
│ Architecture         │ VRAM per GPU         │ Best For                   │
├──────────────────────┼──────────────────────┼────────────────────────────┤
│ Single GPU           │ 100% of model        │ < 3B Parameters            │
│ DDP (Replicated)     │ 100% of model        │ < 8B Parameters            │
│ FSDP / ZeRO-2        │ ~ 25% of model       │ 8B – 34B Parameters        │
│ ZeRO-3 (Full Shard)  │ ~ 10% of model       │ 70B+ Parameters            │
└──────────────────────┴──────────────────────┴────────────────────────────┘
```

# How `accelerate` Powers `device_map="auto"`

In **Lesson 2.5**, you learned that passing `device_map="auto"` to `transformers` lets models automatically distribute layers across GPU and CPU memory.

That magic is powered directly by `accelerate`.

Here's what happens behind the scenes:

1. **Inspects VRAM**: Checks how much GPU memory is available.
2. **Measures Layers**: Calculates the size of every Transformer block.
3. **Builds a Map**: Assigns layers to GPU VRAM until ~90% capacity, then overflows remaining layers to CPU RAM.

```text
GPU VRAM (Fast)  ──► Layers 0 through N  (as many as fit)
CPU RAM  (Slower) ──► Remaining layers    (overflow)
NVMe SSD (Slowest)──► Last resort         (extreme cases)
```

Think of it like loading a moving truck. The most-used furniture goes in the truck (GPU). Overflow goes in the trailer (CPU). If you still have too much, it goes in storage (disk).

For our **Qwen3-0.6B**, the entire model fits comfortably in GPU VRAM, so `device_map="auto"` simply places everything on `cuda:0`.

# Mixed Precision: FP16 vs BF16

During training, performing all math in 32-bit precision (`FP32`) is slow and memory-intensive.

`accelerate` manages **Automatic Mixed Precision (AMP)**:

```text
Forward Pass Math    ──► Executed in 16-bit (FP16/BF16) for 2x Speed & Low VRAM
Loss & Weight Updates ──► Computed in 32-bit (FP32) for Numerical Stability
```

There are two common 16-bit formats:

```text
┌─────────────────┬─────────────────────────────────────────────────┐
│ FP16 (Half)     │ Fast, supported everywhere, but can underflow   │
│ BF16 (Brain)    │ Same dynamic range as FP32, no underflow issues │
└─────────────────┴─────────────────────────────────────────────────┘
```

**FP16** has a narrower range and can cause small gradient values to round to zero (underflow). PyTorch compensates with a `GradScaler`, but it adds complexity.

**BF16** (BFloat16, invented by Google Brain) has the same exponent range as FP32, so underflow is extremely rare. If your GPU supports it (Ampere/A100 and newer), BF16 is the better choice.

`accelerate` handles all of this automatically — you just specify `mixed_precision="fp16"` or `"bf16"` and it manages casting and scaling behind the scenes.

# The `accelerate` CLI Tools

`accelerate` includes command-line tools that simplify configuration:

### `accelerate config`

An interactive wizard that asks about your hardware setup:

```text
Which environment? ❯ This machine
Which type?        ❯ Single GPU
Mixed precision?   ❯ fp16
```

Your answers are saved to a config file so you don't repeat this every time.

### `accelerate launch`

Runs your training script with the saved configuration:

```text
accelerate launch scripts/train_sahur.py
```

Accelerate reads your config, handles process spawning and GPU bindings, and launches your script cleanly. No need to manually set environment variables or CUDA device indices.

### `accelerate env`

Inspects your system and prints a summary:

```text
- accelerate version: 0.33.0
- Platform: Windows-10
- PyTorch version: 2.4.0+cu121
- GPU type: NVIDIA GeForce RTX 2050
- Number of GPUs: 1
- Mixed precision supported: FP16
```

# How Accelerate Fits Into Project Sahur

In **Project Sahur**, `accelerate` works quietly in the background:

```text
LOCAL LAPTOP (RTX 2050 4GB):
  - device_map="auto" offloads layers cleanly
  - accelerate env inspects GPU capabilities

GOOGLE COLAB / CLOUD GPU:
  - accelerate launch runs SFTTrainer
  - Automatic FP16/BF16 mixed precision
```

You'll rarely interact with `accelerate` directly. Its power comes from the fact that `transformers`, `peft`, and `trl` all use it internally. When you call `device_map="auto"` or use `SFTTrainer`, `accelerate` is the engine doing the heavy lifting.

It guarantees that our training and inspection scripts remain **100% portable** across hardware setups — from your laptop to Google Colab to a cloud GPU cluster.
