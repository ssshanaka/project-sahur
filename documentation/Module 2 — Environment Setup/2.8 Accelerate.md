# The Multi-GPU Problem: Raw PyTorch Complexity

Imagine you write a PyTorch fine-tuning script on your laptop's single GPU:

```python
import torch

device = "cuda" if torch.cuda.is_available() else "cpu"
model.to(device)

for epoch in range(epochs):
    for batch in dataloader:
        inputs = batch["input_ids"].to(device)
        outputs = model(inputs)
        loss = outputs.loss
        loss.backward()
        optimizer.step()
        optimizer.zero_grad()
```

Now, imagine you want to run this exact same script on a 4-GPU server (e.g. 4x NVIDIA A100s).

### What Raw PyTorch Requires for Multi-GPU (DDP):

1. **Process Initialization**: Initialize `torch.distributed.init_process_group(backend="nccl")`.
2. **Rank Management**: Determine local rank (`LOCAL_RANK`), global rank (`RANK`), and world size (`WORLD_SIZE`).
3. **Device Binding**: Explicitly bind each Python process to `cuda:LOCAL_RANK`.
4. **Model Wrapping**: Wrap the model in `torch.nn.parallel.DistributedDataParallel(model, device_ids=[local_rank])`.
5. **Data Sampling**: Wrap your data loader in `torch.utils.data.distributed.DistributedSampler`.
6. **Gradient Scaling**: Manage `torch.cuda.amp.GradScaler()` manually across all GPUs.
7. **Clean Printing**: Prevent every GPU process from printing duplicated text 4 times to stdout.
8. **Process Cleanup**: Call `torch.distributed.destroy_process_group()` on exit.

```text
┌────────────────────────────────────────────────────────────────────────┐
│ RAW PYTORCH DDP BOILERPLATE                                            │
│ 50+ lines of distributed code ➔ Rigid setup ➔ Fragile device indices   │
└────────────────────────────────────────────────────────────────────────┘
```

If you make a single indexing mistake in raw PyTorch DDP, your training will deadlock or crash with unhelpful `NCCL` error tracebacks.

# The Accelerate Solution: 3 Lines of Code

The `accelerate` library replaces all 50+ lines of distributed PyTorch boilerplate with **3 simple lines**:

```python
# 1. Initialize the Accelerator
from accelerate import Accelerator

accelerator = Accelerator()

# 2. Prepare Model, Optimizer, and DataLoader
model, optimizer, dataloader = accelerator.prepare(model, optimizer, dataloader)

# 3. Replace loss.backward() with accelerator.backward(loss)
accelerator.backward(loss)
```

That's it.

The exact same Python script will now run seamlessly on:
- A CPU
- A single GPU (RTX 2050)
- A Multi-GPU server (4x A100 GPUs)
- A TPU cluster
- A DeepSpeed / FSDP distributed environment

You write clean code once; `accelerate` handles hardware dispatch automatically!

# Dissecting the `Accelerator` API

Let's look at the key methods provided by the `Accelerator` class:

```text
┌───────────────────────────────────┬────────────────────────────────────────────────────────┐
│ Accelerator Method                │ Purpose & Functionality                                │
├───────────────────────────────────┼────────────────────────────────────────────────────────┤
│ `accelerator = Accelerator()`     │ Detects hardware, ranks, precision, and environment    │
│ `accelerator.prepare(...)`        │ Wraps models in DDP/FSDP & configures data samplers     │
│ `accelerator.backward(loss)`      │ Handles gradient scaling & backprop across all devices │
│ `accelerator.print(...)`          │ Prints text ONLY from the main process (rank 0)        │
│ `accelerator.is_main_process`     │ Boolean flag to guard logging, saving, and checkpoints │
│ `accelerator.wait_for_everyone()` │ Synchronizes all GPU processes (barrier checkpoint)    │
│ `accelerator.unwrap_model(...)`   │ Removes DDP wrapper to extract underlying PyTorch model│
│ `accelerator.save_model(...)`     │ Saves clean model weights to disk without DDP overhead │
└───────────────────────────────────┴────────────────────────────────────────────────────────┘
```

---

### 1. `accelerator.prepare()`
When you pass your objects to `prepare()`:

```python
model, optimizer, train_dataloader, lr_scheduler = accelerator.prepare(
    model, optimizer, train_dataloader, lr_scheduler
)
```

Accelerate automatically:
- Moves model parameters to the correct GPU device (`cuda:local_rank`).
- Wraps the model in `DistributedDataParallel` if running on multi-GPU.
- Replaces the `DataLoader` sampler with a `DistributedSampler` so each GPU receives a unique, non-overlapping slice of data.
- Configures mixed precision (`fp16` / `bf16`) automatically.

---

### 2. `accelerator.backward(loss)`
In standard PyTorch mixed-precision training (`FP16`), small gradients can underflow to zero. PyTorch requires a `GradScaler` to scale loss up before backprop and unscale it before the optimizer step.

`accelerator.backward(loss)` replaces:
- `loss.backward()`
- `scaler.scale(loss).backward()`
- `scaler.step(optimizer)`
- `scaler.update()`

It handles scaling, unscaling, and gradient accumulation automatically behind one unified function call!

---

### 3. `accelerator.print()` & `accelerator.is_main_process`
When running on a 4-GPU server, 4 separate Python processes execute your script simultaneously.

If you write `print("Epoch 1 Complete")`, all 4 processes will print to your terminal:

```text
Epoch 1 Complete
Epoch 1 Complete
Epoch 1 Complete
Epoch 1 Complete
```

To prevent terminal clutter and duplicated file writes:

```python
# Option A: Use accelerator.print() (Only prints from rank 0)
accelerator.print(f"Epoch {epoch} complete | Loss: {loss.item():.4f}")

# Option B: Guard checkpoint saving with is_main_process
if accelerator.is_main_process:
    unwrapped_model = accelerator.unwrap_model(model)
    unwrapped_model.save_pretrained("checkpoints/sahur-v1")
```

# Distributed Communication Primitives (NCCL)

To understand how GPUs coordinate during multi-GPU training, we must look at **NCCL (NVIDIA Collective Communications Library)** primitives.

When running distributed training, GPUs communicate using four key collective primitives:

```text
┌───────────────────┬────────────────────────────────────────────────────────────────────────┐
│ Primitive         │ Mathematical Functionality                                             │
├───────────────────┼────────────────────────────────────────────────────────────────────────┤
│ 1. AllReduce      │ Sums / averages tensors across all GPUs and distributes result back    │
│ 2. AllGather      │ Collects tensors from all GPUs and concatenates them along batch dim   │
│ 3. Broadcast      │ Sends a tensor from Rank 0 (Master) to all other worker GPUs           │
│ 4. ReduceScatter  │ Sums tensors across GPUs and splits (shards) the result among nodes    │
└───────────────────┴────────────────────────────────────────────────────────────────────────┘
```

---

### Visualizing NCCL Primitives

```text
ALLREDUCE (Gradient Synchronization in DDP):
GPU 0: [Grad A] ──┐
GPU 1: [Grad B] ──┼──► [ AllReduce Sum: A + B + C + D ] ──► Every GPU gets [Avg Grad]
GPU 2: [Grad C] ──┤
GPU 3: [Grad D] ──┘

ALLGATHER (Gathering Evaluation Predictions):
GPU 0: [Pred 0] ──┐
GPU 1: [Pred 1] ──┼──► Every GPU gets concatenated array [Pred 0, Pred 1, Pred 2, Pred 3]
GPU 2: [Pred 2] ──┤
GPU 3: [Pred 3] ──┘
```

In `accelerate`, you can invoke these primitives directly:
- `accelerator.gather(tensor)` $\implies$ Invokes `AllGather`
- `accelerator.reduce(tensor, reduction="sum")` $\implies$ Invokes `AllReduce`

# Distributed Training Architectures Explained

When scaling LLM training across multiple GPUs, there are three primary distributed architectures you must know as an AI engineer:

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. DDP (DISTRIBUTED DATA PARALLEL)                                     │
│    Replicates 100% of Model & Optimizer on EVERY GPU.                  │
│    Best for: Small/Medium models that fit on 1 GPU (e.g. Qwen3-0.6B).  │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2. FSDP (FULLY SHARDED DATA PARALLEL - PYTORCH NATIVE)                 │
│    Shards Model Weights, Gradients, and Optimizer States across GPUs.   │
│    Best for: Large models (8B–70B) that exceed single GPU VRAM.        │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3. DEEPSPEED (MICROSOFT ZERO ARCHITECTURE)                             │
│    ZeRO-1: Shards Optimizer States (4x VRAM saving)                    │
│    ZeRO-2: Shards Optimizer States + Gradients (8x VRAM saving)        │
│    ZeRO-3: Shards Optimizer States + Gradients + Model Weights (16x+)  │
└────────────────────────────────────────────────────────────────────────┘
```

Let's dissect how each architecture manages memory.

---

### Architecture 1: DDP (Distributed Data Parallel)

In standard DDP, every GPU holds a **complete replica** of the model weights, gradients, and optimizer states:

```text
GPU 0: [ Full Model (1.2GB) ] [ Gradients (1.2GB) ] [ AdamW States (7.2GB) ] ──► Processes Data Slice A
GPU 1: [ Full Model (1.2GB) ] [ Gradients (1.2GB) ] [ AdamW States (7.2GB) ] ──► Processes Data Slice B
```

- **How it works**: Each GPU computes local gradients on its own data batch. At the end of the backward pass, GPUs execute an **AllReduce** operation to average gradients across all GPUs before updating weights.
- **Limitation**: If the model is too large to fit on 1 GPU, DDP cannot be used!

---

### Architecture 2: DeepSpeed ZeRO & FSDP

To fine-tune massive models (like 70B parameter LLMs), Microsoft introduced **ZeRO (Zero Redundancy Optimizer)**, implemented natively in PyTorch as **FSDP**.

Instead of replicating everything, FSDP **shards** (splits) the memory components across all GPUs:

```text
┌────────────────────────────────────────────────────────────────────────┐
│ DEEPSPEED / FSDP SHARDING LEVELS                                       │
├────────────────────────────────────────────────────────────────────────┤
│ ZeRO-Stage 1 ──► Shards Optimizer States across GPUs (4x Memory saving)│
│ ZeRO-Stage 2 ──► Shards Optimizer States + Gradients (8x Memory saving) │
│ ZeRO-Stage 3 ──► Shards Optimizer States + Gradients + Model Weights   │
│                  (16x+ Memory saving ➔ Full Model Sharding)            │
└────────────────────────────────────────────────────────────────────────┘
```

With ZeRO-3 / FSDP, a 70B parameter model whose weights normally require 140 GB VRAM can be sharded across four 48GB GPUs (35 GB per GPU), allowing you to train models that would otherwise be impossible to fit!

# CPU & NVMe Offloading Mechanics

When fine-tuning giant models on limited GPU hardware, ZeRO-3 and FSDP allow offloading inactive parameters directly to system CPU RAM or NVMe storage.

```text
┌────────────────────────────────────────────────────────────────────────┐
│ MEMORY HIERARCHY FOR OFF LOADING                                       │
├────────────────────────────────────────────────────────────────────────┤
│ GPU VRAM (Fastest - 1,000 GB/s) ──► Active Transformer Block Layer N   │
│ CPU RAM  (Medium  -    50 GB/s) ──► Inactive Layers + AdamW States     │
│ NVMe SSD (Slowest -     7 GB/s) ──► Swapped Optimizer States           │
└────────────────────────────────────────────────────────────────────────┘
```

### How CPU Offloading Works:
1. During the forward pass, layer parameters are fetched into GPU VRAM just before execution.
2. Immediately after computing activations, the layer weights are freed from VRAM.
3. AdamW optimizer updates are calculated directly on the CPU, saving massive VRAM at the cost of PCIe bus transfer time.

# Mixed Precision Acceleration (`FP16` vs `BF16` vs `FP8`)

During training, operating in 32-bit floating-point precision (`FP32`) is slow and memory-intensive.

`accelerate` manages **Automatic Mixed Precision (AMP)**:

```text
Forward Pass Math   ──► Executed in 16-bit (FP16 / BF16) for 2x Speed & Low VRAM
Loss & Weight Updates ──► Computed in 32-bit (FP32) for Numerical Stability
```

```text
┌─────────────────┬─────────────┬─────────────────┬──────────────────────────────────────────┐
│ Precision Mode  │ Exponent    │ Mantissa (Prec) │ Notes                                    │
├─────────────────┼─────────────┼─────────────────┼──────────────────────────────────────────┤
│ FP32 (Full)     │ 8 bits      │ 23 bits         │ Baseline precision (Slow & high VRAM)    │
│ FP16 (Half)     │ 5 bits      │ 10 bits         │ Fast, supported everywhere, needs scaler │
│ BF16 (Brain)    │ 8 bits      │ 7 bits          │ Same dynamic range as FP32, no underflow │
│ FP8 (E4M3/E5M2) │ 4/5 bits    │ 3/2 bits        │ Cutting-edge 8-bit float (H100 / B200)   │
└─────────────────┴─────────────┴─────────────────┴──────────────────────────────────────────┘
```

When initializing `Accelerator(mixed_precision="fp16")` or `mixed_precision="bf16"`, Accelerate handles activation casting and loss scaling automatically!

# How `accelerate` Powers `device_map="auto"`

In **Lesson 2.5**, you learned that passing `device_map="auto"` to Hugging Face `transformers` allows models to offload layers dynamically across GPU VRAM, CPU RAM, and NVMe disk space.

`device_map="auto"` is powered directly by `accelerate`!

### How `accelerate` Infers Device Maps:

1. **Calculates VRAM**: Inspects available GPU VRAM (`torch.cuda.mem_get_info()`).
2. **Calculates Layer Sizes**: Inspects parameter sizes of every Transformer block (`q_proj`, `k_proj`, `v_proj`, `mlp`).
3. **Builds Offload Graph**: Assigns layers 0 to $N$ into VRAM until 90% capacity is reached, then assigns remaining layers to CPU RAM.

```python
from accelerate import infer_auto_device_map
from transformers import AutoModelForCausalLM

# Load model metadata without loading weights into memory
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-0.6B", low_cpu_mem_usage=True)

# Infer optimal device map
device_map = infer_auto_device_map(model, max_memory={0: "3GB", "cpu": "12GB"})
print("Inferred Device Map:", device_map)
```

# Advanced Multi-GPU Training Script (`scripts/train_accelerate_advanced.py`)

Here is a complete, production-grade script demonstrating custom `accelerate` loops with gradient accumulation, evaluation, and clean model unwrapping:

```python
import torch
from torch.utils.data import DataLoader
from transformers import AutoModelForCausalLM, AutoTokenizer, AdamW, get_cosine_schedule_with_warmup
from accelerate import Accelerator

# 1. Initialize Accelerator
accelerator = Accelerator(mixed_precision="fp16", gradient_accumulation_steps=4)

MODEL_ID = "Qwen/Qwen3-0.6B"
accelerator.print(f"Loading Model & Tokenizer: {MODEL_ID}...")

tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)
model = AutoModelForCausalLM.from_pretrained(MODEL_ID)

# 2. Setup Optimizer & Scheduler
optimizer = AdamW(model.parameters(), lr=2e-4)

# 3. Prepare Model, Optimizer & DataLoader with Accelerate
model, optimizer, train_dataloader = accelerator.prepare(
    model, optimizer, train_dataloader
)

epochs = 3
for epoch in range(epochs):
    model.train()
    total_loss = 0.0
    
    for step, batch in enumerate(train_dataloader):
        with accelerator.accumulate(model):
            outputs = model(**batch)
            loss = outputs.loss
            
            # Accelerate handles backward & gradient scaling automatically
            accelerator.backward(loss)
            
            optimizer.step()
            optimizer.zero_grad()
            
            total_loss += loss.item()

    avg_loss = total_loss / len(train_dataloader)
    accelerator.print(f"Epoch {epoch+1}/{epochs} Complete | Avg Loss: {avg_loss:.4f}")

# 4. Save Final Model from Main Process
accelerator.wait_for_everyone()
if accelerator.is_main_process:
    unwrapped_model = accelerator.unwrap_model(model)
    unwrapped_model.save_pretrained("checkpoints/sahur-accelerate-v1")
    tokenizer.save_pretrained("checkpoints/sahur-accelerate-v1")
    print("Model Checkpoint Saved Cleanly!")
```

# Troubleshooting Multi-GPU & Accelerate Errors

Here are four common errors encountered during distributed execution and how to resolve them:

### 1. `NCCL error: unhandled system error / timeout`
- **Cause**: GPUs failed to synchronize over the network during AllReduce gradient aggregation (often caused by firewall blocks or mismatched CUDA versions).
- **Fix**: Set environment variable `export NCCL_DEBUG=INFO` to inspect network interfaces, or set `export NCCL_IB_DISABLE=1` if InfiniBand is unavailable.

### 2. `CUDA out of memory on GPU 0 while GPU 1 is empty`
- **Cause**: Forgot to call `accelerator.prepare(model, train_dataloader)`, causing Process 0 to run all computations while other GPUs sit idle.
- **Fix**: Always pass model and data loaders through `accelerator.prepare()`.

### 3. Duplicate Text Outputs in Terminal
- **Cause**: Using standard `print()` calls in a multi-GPU environment without checking process rank.
- **Fix**: Replace `print()` with `accelerator.print()`, or wrap code blocks with `if accelerator.is_main_process:`.

### 4. Mismatched Learning Rate on Multi-GPU Runs
- **Cause**: Effective batch size scales linearly with the number of GPUs ($N$), but learning rate was kept at single-GPU scale.
- **Fix**: When scaling from 1 GPU to $N$ GPUs, scale the learning rate by $\sqrt{N}$ or adjust `gradient_accumulation_steps` to maintain a constant effective batch size.

tensor = torch.tensor([1.0, 2.0, 3.0], device=accelerator.device)

if accelerator.is_main_process:
    print(f"\nGathered Tensor Across Devices: {synced_tensor}")
