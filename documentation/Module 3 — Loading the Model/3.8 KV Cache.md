In **Lessons 3.4 through 3.7**, we mastered sampling strategies—controlling Temperature, Top-k, and Top-p to give Sahur a dynamic, natural Gen Z persona.

Now, we face an invisible engineering wall: **Inference Speed & Computational Efficiency**.

If you've ever built a basic Transformer generation loop without optimization, you might have noticed a frustrating pattern: the longer the output gets, the slower each new token takes to generate. Token #1 takes 20 milliseconds, but token #500 takes 2 full seconds!

Why does this happen? Because by default, a naive Transformer recalculates attention for every previous word in the prompt from scratch on every single token step.

In this final lesson of Module 3, we will dissect the **KV Cache (Key-Value Cache)**—the single most important memory optimization in modern LLM inference engines.

# Step 1 — Why does this even exist?

Let's trace what happens when Qwen3 generates a sentence word-by-word without caching.

Suppose your prompt is 3 tokens long: `["Yo", "Sahur", ","]`.

1. **Step 1**: To predict token 4 (`"what's"`), the model projects Query, Key, and Value matrices for tokens `[1, 2, 3]`.
2. **Step 2**: Token 4 (`"what's"`) is appended. Now the prompt is 4 tokens long: `["Yo", "Sahur", ",", "what's"]`.
3. **Step 3**: To predict token 5 (`"good"`), a naive Transformer runs matrix multiplication to project Keys and Values for `[1, 2, 3, 4]` again!

Notice the disaster here: **Tokens 1, 2, and 3 have not changed!** Their weight matrices are frozen, their positional embeddings are fixed, and their historical context is identical. Yet, without caching, the GPU wastes millions of TFLOPS re-computing the exact same Key ($K$) and Value ($V$) projections for previous tokens over and over again.

### Time Complexity Comparison:

- **Without KV Cache**: Generating $N$ tokens requires $1 + 2 + 3 + \dots + N = \frac{N(N+1)}{2}$ token passes $\to \mathcal{O}(N^2)$ quadratic complexity.
- **With KV Cache**: Generating $N$ tokens requires storing past $K$ and $V$ tensors and processing only $1$ new token per step $\to \mathcal{O}(N)$ linear complexity.

# Step 2 — Internal Mechanics

### 1. Prefill Phase vs. Decode Phase

LLM inference consists of two distinct operational modes:

```text
                                [ USER PROMPT TENSORS ]
                                           │
                                           ▼
                      ┌─────────────────────────────────────────┐
                      │             PREFILL PHASE               │
                      │  Processes all prompt tokens in parallel│
                      │  Computes & saves initial KV Cache      │
                      └────────────────────┬────────────────────┘
                                           │
                                           ▼
                      ┌─────────────────────────────────────────┐
                      │              DECODE PHASE               │
                      │  Generates 1 token at a time            │
                      │  Fetches old KV, appends new K_i, V_i   │
                      └─────────────────────────────────────────┘

```

#### A. The Prefill Phase (Compute-Bound)

- The entire prompt of length $L$ is passed through Qwen3's 28 layers simultaneously in parallel.
- PyTorch calculates Query ($Q$), Key ($K$), and Value ($V$) matrices for all $L$ tokens at once.
- The $K$ and $V$ tensors for all $L$ tokens across all 28 layers are saved in GPU VRAM as the **Initial KV Cache**.

#### B. The Decode Phase (Memory-Bandwidth Bound)

- The sequence length of the input is strictly **1 new token**.
- The model computes $Q_{new}$, $K_{new}$, and $V_{new}$ for that single new token.
- $K_{new}$ and $V_{new}$ are concatenated with the cached $K_{cached}$ and $V_{cached}$ tensors in GPU memory.
- Multi-Head Attention computes scaled dot-product attention between $Q_{new}$ and the updated $K_{cached}$, then multiplies by $V_{cached}$:

$$\text{Attention}(Q_{new}, K_{cached}, V_{cached}) = \text{Softmax}\left(\frac{Q_{new} K_{cached}^T}{\sqrt{d_k}}\right) V_{cached}$$

---

### 2. The Memory Trade-Off (Compute vs. VRAM)

KV Cache is not a free lunch. We are trading **GPU Memory (VRAM)** to save **GPU Compute (Time)**.

How much VRAM does the KV Cache take? Here is the exact mathematical formula:

$$\text{KV Cache Size (Bytes)} = 2 \times n_{\text{layers}} \times n_{\text{heads\_kv}} \times d_{\text{head}} \times \text{seq\_len} \times \text{precision\_bytes}$$

Where:

- Factor of $2$ = Stores both Key ($K$) and Value ($V$) matrices.
- $n_{\text{layers}}$ = Number of Transformer layers in the model (Qwen3-0.6B = 28 layers).
- $n_{\text{heads\_kv}}$ = Number of Key/Value attention heads (Qwen3 uses Grouped-Query Attention).
- $d_{\text{head}}$ = Hidden dimension size per head ($\frac{d_{\text{model}}}{n_{\text{heads}}}$).
- $\text{precision\_bytes}$ = FP16 = 2 bytes per float.

# Step 3 — Notebook Walkthrough (Cell-by-Cell)

Open your Google Colab notebook and let's run a live benchmark comparing generation speeds with and without KV Cache.

### 📦 Cell 1: Model Initialization

**What this cell does:** Loads `Qwen/Qwen3-0.6B` onto the T4 GPU.

```python
import time
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

MODEL_ID = "Qwen/Qwen3-0.6B"

print("Loading tokenizer and model...")
tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)

if tokenizer.pad_token_id is None:
    tokenizer.pad_token_id = tokenizer.eos_token_id

model = AutoModelForCausalLM.from_pretrained(
    MODEL_ID,
    torch_dtype=torch.float16,
    device_map="auto"
)

print(f"Model mounted on GPU: {model.device}")

```

---

### 💬 Cell 2: Test Prompt Setup

**What this cell does:** Prepares a prompt that requires generating a multi-paragraph response.

```python
messages = [
    {"role": "system", "content": "You are Sahur, a hyper-responsive Gen Z AI assistant."},
    {"role": "user", "content": "Write a detailed 150-word story about an AI assistant running out of coffee."}
]

formatted_prompt = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True
)

inputs = tokenizer(formatted_prompt, return_tensors="pt").to("cuda")
prompt_len = inputs.input_ids.shape[1]

print(f"Prompt encoded into {prompt_len} tokens.")

```

---

### ⚡ Cell 3: Generation WITH KV Cache (`use_cache=True`)

**What this cell does:** Measures token generation speed (Tokens/Second) with KV Cache enabled.

```python
print("1️⃣ Benchmarking WITH KV Cache (use_cache=True)...")

torch.cuda.synchronize()  # Wait for GPU idle
start_time = time.time()

with torch.no_grad():
    cached_output = model.generate(
        input_ids=inputs.input_ids,
        attention_mask=inputs.attention_mask,
        max_new_tokens=150,
        use_cache=True,  # Enables KV Cache
        do_sample=False,
        pad_token_id=tokenizer.pad_token_id,
        eos_token_id=tokenizer.eos_token_id
    )

torch.cuda.synchronize()  # Sync GPU execution timer
cached_time = time.time() - start_time

cached_tokens_gen = cached_output[0].shape[0] - prompt_len
cached_tps = cached_tokens_gen / cached_time

print(f"Generated {cached_tokens_gen} tokens in {cached_time:.2f} seconds.")
print(f"🔥 SPEED WITH CACHE: {cached_tps:.2f} tokens/sec")

```

---

### 🐢 Cell 4: Generation WITHOUT KV Cache (`use_cache=False`)

**What this cell does:** Measures token generation speed with KV Cache disabled, forcing full $O(N^2)$ recalculation.

```python
print("2️⃣ Benchmarking WITHOUT KV Cache (use_cache=False)...")

torch.cuda.synchronize()
start_time = time.time()

with torch.no_grad():
    no_cache_output = model.generate(

    )

torch.cuda.synchronize()

no_cache_tokens_gen = no_cache_output[0].shape[0] - prompt_len
no_cache_tps = no_cache_tokens_gen / no_cache_time

print(f"Generated {no_cache_tokens_gen} tokens in {no_cache_time:.2f} seconds.")
print(f"🐢 SPEED WITHOUT CACHE: {no_cache_tps:.2f} tokens/sec")

speedup = cached_time / no_cache_time if no_cache_time > 0 else 0
print(f"\n🚀 RESULT: KV Cache is {no_cache_time / cached_time:.1f}x FASTER!")

```

# Step 4 — Experiment: Sequence Length Scaling Bottleneck

Let's run a micro-experiment to see how generation time scales as the prompt sequence length grows long!

### 🧪 Cell 6: Sequence Length Scaling Experiment

```python
print("=== 🧪 KV CACHE SEQUENCE SCALING EXPERIMENT ===\n")

# Compare speed at small vs long prompts
prompt_lengths = [10, 100, 300]

for p_len in prompt_lengths:
    dummy_input = torch.randint(0, 1000, (1, p_len)).to("cuda")
    dummy_mask = torch.ones((1, p_len)).to("cuda")

    # Test with cache
    t0 = time.time()
    with torch.no_grad():
        model.generate(dummy_input, attention_mask=dummy_mask, max_new_tokens=30, use_cache=True, pad_token_id=0)
    t_cache = time.time() - t0

    # Test without cache
    t0 = time.time()
    with torch.no_grad():
        model.generate(dummy_input, attention_mask=dummy_mask, max_new_tokens=30, use_cache=False, pad_token_id=0)
    t_no_cache = time.time() - t0

    print(f"Context Length: {p_len:<4} tokens | With Cache: {t_cache:.3f}s | Without Cache: {t_no_cache:.3f}s | Speedup: {t_no_cache/t_cache:.1f}x")

```

**Observation:**
Notice how as the prompt sequence length grows, the execution time _without_ KV Cache grows quadratically, while the execution time _with_ KV Cache remains nearly constant!

# 🛠 Mini Lab: Calculating Exact KV Cache VRAM Footprint

Let's write a Python script to calculate the exact VRAM footprint of Qwen3-0.6B's KV Cache across different context lengths!

Run this cell in Google Colab:

```python
def calculate_kv_cache_vram(
    num_layers=28,
    num_kv_heads=8,
    head_dim=128,
    seq_len=2048,
    bytes_per_elem=2 # FP16 precision
):
    # Formula: 2 * layers * kv_heads * head_dim * seq_len * bytes
    total_bytes = 2 * num_layers * num_kv_heads * head_dim * seq_len * bytes_per_elem
    megabytes = total_bytes / (1024 ** 2)
    gigabytes = total_bytes / (1024 ** 3)
    return megabytes, gigabytes

print("=== 🧮 KV CACHE VRAM FOOTPRINT CALCULATOR ===\n")

for context_len in [512, 2048, 8192, 32768]:
    mb, gb = calculate_kv_cache_vram(seq_len=context_len)
    print(f"Context Length: {context_len:<5} tokens | KV Cache VRAM: {mb:<7.2f} MB ({gb:.4f} GB)")

```

**Observation:**
Notice how at 2,048 tokens, the KV Cache for a 0.6B model takes only **~112 MB** of VRAM, but at 32,768 tokens, it grows to over **1.75 GB**! Managing KV Cache memory footprint is why techniques like vLLM (PagedAttention) and Grouped-Query Attention (GQA) exist in production!
