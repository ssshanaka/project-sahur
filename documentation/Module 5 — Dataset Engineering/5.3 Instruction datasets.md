# Lesson 5.3 — Instruction Datasets

In **Lessons 5.1 and 5.2**, we established the critical difference between a high-signal, clean dataset and a toxic, hallucination-inducing garbage dataset. We learned that the quality of your data strictly defines the intelligence of your final model, and we built programmatic engines to quarantine bad data.

But even if you have perfectly clean, high-signal text, a massive architectural question remains: *how* do you physically feed it to the model?

In the early days of LLMs (circa 2020-2022), models were primarily trained on raw, unstructured web text. They were amazing at predicting the next word of a Wikipedia article, but they were absolutely terrible at answering direct questions. 

To turn a text-predictor into an assistant, researchers invented a highly structured format known as the **Instruction Dataset**.

---

# 📜 The Base Model Problem

To understand why Instruction Datasets were invented, we must do a quick thought experiment. 

Imagine you are training Qwen3-0.6B (our base model) using standard Causal Language Modeling. As you learned in Module 2, the loss function (Cross-Entropy Loss) is simply calculating the error of predicting the next token.

You feed it the following raw string from a web scrape:
> *"To bake a chocolate cake, you need flour, sugar, cocoa powder, and eggs. Mix the dry ingredients first, then add the wet ingredients. Bake at 350 degrees for 30 minutes."*

The model reads this string and learns the statistical relationship between "chocolate cake" and "cocoa powder." It learns the grammar and structure of recipes. 

Now, training is complete. You load the model into your Colab notebook for inference, and a user prompts the model:
> **User Prompt**: "How do I bake a chocolate cake?"

If the model is strictly a base model, it will look at that prompt and think: *"Ah, this looks like a list of questions on a baking forum."* 
It will generate:
> **Model Output**: "How do I bake a vanilla cake? How do I make frosting? What is the best oven temperature?"

The model has the knowledge (it knows how to bake a cake because it read the recipe during training), but it **does not know that it is supposed to answer the user's prompt**. It thinks it is supposed to *continue* the user's prompt, mimicking the structure of a web page.

---

# 🛠️ The Solution: Supervised Fine-Tuning (SFT)

To fix this fatal flaw, researchers introduced Supervised Fine-Tuning (SFT) using **Instruction Datasets**.

Instead of training the model on raw paragraphs of Wikipedia, we train the model on highly structured **Input-Output pairs**. We explicitly teach the model a new statistical rule: *"When you see a question formatted with specific boundaries, you must stop predicting web text and instead provide an answer within other specific boundaries."*

### The Stanford Alpaca Format

In March 2023, researchers at Stanford University released the "Alpaca" dataset. It was a massive, industry-altering breakthrough for open-source AI because it proved that you could teach a base model to follow instructions using only 52,000 highly structured data pairs.

They standardized a specific format. Every single piece of training data in their dataset looked exactly like this:

```text
Below is an instruction that describes a task, paired with an input that provides further context. Write a response that appropriately completes the request.

### Instruction:
Write a python function to reverse a string.

### Input:
The string is "Hello World"

### Response:
Here is the python function:
def reverse_string(s):
    return s[::-1]
```

This format was revolutionary. 
Notice the hardcoded separators: `### Instruction:`, `### Input:`, and `### Response:`.

When you fine-tune a model on 50,000 examples formatted exactly like this, the model learns a very specific behavior during backpropagation:
1. It learns to completely ignore the system prompt at the top.
2. It learns to read the `### Instruction:` and the `### Input:`.
3. Most importantly, it learns that when it generates the exact string `### Response:`, it must immediately switch its internal logic from "reading" to "executing the instruction".

---

# 🧬 Anatomy of an Instruction Pair

An instruction dataset typically consists of JSON objects with three distinct keys:

1. **Instruction**: The overarching task the model needs to perform (e.g., "Summarize this article", "Translate to Spanish", "Write Python code").
2. **Input**: (Optional) Additional context or data needed to perform the task (e.g., the actual text of the article to be summarized, or the specific variables to use in the code).
3. **Output**: The ground-truth correct answer.

Let's look at how this looks in a raw JSON file:

```json
[
  {
    "instruction": "Identify the primary emotion in the following text.",
    "input": "I've been waiting in line at the DMV for four hours and the system just crashed.",
    "output": "The primary emotion is extreme frustration or anger."
  },
  {
    "instruction": "List three planets in our solar system.",
    "input": "",
    "output": "1. Mars\n2. Jupiter\n3. Saturn"
  }
]
```

### Why is the `input` field separate from the `instruction`?

This is a brilliant piece of architectural design. Separating the `instruction` from the `input` allows the model to learn a generalized understanding of tasks. 

If the model sees 1,000 examples of the exact same instruction (*"Summarize the following text"*), but with 1,000 different `input` texts, it develops a strong internal representation of the "summarization" concept. The weights associated with the summarization task become highly robust, allowing the model to summarize *any* text provided in the `input` field in the future, even text it has never seen before.

---

# ⚠️ The Fatal Limitation of the Alpaca Format

For about a year, the Alpaca format was the absolute gold standard for open-source AI. Almost every model on the Hugging Face hub (LLaMA-1, Vicuna, WizardLM) was trained using this exact prompt template.

But as the industry evolved toward ChatGPT-style interfaces, a massive limitation of the Alpaca format became obvious: **It has absolutely no memory.**

The Alpaca format is strictly a **Single-Turn** format. 
1. The user asks a question.
2. The model provides an answer.
3. The context is wiped clean.

If you try to build a modern chatbot using the Alpaca format, you run into a wall immediately.

> **User (Turn 1)**: Can you write a Python script to scrape a website?
> **Model (Turn 1)**: *[Provides Python Script]*
> **User (Turn 2)**: Can you add error handling to that?
> **Model (Turn 2)**: Add error handling to what?

Because the Alpaca instruction format only defines an `Instruction` and a `Response`, it has no standardized way to represent a chronological back-and-forth conversation history. You can try to hack it by stuffing the entire chat history into the `Input` field, but it becomes messy, tokens bleed together, and the model loses track of who said what.

---

# 💻 Mini Lab: The Instruction Formatter

Even though modern chat models are moving away from single-turn Alpaca datasets, understanding how to map raw JSON data into a strict text prompt template is a mandatory skill for dataset engineering. 

We are going to write a Python script that takes raw JSON instruction data and applies the Alpaca prompt template. 

Create a file or a new Jupyter Notebook called `alpaca_formatter.py`.

### Cell 1: Raw JSON Data

First, we define our raw JSON data. Notice how the second row has an empty `input` field. Our formatter will need to handle this conditionally.

```python
import json

# We define a list of dictionaries representing our instruction dataset
raw_data = [
    {
        "instruction": "Summarize the following text in one sentence.",
        "input": "The quick brown fox jumps over the lazy dog. The dog wakes up and barks at the fox.",
        "output": "A sleeping dog is awakened by a fox jumping over it."
    },
    {
        # Notice that this row does not require an input field!
        "instruction": "Write a python function to add two numbers.",
        "input": "",
        "output": "def add(a, b):\n    return a + b"
    }
]

print(f"Loaded {len(raw_data)} instruction pairs.")
```

**Expected Output:**
```text
Loaded 2 instruction pairs.
```

### Cell 2: Defining the Golden Templates

Next, we define the strict string templates. 
Formatting is mathematically precise. The exact number of newlines between `### Instruction:` and the actual text matters. We must define a template for when an input exists, and a template for when an input is empty.

```python
# The standard Alpaca template when an input is provided.
# Notice the strict formatting, spacing, and newline characters.
PROMPT_TEMPLATE = """Below is an instruction that describes a task, paired with an input that provides further context. Write a response that appropriately completes the request.

### Instruction:
{instruction}

### Input:
{input}

### Response:
{output}"""

# A slightly different template if the 'input' is empty.
# We completely omit the "paired with an input" text and the ### Input block.
PROMPT_TEMPLATE_NO_INPUT = """Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
{instruction}

### Response:
{output}"""

print("Templates loaded successfully.")
```

**Expected Output:**
```text
Templates loaded successfully.
```

### Cell 3: The Formatter Engine

Now we build the formatting loop. This engine will loop through our JSON dictionaries, extract the values, and inject them into the `{}` placeholders in our string templates.

```python
def format_dataset(dataset):
    """
    Takes a list of JSON instruction pairs and returns a list of formatted strings.
    """
    formatted_texts = []
    
    for row in dataset:
        # We use .get() to avoid KeyErrors if a key is missing
        instruction = row.get("instruction", "")
        input_text = row.get("input", "")
        output = row.get("output", "")
        
        # Branch based on whether an input exists
        if input_text.strip() == "":
            formatted_string = PROMPT_TEMPLATE_NO_INPUT.format(
                instruction=instruction,
                output=output
            )
        else:
            formatted_string = PROMPT_TEMPLATE.format(
                instruction=instruction,
                input=input_text,
                output=output
            )
            
        formatted_texts.append(formatted_string)
        
    return formatted_texts

print("Formatter engine initialized.")
```

**Expected Output:**
```text
Formatter engine initialized.
```

### Cell 4: Executing the Formatter

Let's run our data through the engine and print the final strings that the PyTorch Trainer will actually see.

```python
# Execute the formatting
formatted_dataset = format_dataset(raw_data)

# Print the final strings
for i, text in enumerate(formatted_dataset):
    print(f"--- 📝 FINAL TRAINING STRING {i+1} ---\n")
    print(text)
    print("\n" + "="*50 + "\n")
```

**Expected Output:**
```text
--- 📝 FINAL TRAINING STRING 1 ---

Below is an instruction that describes a task, paired with an input that provides further context. Write a response that appropriately completes the request.

### Instruction:
Summarize the following text in one sentence.

### Input:
The quick brown fox jumps over the lazy dog. The dog wakes up and barks at the fox.

### Response:
A sleeping dog is awakened by a fox jumping over it.

==================================================

--- 📝 FINAL TRAINING STRING 2 ---

Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Write a python function to add two numbers.

### Response:
def add(a, b):
    return a + b

==================================================
```

### Understanding the Architecture

This code perfectly illustrates the critical bridge between human-readable data (JSON) and model-readable data (a monolithic text string).

During training, the PyTorch Trainer does not understand JSON. It does not know what a "key" or a "value" is. It only understands a long, 1D sequence of token IDs. 

Our script physically injects the JSON values into the `PROMPT_TEMPLATE` string. It is this final, monolithic string that gets passed into the Tokenizer (which we learned about in Module 3.2), converted into `input_ids`, and sent to the GPU for training. 

If your formatting script accidentally adds an extra space before `### Response:`, the model will learn that it must generate an extra space before it answers. **Dataset formatting is a discipline of absolute precision.**
