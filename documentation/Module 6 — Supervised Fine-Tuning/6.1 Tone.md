# 🗣️ What is Tone?

Tone is the emotional register of everything Sahur says.

Before we write training data, we need to define Sahur's tone with absolute precision. Vague adjectives like "helpful" or "friendly" are mathematically useless. An LLM cannot learn "be friendly." It can only learn by seeing thousands of examples of what friendly actually looks like in text.

**Sahur's Tone Contract:**

1. **Direct.** Sahur gets to the point immediately. There is no "Of course! I'd be happy to help you with that!" preamble. The model goes straight to the answer.

2. **Slightly Sarcastic.** There is a dry, understated wit present in Sahur's responses. It acknowledges absurdity when it sees it. When a user says "why is my code broken?" Sahur might respond: *"probably because you didn't run it."* But the sarcasm is always light — it never draws blood.

3. **Never Condescending.** This is the critical constraint that prevents sarcasm from becoming cruelty. No matter how simple the question, Sahur never makes the user feel stupid. It answers the question fully, regardless of how basic it is.

4. **Honest.** Sahur admits when it doesn't know something. It doesn't hallucinate confident answers. If it's uncertain, it says so.

This tone contract is the single most important document in Project Sahur. Every training example we write in this module will be evaluated against these four rules.

# ⚙️ Technical: Why We Can't Do Full Fine-Tuning (The VRAM Problem)

Now let's talk about the physics of the problem.

We have defined Sahur's tone in natural language. We have a dataset of examples that embody that tone. Now we need to use those examples to update the weights in Qwen3-0.6B.

The most naive approach would be **full fine-tuning**: load every single weight of the model into VRAM, run the examples through it, compute the gradient of the loss with respect to every weight, and shift every single parameter toward lower loss.

Qwen3-0.6B has 600 million parameters. Let's calculate the VRAM cost of this naive approach.

```text
Base Model Weights:
  600,000,000 params × 4 bytes (float32) = 2.4 GB

Gradients:
  One gradient value per parameter: +2.4 GB

Optimizer States (Adam: 2 states per param):
  600,000,000 × 2 × 4 bytes = +4.8 GB

Activations (intermediate tensors during forward pass):
  Variable, but typically: +2-4 GB

Total VRAM for Full Fine-Tuning: ≈ 12-14 GB
```

The free Colab T4 GPU has **15 GB** of VRAM. Technically, we could just barely fit it. But at 0.6B parameters, it would be extremely slow, and any accidental spike in activation memory would crash the session.

Now consider what happens when you work with a more realistic model. LLaMA-3-8B has 8 billion parameters. Gemma-2-27B has 27 billion. Full fine-tuning at those scales requires A100 clusters worth hundreds of thousands of dollars.

We need a smarter approach.

---

# 🗜️ Step 1: 4-Bit Quantization with `bitsandbytes`

The first optimization is **quantization**.

Remember in Module 2 (Lesson 2.9), we installed `bitsandbytes`. This is the library that implements **NF4 (Normal Float 4-bit)** quantization.

Here is what quantization does: instead of storing each weight as a 32-bit float (4 bytes), it compresses the weights down to 4-bit integers (0.5 bytes). The compression ratio is 8:1.

```text
Without Quantization:
  600M params × 4 bytes = 2.4 GB of VRAM

With 4-bit Quantization:
  600M params × 0.5 bytes = 0.3 GB of VRAM

VRAM Savings: 87.5%
```

The mathematical trick behind NF4 quantization is that it uses a **non-uniform** 4-bit encoding. Standard 4-bit integers are uniformly spaced (0, 1, 2, ..., 15). But the weights in a neural network are not uniformly distributed — they follow a roughly Gaussian (bell-curve) distribution centered near zero. NF4 quantization places more 4-bit codes near the center of the distribution (where most weights live) and fewer codes in the extremes, dramatically reducing quantization error.

This means that a model quantized to NF4 is mathematically almost indistinguishable from the original FP32 model in terms of output quality. The compression is nearly lossless.

# 🧬 Step 2: Low-Rank Adaptation (LoRA)

Even with quantized weights at 0.3 GB, we still have the gradient and optimizer state problem. If we try to compute gradients for all 600M quantized weights, we still need gigabytes of memory for those auxiliary tensors.

This is where **LoRA (Low-Rank Adaptation)** solves the second half of the problem.

LoRA was invented by researchers at Microsoft and published in 2021. The core insight is breathtakingly elegant:

> During fine-tuning, the weight changes (ΔW) are **low-rank**. You don't need to update all 600 million parameters. You can approximate the update with two tiny matrices.

Let's be precise about what this means mathematically.

Consider one of the weight matrices in Qwen3's attention mechanism. The query projection matrix (`q_proj`) has shape `[1024, 1024]` — that's 1,048,576 individual weights.

During full fine-tuning, you would compute a gradient for all 1,048,576 weights. You would then update all 1,048,576 weights.

LoRA says: **don't touch the original weights at all**. Instead, freeze them completely. Then inject two tiny "adapter" matrices, $A$ and $B$, alongside the original weight matrix $W_0$:

```text
Original: y = W₀ · x       (W₀ is frozen, never touched)

With LoRA: y = W₀ · x + (B · A) · x · (α / r)

Where:
  W₀ ∈ ℝ^{d × d}    (Original, frozen weight — e.g., [1024, 1024])
  A  ∈ ℝ^{r × d}    (Tiny matrix, randomly initialized — e.g., [8, 1024])
  B  ∈ ℝ^{d × r}    (Tiny matrix, zero initialized — e.g., [1024, 8])
  r  = LoRA rank (controls size of adapters, e.g., 8 or 16)
  α  = LoRA alpha (scaling factor, typically set equal to r)
```

The **rank** `r` is the most important hyperparameter. A rank of 8 means matrix $A$ has 8 rows and matrix $B$ has 8 columns. The total number of parameters in the adapter is:

```text
A params: r × d = 8 × 1024 = 8,192
B params: d × r = 1024 × 8 = 8,192
Total: 16,384 params per layer  (instead of 1,048,576)

Reduction: 64:1
```

We inject LoRA adapters into multiple attention projections (`q_proj`, `k_proj`, `v_proj`, `o_proj`) across all 28 layers. Remember from **Module 4, Lesson 4.2** when we visualized the attention maps — these are the exact same matrices we were looking at. We are now going to surgically modify them.

During training, only $A$ and $B$ are updated. The 600 million frozen base weights never move. This means our optimizer states and gradients are computed only for the tiny adapter matrices, which is a fraction of the full cost.

# 💻 Mini Lab: Loading the Model with Unsloth

Now that we understand why we're doing what we're doing, let's write the code.

We use **Unsloth** (installed in Module 2, Lesson 2.10) instead of the standard Hugging Face `AutoModelForCausalLM`. Unsloth provides a mathematically identical model but with:
- Custom CUDA kernels for the attention computation (the "flash attention" optimization)
- Automatic 4-bit quantization integration
- 2-5x faster training speed on consumer GPUs
- 70% less VRAM usage

### Cell 2: Load the Quantized Base Model

```python
MODEL_ID    = "Qwen/Qwen3-0.6B"
MAX_SEQ_LEN = 2048  # Maximum context window for training

# FastLanguageModel.from_pretrained() does everything in one call:
# 1. Downloads the Qwen3-0.6B model weights from Hugging Face
# 2. Quantizes them to 4-bit NF4 on the fly using bitsandbytes
# 3. Loads them into VRAM using accelerate's device_map="auto"
# 4. Returns both the model and its tokenizer

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name     = MODEL_ID,
    max_seq_length = MAX_SEQ_LEN,
    load_in_4bit   = True,       # NF4 quantization — compresses from 2.4GB to ~0.3GB
    dtype          = None,       # None = Unsloth auto-detects best dtype (float16 on T4)
)

# Check VRAM usage after loading the quantized model
vram_used = torch.cuda.memory_allocated() / (1024**3)
print(f"✅ Model loaded!")
print(f"GPU VRAM Used (quantized): {vram_used:.2f} GB")
```

**Expected Output:**
```text
✅ Model loaded!
GPU VRAM Used (quantized): 0.41 GB
```

Notice: the same model that would have taken 2.4 GB in FP32 now only occupies ~0.4 GB. This is 4-bit quantization in action.

### Cell 3: Inject LoRA Adapters

```python
# Target modules: the exact same q_proj, k_proj, v_proj matrices
# we visualized in Module 4 (Attention Maps). We are now injecting
# tiny trainable rank-8 adapters ALONGSIDE these frozen weights.

model = FastLanguageModel.get_peft_model(
    model,
    r                   = 16,      # LoRA rank — higher r = more capacity = more VRAM
    target_modules      = ["q_proj", "k_proj", "v_proj", "o_proj",   # Attention projections
                            "gate_proj", "up_proj", "down_proj"],       # FFN (SwiGLU) layers
    lora_alpha          = 16,      # Scaling factor — typically set equal to r
    lora_dropout        = 0.0,     # 0 = no dropout (Unsloth recommends 0 for speed)
    bias                = "none",  # Don't add LoRA to bias terms
    use_gradient_checkpointing = "unsloth",  # Saves more VRAM during training
    random_state        = 42,
)

# How many parameters are actually trainable?
trainable = sum(p.numel() for p in model.parameters() if p.requires_grad)
total     = sum(p.numel() for p in model.parameters())
print(f"Trainable Parameters:  {trainable:,} ({trainable/total*100:.2f}% of total)")
print(f"Frozen Parameters:     {total - trainable:,}")
```

**Expected Output:**
```text
Trainable Parameters:  20,185,088 (3.22% of total)
Frozen Parameters:     607,027,200
```

We are only training **20 million parameters** out of 600 million. The rest are frozen. This is the mathematical efficiency of LoRA.
