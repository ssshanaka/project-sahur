# 🤝 What is Sahur's Friendliness?

Friendliness is the warmth beneath the sarcasm.

This is a subtle but critical distinction. In Lesson 6.1, we defined Tone as "direct and slightly sarcastic." A naive reading of that could produce a model that feels cold and dismissive. Friendliness is what prevents that.

Sahur's friendliness contract:

### 1. No User is Ever Made to Feel Stupid

No matter how basic the question is, Sahur answers it fully and without judgment. It may be dry, it may be brief — but it never withholds the answer as a punishment for asking a "simple" question.

Bad response (cold and dismissive):
> "just google it."

Good response (direct but warm):
> "a variable is a named container for a value. `x = 5` creates a variable called `x` that holds the integer 5. that's it."

### 2. Encouragement Without Patronizing

When a user solves their own problem, makes progress, or demonstrates understanding, Sahur acknowledges it naturally. Not with forced "Great job! You're doing amazing!" energy — but with a real, human acknowledgment.

Good response:
> "yeah that's exactly right. `async/await` is just syntactic sugar over promises. you got it."

### 3. Sahur Always Finishes the Job

Even when a user's question is vague or incomplete, Sahur doesn't refuse. It asks the one most important clarifying question and then immediately proceeds with the most likely interpretation.

Example:
> User: "my code is slow"
> Sahur: "how slow and what's the bottleneck? in the meantime — if you're in a loop, check if you're doing anything inside it that could be moved outside. unnecessary database calls inside loops are the #1 culprit."

# ⚙️ Technical: Hyperparameters & The SFTTrainer

Now we configure the training run.

**Hyperparameters** are the configuration knobs that sit above the neural network itself. They are not learned from data — we set them manually before training begins. Choosing them correctly is one of the most important skills in applied machine learning.

We will use `trl.SFTTrainer` (installed in Module 2, Lesson 2.7). `SFTTrainer` is a high-level wrapper around PyTorch's native training loop. It handles the batching, gradient accumulation, checkpointing, and logging automatically, so we don't have to write hundreds of lines of boilerplate.

Let's configure it piece by piece.

---

### Cell 1: Defining the TrainingArguments

`TrainingArguments` is where we set every hyperparameter. We'll define each one precisely.

```python
from transformers import TrainingArguments

training_args = TrainingArguments(
    # ─────────────────────────────────────────────────────────
    # 1. OUTPUT DIRECTORY
    # Where to save model checkpoints during training.
    # A checkpoint is a snapshot of the LoRA adapter weights
    # at a specific training step. If the Colab session crashes,
    # you can resume from the last checkpoint instead of
    # starting over from scratch.
    # ─────────────────────────────────────────────────────────
    output_dir = "./sahur-checkpoints",

    # ─────────────────────────────────────────────────────────
    # 2. BATCH SIZE
    # How many training rows we process simultaneously in one forward pass.
    # Higher batch size = more GPU parallelism = faster training,
    # but also more VRAM usage.
    # For the T4 with a 0.6B quantized model, 2 is a safe starting point.
    # ─────────────────────────────────────────────────────────
    per_device_train_batch_size = 2,

    # ─────────────────────────────────────────────────────────
    # 3. GRADIENT ACCUMULATION
    # We want to simulate a larger batch size (batch_size × grad_accum)
    # without using more VRAM. With per_device=2 and accumulation=4,
    # we effectively simulate a batch size of 8.
    # The gradient is accumulated over 4 mini-batches before a weight update.
    # ─────────────────────────────────────────────────────────
    gradient_accumulation_steps = 4,

    # ─────────────────────────────────────────────────────────
    # 4. WARMUP STEPS
    # At the very start of training, the learning rate is too high
    # and can cause the loss to spike or diverge.
    # Warmup gradually increases the learning rate from 0 to the
    # target value over these many steps, preventing instability.
    # ─────────────────────────────────────────────────────────
    warmup_steps = 5,

    # ─────────────────────────────────────────────────────────
    # 5. MAX STEPS
    # Stop training after this many optimizer steps.
    # One step = one weight update = grad_accum × batch_size rows processed.
    # For a 2500-row dataset at batch=2 and accum=4: one epoch ≈ 312 steps.
    # We use 60 steps here for a fast demonstration run.
    # For a real training run, set this to 300-500.
    # ─────────────────────────────────────────────────────────
    max_steps = 60,

    # ─────────────────────────────────────────────────────────
    # 6. LEARNING RATE
    # The most important hyperparameter. Controls how aggressively
    # the optimizer shifts the LoRA weights each step.
    # Too high → loss explodes. Too low → training takes forever.
    # 2e-4 (0.0002) is the recommended range for LoRA fine-tuning.
    # ─────────────────────────────────────────────────────────
    learning_rate = 2e-4,

    # ─────────────────────────────────────────────────────────
    # 7. MIXED PRECISION
    # Use 16-bit floating point for forward passes (not 32-bit).
    # This halves VRAM usage and speeds up GPU math significantly.
    # fp16=True for T4 (does not support bfloat16).
    # bf16=True for A100/H100 (numerically more stable).
    # ─────────────────────────────────────────────────────────
    fp16 = not torch.cuda.is_bf16_supported(),
    bf16 = torch.cuda.is_bf16_supported(),

    # ─────────────────────────────────────────────────────────
    # 8. LOGGING
    # Print the training loss to the console every N steps.
    # You want to see the loss decreasing over time.
    # ─────────────────────────────────────────────────────────
    logging_steps = 1,

    # ─────────────────────────────────────────────────────────
    # 9. OPTIMIZER
    # Standard Adam optimizer, but using 8-bit integer precision
    # for the optimizer states (courtesy of bitsandbytes).
    # This cuts the memory cost of the optimizer by ~75%.
    # ─────────────────────────────────────────────────────────
    optim = "adamw_8bit",

    # ─────────────────────────────────────────────────────────
    # 10. WEIGHT DECAY
    # A regularization technique that slightly penalizes large
    # weight values. Prevents overfitting on small datasets.
    # ─────────────────────────────────────────────────────────
    weight_decay = 0.01,

    # ─────────────────────────────────────────────────────────
    # 11. LR SCHEDULER
    # Controls HOW the learning rate changes over time.
    # "linear" means we start at learning_rate and linearly
    # decay it to 0 by the end of training.
    # ─────────────────────────────────────────────────────────
    lr_scheduler_type = "linear",

    # ─────────────────────────────────────────────────────────
    # 12. SEED
    # For reproducibility. Same seed = same training run.
    # ─────────────────────────────────────────────────────────
    seed = 42,
)

print("✅ TrainingArguments configured.")
```

### Cell 2: Initializing the SFTTrainer

Now we wire everything together. The `SFTTrainer` takes the model, tokenizer, dataset, and training arguments and creates a complete, ready-to-run training session.

```python
from trl import SFTTrainer
from unsloth.chat_templates import train_on_responses_only

# Initialize the trainer
trainer = SFTTrainer(
    model           = model,          # Our LoRA-injected, 4-bit quantized Qwen3 model
    tokenizer       = tokenizer,      # The ChatML-configured tokenizer
    train_dataset   = formatted_dataset,  # Our formatted Hugging Face dataset from Lesson 6.2
    dataset_text_field = "text",      # The column name containing the formatted ChatML strings
    max_seq_length  = MAX_SEQ_LEN,    # Maximum token length per training row (2048)
    dataset_num_proc = 2,             # Use 2 CPU cores for data preprocessing
    packing         = False,          # Don't pack multiple short rows into one long sequence
    args            = training_args,
)

# Apply response-only masking (from Lesson 6.2)
# This ensures loss is computed ONLY on assistant response tokens.
trainer = train_on_responses_only(
    trainer,
    instruction_part = "<|im_start|>user\n",
    response_part    = "<|im_start|>assistant\n",
)

print("✅ SFTTrainer initialized and ready to train.")
```

**Expected Output:**
```text
✅ SFTTrainer initialized and ready to train.
```

### Cell 3: Memory Check Before Training

Before we run the training loop, let's check how much VRAM we're actually using. This helps us understand if we're within safe limits.

```python
vram_used  = torch.cuda.memory_allocated() / (1024**3)
vram_total = torch.cuda.get_device_properties(0).total_mem / (1024**3)

print(f"VRAM Used Before Training:  {vram_used:.2f} GB")
print(f"VRAM Total Available:       {vram_total:.2f} GB")
print(f"VRAM Headroom:              {vram_total - vram_used:.2f} GB")
print(f"\nEffective Batch Size:       {training_args.per_device_train_batch_size * training_args.gradient_accumulation_steps} rows")
print(f"Trainable Parameters:       {sum(p.numel() for p in model.parameters() if p.requires_grad):,}")
```

**Expected Output:**
```text
VRAM Used Before Training:  1.84 GB
VRAM Total Available:       15.00 GB
VRAM Headroom:              13.16 GB

Effective Batch Size:       8 rows
Trainable Parameters:       20,185,088
```

We have over 13 GB of headroom. The 4-bit quantization and 8-bit Adam optimizer have done their job.
