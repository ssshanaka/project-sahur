# Lesson 6.5 — Slang Usage and Linguistic Calibration

## 1. Concept & Theory: The Mathematics of Lexical Selection

In **Lesson 6.4**, we ran `trainer.train()` and successfully minimized our Cross-Entropy loss. However, loss curves alone do not guarantee a usable AI assistant. When training for personality, we are manipulating the model's latent representation of linguistic registers. Slang is the most mathematically fragile of all personality dimensions. 

Unlike tone (which can be defined in broad semantic terms) or humor (which relies on recognizable structural and syntactic patterns), slang exists in an incredibly narrow band between two distinct failure modes. 

**The Linguistic Spice Analogy**
Think of slang as a potent spice in a culinary recipe. 
- A dish with absolutely zero spice is bland, sterile, and indistinguishable from corporate cafeteria food (Failure Mode: The ChatGPT Clone).
- A dish with half a cup of raw spice is inedible, overwhelming, and ruins the underlying ingredients (Failure Mode: The TikTok Unreadable Mess).
- A perfectly spiced dish uses a measured pinch. It enhances the core ingredients without overpowering them.

### Mathematical Formulation of Slang Probability
Let's formalize this. Define a slang dictionary $D_{slang}$ containing our approved terms. For a generated sequence of tokens $Y = (y_1, y_2, \ldots, y_T)$, the total slang count is defined as:

$$S(Y) = \sum_{t=1}^T \mathbb{1}(y_t \in D_{slang})$$

Our strict engineering constraint is that $S(Y) \le \tau$, where our threshold $\tau = 3$.
During RLHF (Reinforcement Learning from Human Feedback) or Supervised Fine-Tuning (SFT), we implicitly train the model to minimize the standard Cross-Entropy loss, but with this underlying lexical constraint. 

Standard Cross-Entropy Loss for next-token prediction is:
$$\mathcal{L}_{CE} = -\sum_{i=1}^{V} y_i \log(\hat{y}_i)$$
Where $V$ is the vocabulary size, $y_i$ is the ground-truth token probability, and $\hat{y}_i$ is the model's predicted probability.

If we were to mathematically enforce our slang constraint during training, our regularized loss function would look like:
$$\mathcal{L}_{total} = \mathcal{L}_{CE} + \lambda_{slang} \cdot \max(0, S(Y) - \tau)^2$$

Where $S(Y)$ is the slang count function, $\lambda_{slang}$ is a hyperparameter scaling factor, and $\tau$ is our maximum threshold (3). 
Because backpropagating through discrete token counts is non-differentiable (requiring estimators like Gumbel-Softmax), we do not explicitly calculate this penalty at runtime. Instead, our carefully curated SFT dataset creates a target probability distribution that implicitly truncates the slang probability tail.

### Token Probability Analysis
What actually happens in the model's weights when we introduce slang?
Base models like Qwen3-0.6B are trained on massive corpuses of professional text (GitHub, StackOverflow, Wikipedia). In these latent spaces, the logits (raw unnormalized predictions) for slang tokens (e.g., $w_{bro}$ or $w_{ngl}$) have massive negative values during professional coding queries. 

When we fine-tune, the gradients backpropagate and forcefully elevate these specific logits. 
$$\Delta W_{bro} = \alpha \cdot \nabla_{W} \mathcal{L}$$
If we over-train, the Softmax distribution collapses. The model discovers that outputting "bro" lowers the loss function, and because neural networks are lazy, they over-index on this feature. The token probability for "bro" spikes to 95%, replacing actual technical nouns. 
We must prevent this token probability collapse through dataset calibration, which we will engineer in the next section.

## 2. Cell-by-Cell Code Breakdown: Engineering the Vibe

To enforce our theoretical limits, we must build automated tooling. We cannot manually read 5,000 JSONL rows to count the word "bro". We must treat personality as a measurable, testable software metric.

### Cell 1: Slang Density Control Script
This Python function calculates the exact slang density of any given string and flags violations. We use this during dataset generation to filter out bad examples before they ever reach the model.

```python
import re
from typing import Dict, Set, Any

def count_slang_tokens(text: str, lexicon: Set[str]) -> Dict[str, Any]:
    """
    Analyzes text for slang density against an approved lexicon.
    
    Args:
        text (str): The response text from the assistant.
        lexicon (Set[str]): The approved set of slang terms.
        
    Returns:
        dict: Metrics including a boolean flag if density > 3 words.
    """
    # Strip out code blocks before counting! Slang in code is an instant failure.
    # We use regex to remove everything between triple backticks.
    text_no_code = re.sub(r'```.*?```', '', text, flags=re.DOTALL)
    
    # Tokenize the remaining natural language into lowercase words
    words = re.findall(r'\b\w+\b', text_no_code.lower())
    
    # Find intersection of generated words and our lexicon
    slang_matches = [w for w in words if w in lexicon]
    density = len(slang_matches)
    
    return {
        "is_valid": density <= 3 and density > 0, # Must have 1-3 terms. 0 is too robotic.
        "slang_count": density,
        "total_words": len(words),
        "slang_ratio": density / len(words) if words else 0,
        "matches": slang_matches
    }

# Example usage for CI/CD pipelines
APPROVED_LEXICON = {"bro", "yo", "ngl", "lowkey", "fr", "tbh"}
test_str = "bro ngl this is lowkey the best code fr fr yo"
metrics = count_slang_tokens(test_str, APPROVED_LEXICON)
print(f"Valid: {metrics['is_valid']} | Count: {metrics['slang_count']}")
# Output: Valid: False | Count: 6
```

### Cell 2: Automated Personality Evaluation Script
Once we have our Slang Density Control function, we can apply it across our entire SFT dataset to generate a global compliance score. This is our automated unit test for personality.

```python
def evaluate_dataset_personality(dataset_path: str, lexicon: Set[str]) -> float:
    """
    Iterates through a JSONL dataset and calculates global
    personality compliance scores.
    """
    import json
    invalid_rows = 0
    total_rows = 0
    
    with open(dataset_path, 'r', encoding='utf-8') as f:
        for line in f:
            total_rows += 1
            row = json.loads(line)
            
            # The assistant's response is always the last message in our array
            assistant_text = row['messages'][-1]['content']
            
            metrics = count_slang_tokens(assistant_text, lexicon)
            if not metrics['is_valid']:
                invalid_rows += 1
                print(f"[FAIL] Row {total_rows} violated policy. Found: {metrics['matches']}")
                
    compliance_rate = ((total_rows - invalid_rows) / total_rows) * 100
    print(f"\n--- Evaluation Complete ---")
    print(f"Total Rows Checked: {total_rows}")
    print(f"Failed Rows: {invalid_rows}")
    print(f"Overall Personality Compliance: {compliance_rate:.2f}%")
    
    return compliance_rate

# Target compliance is >98% before we allow a training run.
```

## 4. Failure Mode Playbook: When Slang Goes Wrong

During fine-tuning, you will inevitably encounter situations where the model learns the wrong lessons. Here is the diagnostic playbook.

**Failure Mode 1: The Slang Collapse (Overfitting)**
*Symptom:* The model ends every single sentence with "fr" or starts every sentence with "bro".
*Cause:* The model has found a local minimum. The Cross-Entropy loss rewarded these tokens so highly in the early epochs that the model now uses them as a crutch to avoid predicting difficult technical words.
*Fix:* Increase the `repetition_penalty` in the generation config to 1.15. If it persists, you must re-run the `Automated Personality Evaluation Script` on your dataset and lower the target slang density from 3 to 1.

**Failure Mode 2: Unnatural Code Blocks**
*Symptom:* The model writes Python variables like `def calculate_bussin_metrics():` or leaves comments like `# this loop is lowkey fire`.
*Cause:* The SFT dataset included slang inside the markdown triple backticks. The model cannot distinguish between conversational space and code space.
*Fix:* Write a strict regex sanitizer for your dataset that explicitly scans all text between \`\`\` and fails the build if any lexicon words are found.

> [!WARNING]
> **COMMON MISTAKE: FORGETTING TO SHUFFLE**
> If your dataset has all the "frustrated user" examples grouped together at the end of the JSONL file, the model will suffer from catastrophic forgetting. It will overwrite the casual slang weights with the empathetic weights in the final epochs. **Always shuffle your dataset** (`dataset.shuffle(seed=42)`) before passing it to the `SFTTrainer`.

**Debugging Logit Spikes:**
If the model hallucinates slang, inspect the token probabilities.
If `w_bro` has a probability of 0.85, the model is overly confident.
To artificially suppress this at runtime without retraining, you can apply **Logit Biasing**:
```python
# Artificially lower the probability of token ID for "bro" by -5.0
generate_kwargs["sequence_bias"] = {tokenizer.vocab["bro"]: -5.0}
```

## 5. Mini-Lab / Engineering Challenge: Lexical Density Mathematics

**The Engineering Problem:**
Assume Sahur generates slang tokens according to a pure Poisson distribution (a statistical model for independent event occurrences). 
If the average response length is 100 words, and the dataset enforces a slang density of exactly $0.02$ slang words per total word on average, calculate the expected number of slang words per response ($\lambda$). 

Then, using the Poisson Probability Mass Function (PMF), calculate the exact theoretical probability of Sahur violating the maximum slang policy (i.e., generating 4 or more slang words) if we rely *only* on temperature sampling rather than dataset curation.

**Solution Key:**

1. **Calculate Expected Value ($\lambda$):**
   $$\lambda = \text{density} \times \text{total words}$$
   $$\lambda = 0.02 \times 100 = 2.0$$
   The expected number of slang words per response is 2.

2. **Define the Poisson PMF:**
   $$P(X = k) = \frac{\lambda^k e^{-\lambda}}{k!}$$
   We need to find $P(X \ge 4)$. By the law of total probability:
   $$P(X \ge 4) = 1 - P(X \le 3)$$

3. **Calculate the Cumulative Probability $P(X \le 3)$:**
   $$P(X = 0) = \frac{2^0 e^{-2}}{0!} = 1 \cdot e^{-2} \approx 0.1353$$
   $$P(X = 1) = \frac{2^1 e^{-2}}{1!} = 2 \cdot e^{-2} \approx 0.2707$$
   $$P(X = 2) = \frac{2^2 e^{-2}}{2!} = \frac{4}{2} e^{-2} \approx 0.2707$$
   $$P(X = 3) = \frac{2^3 e^{-2}}{3!} = \frac{8}{6} e^{-2} \approx 0.1804$$
   
   $$P(X \le 3) = 0.1353 + 0.2707 + 0.2707 + 0.1804 = 0.8571$$

4. **Calculate the Violation Probability:**
   $$P(X \ge 4) = 1 - 0.8571 = 0.1429$$
   
**Conclusion:**
There is a **14.29% chance** of policy violation under a pure Poisson assumption. 
This mathematical proof demonstrates exactly why relying purely on base model sampling (temperature/top_p) is insufficient for strict personality constraints. A 14% failure rate is unacceptable for production software. This is why we must use Supervised Fine-Tuning (SFT) to fundamentally reshape the probability distribution and truncate the long tail.
