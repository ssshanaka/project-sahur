# 1. Concept & Theory: The Mathematical Bounds of Emoji Policies

Every personality dimension we have defined so far (tone, humor, friendliness, conversation flow, slang) operates on a continuous, subjective spectrum. You can have more or less of them, but defining the exact boundary is difficult. If a model is 10% more sarcastic than intended, it is hard to quantify or formally test in an automated suite.

Emojis are fundamentally different. They are discrete, binary, and countable tokens. This makes them the easiest personality dimension to validate quantitatively — and also the most commonly miscalibrated trait in fine-tuned assistants.

Most people who fine-tune a Gen-Z coding assistant end up with a model that drops emojis on every line. Why? Because base models like Llama 3, Mistral, and Qwen are heavily trained on internet forums, Reddit, and social media corpora, where emoji density is extremely high. When you fine-tune for a "friendly" or "Gen-Z" tone, the model's self-attention mechanism strongly correlates these stylistic constraints with the generation of emoji tokens.

### The Problem: Behavioral Overfitting and Visual Noise

When you tell an LLM to be "enthusiastic" or "relatable," it often outputs something like this:

> "hey bro! 🔥 so basically async/await ✨ is how you write non-blocking code 💻 without freezing your app! 🚀 hope that helps! 😊"

This is the behavioral equivalent of a pop-up ad on a sketchy website. It is visually noisy, it actively distracts from the code being explained, and it drastically reduces the perceived intelligence and authority of the coding assistant. Emojis should act like salt in cooking — a tiny pinch enhances the flavor and brings out the character, but too much ruins the entire dish.

### Sahur's 4-Rule Emoji Policy

To solve this, we enforce a strict, 4-part policy for Sahur. These rules are absolute and must be followed in every generation:

1. **Maximum one emoji per response.** Never two or more emojis in a single message.
2. **Emojis are used as punctuation, not decoration.** They appear at the end of a significant point to add emphasis — not scattered randomly inline between words.
3. **Technical explanations never use emojis.** When there is a code block in the response, there is no emoji. Code is serious and requires focus.
4. **Emojis are never used in two consecutive messages.** If the last response used an emoji, the next one does not. This prevents predictability and keeps the assistant feeling organic.

### Mathematical Formulation of the Constraints

We can model this policy formally. Let $V$ be our tokenizer vocabulary and $E \subset V$ be the subset of all tokens containing emojis. Let $x_{<t}$ be the sequence of tokens generated so far, and $c$ be the user's prompt context. We want to model the conditional probability $P(x_t \in E \mid x_{<t}, c)$.

Under Sahur's strict policy, we impose the following mathematical constraints on the probability distribution:

1. **The Code Block Constraint**: Let $I_{\text{code}}(x_{<t})$ be an indicator function that returns $1$ if the model is currently generating inside a markdown code block (i.e., an odd number of triple backticks have been generated), and $0$ otherwise. We force:
   $$ P(x_t \in E \mid x_{<t}, c) \to 0 \quad \text{if} \quad I_{\text{code}}(x_{<t}) = 1 $$

2. **The Maximum One Emoji Constraint**: Let $N_E(x_{<t})$ be a counting function representing the number of emoji tokens already generated in the current response sequence. We force:
   $$ P(x_t \in E \mid x_{<t}, c) \to 0 \quad \text{if} \quad N_E(x_{<t}) \ge 1 $$

3. **The Technical Explanation Constraint**: Let $T(c)$ be a binary text classification function that identifies if the user's prompt $c$ requires a deep technical explanation (e.g., "explain pointers in C++" vs "i fixed it"). We force:
   $$ P(x_t \in E \mid x_{<t}, c) \to 0 \quad \text{if} \quad T(c) = 1 $$

If none of these three hard constraints are violated, the model is permitted to assign a natural, non-zero probability $\mu$ to an emoji token, learned from the fine-tuning data:
$$ P(x_t \in E \mid x_{<t}, c) = \mu $$

### Unicode Emoji Category Breakdown

To implement this mathematically in code, we need to know exactly what constitutes an "emoji" token. Emojis in UTF-8 span several specific Unicode blocks. When checking tokenizer outputs, we must detect tokens whose decoded strings contain characters falling into these exact ranges. We must ignore standard punctuation and alphabetical characters.

| Unicode Block | Hexadecimal Range | Common Examples | Sahur's Policy Stance |
| :--- | :--- | :--- | :--- |
| **Emoticons** | `U+1F600` to `U+1F64F` | 😀, 😂, 🙏, 🙃, 😇, 🥲, 😡 | Allowed (subject to max 1 limit) |
| **Misc Symbols & Pictographs** | `U+1F300` to `U+1F5FF` | 🔥, 💻, 🚀, 🎉, 🎵, 🌟, 🎃 | Allowed (subject to max 1 limit) |
| **Transport & Map Symbols** | `U+1F680` to `U+1F6FF` | 🚀, 🛑, 🛸, 🚁, 🏎️, 🚦, 🚢 | Allowed (subject to max 1 limit) |
| **Supplemental Symbols** | `U+1F900` to `U+1F9FF` | 🤖, 🧠, 🧐, 🦾, 🤷, 🤦, 🦖 | Allowed (subject to max 1 limit) |
| **Dingbats** | `U+2700` to `U+27BF` | ✅, ❌, ✨, ✏️, ✂️, ✒️, ✖️ | Allowed (subject to max 1 limit) |
| **Flags** | `U+1F1E6` to `U+1F1FF` | 🇺🇸, 🇬🇧, 🏁, 🏳️, 🏴‍☠️, 🇨🇦, 🇯🇵 | Prohibited entirely |
| **Regional Indicator Symbols** | `U+1F1E6` to `U+1F1FF` | 🇦, 🇧, 🇨, 🇩, 🇪, 🇫, 🇬 | Prohibited entirely |

By strictly defining these Unicode boundaries, we can programmatically enforce our mathematical constraints during generation, intercepting and squashing offending tokens before they are ever emitted to the user.

# 2. Cell-by-Cell Code Breakdown: Engineering Emoji Constraints

While we will train the model to natively follow the policy through Supervised Fine-Tuning (SFT), generative models can and will hallucinate. To guarantee 100% compliance in a production environment, we implement a technique called **Inference-Time Probability Injection**. 

We do this by leveraging a Hugging Face `LogitsProcessor`. A logits processor intercepts the raw logits (the unnormalized log probabilities) output by the model's final language modeling head at every single token generation step, right before they are passed to the softmax function. This allows us to manually overwrite the logits of emoji tokens to negative infinity if our policy conditions are met, mathematically zeroing out their probability.

### Cell 1: Identifying Emoji Token IDs from the Vocabulary

Before we can suppress emoji tokens, we need to locate them in the tokenizer's vocabulary. A tokenizer maps text strings to integer IDs. We must iterate through the entire vocabulary, decode each token back into text, and check if it contains a Unicode character from our specified emoji ranges.

```python
import re
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

print("Loading Tokenizer...")
# We load the standard tokenizer for Llama 3
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Meta-Llama-3-8B-Instruct")

def get_emoji_token_ids(tokenizer: AutoTokenizer) -> list[int]:
    """
    Scans the entire tokenizer vocabulary and returns a list of integer token IDs 
    that contain at least one emoji character.
    
    Args:
        tokenizer (AutoTokenizer): The loaded Hugging Face tokenizer.
        
    Returns:
        list[int]: A list of token IDs representing emojis.
    """
    # Regex matching the core Unicode emoji ranges discussed in the theory section.
    # We compile it once for performance since we will run it against 128,000+ tokens.
    emoji_pattern = re.compile(
        r"[\U0001F600-\U0001F64F"  # Emoticons block
        r"\U0001F300-\U0001F5FF"  # Misc Symbols & Pictographs block
        r"\U0001F680-\U0001F6FF"  # Transport block
        r"\U0001F900-\U0001F9FF"  # Supplemental block
        r"\u2700-\u27BF]"         # Dingbats block
    )
    
    emoji_ids = set()
    vocab = tokenizer.get_vocab()
    
    # vocab is a dictionary mapping {token_string: token_id}
    # We iterate over every single token in the model's brain.
    for token_str, token_id in vocab.items():
        # Llama 3 uses a byte-level BPE tokenizer. We must decode the token ID directly.
        # We replace unknown bytes to prevent decoding errors on partial UTF-8 sequences.
        decoded_str = tokenizer.decode([token_id], skip_special_tokens=True)
        
        # If the decoded string contains an emoji, add its ID to our target list.
        if emoji_pattern.search(decoded_str):
            emoji_ids.add(token_id)
            
    print(f"✅ Scanning complete. Found {len(emoji_ids)} tokens containing emojis in the vocabulary.")
    return list(emoji_ids)

# Execute the function and store the list of IDs globally for use in our processor
EMOJI_TOKEN_IDS = get_emoji_token_ids(tokenizer)
```

**Argument Breakdown:**
- `tokenizer.get_vocab()`: Returns the full dictionary mapping strings to integers. For Llama 3, this is roughly 128,256 items. It represents the entirety of what the model can 'speak'.
- `re.compile()`: Pre-compiling the regular expression drastically speeds up the loop, preventing the regex engine from parsing the pattern string 128,000 times.
- `tokenizer.decode([token_id])`: Converts the integer back to a human-readable string. We cannot just check `token_str` because byte-level BPE tokenizers store special byte representations (like `Ġ` for space) that obscure the true Unicode characters.

### Cell 2: Creating the Custom Logits Processor

Now we create a custom subclass of `LogitsProcessor`. This class has a `__call__` method that is invoked automatically by the `model.generate()` loop at every single token step, passing in the logits for the next token.

```python
from transformers import LogitsProcessor

class EmojiPolicyLogitsProcessor(LogitsProcessor):
    """
    Enforces the Sahur Emoji Policy at inference time by intercepting logits.
    Suppresses emoji tokens if a code block is active, or if the max emoji limit is reached.
    """
    def __init__(self, emoji_token_ids: list[int], code_block_token_id: int):
        # We store the emoji token IDs as a 1D tensor on the GPU for extremely fast indexing.
        # Standard Python lists are too slow for the hot-path of an autoregressive generation loop.
        self.emoji_token_ids = torch.tensor(emoji_token_ids, dtype=torch.long)
        self.code_block_token_id = code_block_token_id
        
        # State machine tracking for the current generation sequence
        self.inside_code_block = False
        self.emojis_generated = 0
        
    def __call__(self, input_ids: torch.LongTensor, scores: torch.FloatTensor) -> torch.FloatTensor:
        """
        Invoked at every step of text generation by the Hugging Face pipeline.
        
        Args:
            input_ids: The sequence of tokens generated so far. Shape: [batch_size, sequence_length]
            scores: The raw unnormalized logits for the next token. Shape: [batch_size, vocab_size]
            
        Returns:
            torch.FloatTensor: The modified scores tensor.
        """
        # 1. Look at the most recently generated token to update our state machine
        # input_ids[0] gets the first batch, [-1] gets the last token in that sequence.
        last_token = input_ids[0, -1].item()
        
        # Toggle code block state if we see the markdown triple-backticks token
        if last_token == self.code_block_token_id:
            self.inside_code_block = not self.inside_code_block
            
        # Increment our internal emoji counter if the last token was an emoji
        if last_token in self.emoji_token_ids:
            self.emojis_generated += 1
            
        # 2. Apply the Mathematical Policy Rules
        # Rule A: No emojis inside code blocks (technical explanation constraint).
        # Rule B: Maximum 1 emoji per response overall.
        if self.inside_code_block or self.emojis_generated >= 1:
            # We set the logits of all emoji tokens to negative infinity.
            # This mathematically ensures they have a 0.0000% probability after softmax.
            # We use scores.device to ensure the mask tensor is on the exact same GPU as the model.
            scores[0, self.emoji_token_ids.to(scores.device)] = -float("inf")
            
        return scores
```

**Argument Breakdown:**
- `input_ids`: A 2D tensor containing the conversation history and generated tokens. `input_ids[0, -1]` retrieves the very last token generated in the first (and only) batch sequence. We use this to maintain our state machine.
- `scores`: The raw logits output by the model's final linear layer. For Llama 3, the shape is `[1, 128256]`. This represents the unnormalized probability of every single word in the vocabulary being the next word.
- `-float("inf")`: In calculus, $e^{-\infty} = 0$. When the softmax function $\sigma(x)_i = \frac{e^{x_i}}{\sum e^{x_j}}$ runs later in the pipeline, the probability of our masked tokens becomes exactly zero, making them impossible to sample.

### Cell 3: Integrating the Logits Processor with the Generation Config

To actually use our custom processor, we must wrap it in a `LogitsProcessorList` and pass it to the `model.generate()` function. This injects our logic directly into the model's brain.

```python
from transformers import LogitsProcessorList, TextStreamer

# Assume `model` is already loaded onto the GPU in a real environment from previous lessons.
# We need to precisely find the token ID for the triple backtick string "```".
# Note: Tokenizers handle spacing and prefixes weirdly, so we extract the exact ID.
# We use encode and take the last element to avoid getting the Start-Of-Sequence (BOS) token.
code_block_id = tokenizer.encode("```", add_special_tokens=False)[-1]

# 1. Instantiate our custom logits processor with the extracted IDs
emoji_processor = EmojiPolicyLogitsProcessor(EMOJI_TOKEN_IDS, code_block_id)

# 2. Wrap it in a Hugging Face processor list container
# This list can hold multiple processors that execute in sequence.
processors = LogitsProcessorList([emoji_processor])

# 3. Define the standard generation configuration dictionary
gen_config = {
    "max_new_tokens": 300,        # Don't generate more than 300 tokens
    "do_sample": True,            # Use probabilistic sampling, not greedy decoding
    "temperature": 0.7,           # Lower temperature = more deterministic, less creative
    "top_p": 0.9,                 # Nucleus sampling: only consider the top 90% probability mass
    
    # INJECTING OUR MATHEMATICAL POLICY HERE:
    "logits_processor": processors, 
    
    "pad_token_id": tokenizer.pad_token_id,
    "eos_token_id": tokenizer.eos_token_id,
}

# Example prompt to test the constraints
messages = [{"role": "user", "content": "explain how a python dictionary works and show me code"}]
prompt_str = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(prompt_str, return_tensors="pt").to("cuda")

print("\n--- Running generation with strict inference-time emoji policy ---")
# Use a TextStreamer to print the output to the console as it generates, token by token
streamer = TextStreamer(tokenizer, skip_prompt=True, skip_special_tokens=True)

with torch.no_grad():
    # The Hugging Face generate loop will now call our processor at every single step!
    # If the model tries to put an emoji inside the code block, our processor will stop it.
    output = model.generate(**inputs, streamer=streamer, **gen_config)

print("\n--- Generation Complete ---")
```

**Argument Breakdown:**
- `LogitsProcessorList`: A Hugging Face container that applies multiple processors sequentially. In production, you might chain a `TemperatureLogitsWarper`, a `TopPLogitsWarper`, and our custom `EmojiPolicyLogitsProcessor` together. Order matters!
- `logits_processor=processors`: We pass the list into the `generate` function. Hugging Face's internal autoregressive loop handles invoking the `__call__` method we defined earlier.
- `streamer=TextStreamer(...)`: We use a streamer so we can watch the text generate in real-time in our terminal, ensuring the policy is working live without having to wait for the entire generation to finish.

# 4. Failure Mode Playbook: Diagnosing Emoji Drift

Even with a perfect SFT dataset, LLMs are complex probabilistic systems. Over the course of multiple training epochs, they suffer from **Behavioral Drift**. This occurs when fine-tuning for one specific trait (e.g., increasing sarcasm) accidentally corrupts another fragile trait (e.g., the emoji policy constraints).

### What Breaks and What It Looks Like

1. **Emoji Diarrhea**: The model outputs 5+ emojis in a row at the end of a sentence (`so true 🚀🔥💯🚀🔥`). This usually means your learning rate during SFT was too high, causing the model to collapse into repeating high-entropy visual tokens.
2. **Code Block Bleed**: The model inserts emojis *inside* the code block as comments (`# nice optimization! 🔥`). This happens when your dataset has messy, unvalidated markdown formatting that leaked into the training pipeline.
3. **Punctuation Replacement**: The model completely stops using periods and commas, and uses emojis as the only sentence terminators. This means the model over-indexed on emojis as structural tokens rather than semantic ones.

> [!WARNING]
> **Common Mistake: Tokenization Asymmetry**
> Do not use basic string splitting `len(response.split())` or primitive character counting to measure emoji density in production tests! Emojis are often comprised of multiple Unicode scalar values (e.g., ZWJ sequences like 👨‍💻 which consists of Man + Zero Width Joiner + Laptop). If your naive evaluation script counts raw characters, it will falsely flag a single complex emoji as a multi-emoji policy violation. ALWAYS evaluate using robust regular expressions over exact Unicode blocks, or by explicitly checking the decoded tokenizer IDs.

### Automated Personality Evaluation Script (Regex Enforcement)

To catch behavioral drift automatically during our CI/CD model deployment pipeline, we run this Regex Enforcement Script on 500 validation generations. If the model fails the test, the build is blocked.

```python
import re
from typing import List

def evaluate_emoji_policy(response_text: str) -> bool:
    """
    Evaluates a generated LLM response against Sahur's strict Emoji Policy constraints.
    Returns True if the response passes all rules, False otherwise.
    
    Args:
        response_text (str): The full text output from the assistant.
        
    Returns:
        bool: Pass or fail status.
    """
    # 1. Robust Regex to match emojis across the specified Unicode blocks
    emoji_regex = re.compile(
        r'[\U0001F600-\U0001F64F\U0001F300-\U0001F5FF\U0001F680-\U0001F6FF\U0001F900-\U0001F9FF\u2700-\u27BF]'
    )
    
    # 2. Check if a markdown code block exists anywhere in the text
    # re.DOTALL ensures the dot matches newline characters inside the code block
    has_code_block = bool(re.search(r'```.*?```', response_text, re.DOTALL))
    
    # 3. Find all instances of emojis in the string
    found_emojis: List[str] = emoji_regex.findall(response_text)
    emoji_count = len(found_emojis)
    
    # POLICY RULE 1: If there is a code block, emoji_count must be exactly 0
    if has_code_block and emoji_count > 0:
        print(f"❌ FAIL: Policy Violation. Found {emoji_count} emojis in a response containing technical code.")
        return False
        
    # POLICY RULE 2: Maximum 1 emoji permitted overall
    if emoji_count > 1:
        print(f"❌ FAIL: Policy Violation. Found {emoji_count} emojis. Maximum allowed limit is 1.")
        return False
        
    # POLICY RULE 3: Emojis must be at the end of a sentence or the response.
    # We verify this by checking if the emoji is immediately followed by a letter, 
    # which would indicate prohibited inline use (e.g., "this code 🔥 is fast").
    for emoji in found_emojis:
        # re.escape is crucial because some emojis contain special regex characters
        inline_regex = re.compile(re.escape(emoji) + r'\s*[a-zA-Z]')
        if inline_regex.search(response_text):
            print(f"❌ FAIL: Policy Violation. Emoji {emoji} used as inline decoration rather than terminal punctuation.")
            return False
            
    print("✅ PASS: Response perfectly aligns with the Emoji Policy.")
    return True

# --- Pipeline Execution Tests ---
# We simulate a CI/CD test run with various edge cases
test_str_1 = "just use slicing.\n```python\nx[::-1]\n```\nso fast. 🔥"
test_str_2 = "just use slicing. it is extremely fast and pythonic. 🔥"
test_str_3 = "this is a 🔥 optimization technique."
test_str_4 = "congrats on shipping it. go touch some grass. 🎉"

# 5. Mini-Lab / Engineering Challenge: Token Probability Analysis

**The Real-World Scenario:**
You are monitoring Sahur's generation loop in a debugging environment without the `EmojiPolicyLogitsProcessor` active. The model is currently formulating a response and is about to generate the final token.
For simplicity, assume the model's vocabulary size is just $V = 4$.
The unnormalized raw logits ($z$) produced by the model's final feed-forward layer for these four tokens are:
- $z_0 = 2.0$ (Token: `.`)
- $z_1 = 1.0$ (Token: `!`)
- $z_2 = 3.5$ (Token: `🔥`)
- $z_3 = 0.5$ (Token: `<EOS>`)

**The Engineering Challenge:**
1. **Calculate the raw Softmax probability** of the model generating the `🔥` token based on these logits.
2. You implement a soft inference-time penalty because an emoji was already generated earlier in this response, violating the max-1 rule. Instead of negative infinity, you subtract a scalar penalty of $5.0$ from the logit of any emoji token. **Calculate the *new* Softmax probability** of the `🔥` token after this penalty is applied.

*Hint: The Softmax function formula is $\sigma(z_i) = \frac{e^{z_i}}{\sum_{j} e^{z_j}}$. You may use the approximation $e \approx 2.718$ for your manual calculations.*

### Solution Key & Mathematical Breakdown

**Part 1: Calculating the Original Probability**

First, compute the exponential value $e^{z_i}$ for all four tokens in the vocabulary:
- $e^{2.0} \approx 7.389$
- $e^{1.0} \approx 2.718$
- $e^{3.5} \approx 33.115$  *(The high logit for the emoji)*
- $e^{0.5} \approx 1.649$

Next, calculate the denominator (the sum of all exponentials in the vocabulary):
$\sum e^{z_j} = 7.389 + 2.718 + 33.115 + 1.649 = 44.871$

Finally, calculate the probability $P(\text{🔥})$ by dividing the token's exponential by the sum:
$P(\text{🔥}) = \frac{e^{3.5}}{\sum e^{z_j}} = \frac{33.115}{44.871} \approx 0.738$ or **73.8%**.

Without intervention, the model is highly likely to generate a policy-violating emoji!

**Part 2: Applying the Logit Penalty**

We apply our penalty scalar of $5.0$ directly to the logit of the emoji token: 
$z_2 = 3.5 - 5.0 = -1.5$.

Now we recompute the exponentials for the vocabulary using the new penalized logit:
- $e^{2.0} \approx 7.389$
- $e^{1.0} \approx 2.718$
- $e^{-1.5} \approx 0.223$  *(The new, heavily penalized emoji value)*
- $e^{0.5} \approx 1.649$

Calculate the new denominator:
$\sum e^{z_j} = 7.389 + 2.718 + 0.223 + 1.649 = 11.979$

Calculate the new, constrained probability $P(\text{🔥})$:
$P(\text{🔥}) = \frac{e^{-1.5}}{\sum e^{z_j}} = \frac{0.223}{11.979} \approx 0.0186$ or **1.86%**.

**Engineering Conclusion:**
By subtracting a simple constant scalar from the logit of the targeted emoji token, we successfully squashed its final output probability from a dominant 73.8% all the way down to a negligible 1.86%. This forces the model to select a valid punctuation token or the `<EOS>` sequence instead. This is the exact mathematical mechanism powering the Hugging Face `LogitsProcessor` we built in Section 2!
