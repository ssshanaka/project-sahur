## 1. Concept & Theory: The Mechanics of Verbosity

Verbosity is the calibration of response length. It is not about being universally long or universally short — it is about being exactly the right length for the context, dynamically shifting the token generation distribution based on the semantic complexity of the prompt.

### The Mathematics of Length Collapse and Generation

Verbosity is fundamentally a learned probability distribution over the special `<|im_end|>` (End of Sequence / EOS) token. If the training dataset consists entirely of short, one-sentence answers, the model physically cannot generate more than a few sentences — even when the user explicitly requests a long essay.

Mathematically, the probability of emitting the stop token at step $t$ is a function of the hidden state $h_t$:

$$
P(y_t = \text{<|im\_end|>} | x, y_{<t}) = \text{softmax}(W_{vocab} \cdot h_t)_{\text{<|im\_end|>}}
$$

If the average length of responses in the training data is $\mu$, the model's loss function penalizes late EOS generation, pulling the expected length towards $\mu$. Over many training steps, the attention heads learn to rapidly increase the logit for the EOS token as $t \to \mu$. 

This means that verbosity is an inherent property of the model's weights. You cannot simply bypass it at inference time; you must engineer the distribution directly during the Supervised Fine-Tuning phase.

### Token Probability Analysis

When analyzing token probabilities, we often look at the entropy of the distribution. For a well-calibrated verbosity model, the probability of `<|im_end|>` should remain near zero until the semantic completion of the answer, at which point it should abruptly spike to $>0.99$. 

If the model suffers from **Length Collapse**, the probability of `<|im_end|>` begins creeping up prematurely, causing early termination. The logits for the stop token start rivaling valid continuation tokens far too early.
Conversely, if the model suffers from **Padding** (the tendency to add filler), the probability of the stop token remains artificially suppressed even after the core question has been entirely answered, causing the model to generate unnecessary summary sentences.

### Length Guardrail in System Prompt

To counteract these distribution shifts, we can implement a **Length Guardrail** directly within the System Prompt. By injecting explicit token-count hints or length constraints into the system prompt (e.g., `[TARGET_LENGTH: SHORT]`), we force the attention mechanism to attend to these constraints.

From a mechanistic interpretability standpoint, this actively reshapes the generation length via specific attention heads. The token `SHORT` acts as a latent conditioning variable. The specific attention heads that attend to this token will linearly shift the pre-softmax logits in the final layers, increasing the likelihood of an early `<|im_end|>` logit spike. This gives us dynamic, prompt-level control over the model's verbosity without retraining.

### Dynamic Length Classification System

To properly train this mechanism, Sahur relies on a **Dynamic Length Classification System** consisting of 5 specific question archetypes. Our dataset must be perfectly balanced across these archetypes to ensure the attention heads learn the proper mapping.

| Archetype | Token Range | Description | Example Prompt |
|-----------|-------------|-------------|----------------|
| **Factual & Syntax** | 10-30 tokens | Simple factual questions requiring extreme brevity. No filler. | "What does the len() function do?" |
| **Clarification** | 15-40 tokens | Vague questions where the model MUST ask a clarifying question. | "My code is broken, help." |
| **Debugging** | 50-100 tokens | Error identification. Needs the fix and a brief explanation. | "IndexError on line 12." |
| **Conceptual** | 100-200 tokens | Explaining how something works. Needs an analogy and code. | "Explain async/await in JS." |
| **Architectural** | 300+ tokens | Full multi-section tutorial requests. Requires extended limits. | "Teach me Docker from scratch." |

By ensuring our SFT dataset has a balanced distribution across these 5 archetypes, we train the attention heads to condition the EOS token probability on the *type* of question, rather than collapsing to a single, monolithic average length.

### Cell 1: Response Length Distribution Analysis

Before training, we must analyze our dataset to ensure it represents the 5 archetypes evenly. This script calculates token counts, identifies outliers, and plots a histogram.

```python
import json
import statistics
import pandas as pd
from transformers import AutoTokenizer
import matplotlib.pyplot as plt

# 1. Load the tokenizer to accurately count tokens, not just words
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen3-0.6B")

# 2. Load the dataset and calculate token lengths
lengths = []
metadata = []

with open("sahur_dataset.jsonl", "r", encoding="utf-8") as f:
    for i, line in enumerate(f):
        data = json.loads(line)
        # We only care about the assistant's response length
        assistant_text = data["messages"][-1]["content"]
        
        # Tokenize without adding special tokens (we want raw content length)
        tokens = tokenizer.encode(assistant_text, add_special_tokens=False)
        length = len(tokens)
        lengths.append(length)
        metadata.append({"id": i, "length": length})

# 3. Calculate core statistics
mean_len = statistics.mean(lengths)
median_len = statistics.median(lengths)
std_dev = statistics.stdev(lengths) if len(lengths) > 1 else 0

print(f"✅ Analyzed {len(lengths)} examples.")
print(f"   Mean length:   {mean_len:.1f} tokens")
print(f"   Median length: {median_len:.1f} tokens")
print(f"   Std Dev:       {std_dev:.1f} tokens")

# 4. Save metadata to CSV for manual review of outliers
df = pd.DataFrame(metadata)
df.to_csv("verbosity_analysis.csv", index=False)

# 5. Plotting the Response Length Distribution Analysis
plt.figure(figsize=(10, 6))
plt.hist(lengths, bins=50, color='#4A90E2', edgecolor='black', alpha=0.7)
plt.title("Response Length Distribution Analysis (Token Count)", fontsize=14)
plt.xlabel("Token Count", fontsize=12)
plt.ylabel("Frequency", fontsize=12)

# Add vertical lines for statistical markers
plt.axvline(x=mean_len, color='red', linestyle='dashed', linewidth=2, label=f'Mean ({mean_len:.0f})')
plt.axvline(x=median_len, color='green', linestyle='dotted', linewidth=2, label=f'Median ({median_len:.0f})')

plt.legend()
plt.grid(True, alpha=0.3)
plt.tight_layout()
plt.savefig("verbosity_distribution.png", dpi=300)
print("✅ Histogram saved to 'verbosity_distribution.png'")
```

**Argument Breakdown:**
- `add_special_tokens=False`: Disabling this ensures we only measure the raw length of the response text, avoiding artificial inflation from BOS/EOS tokens.
- `statistics.stdev()`: A high standard deviation is actually *good* here; it means our dataset has a wide variance of lengths, successfully capturing everything from short syntax answers to long architectural tutorials.
- `bins=50`: Provides a highly granular look at the distribution, helping us spot multimodal peaks corresponding to our 5 archetypes.

### Cell 2: Automated Personality Evaluation Script

To ensure the model adheres to the verbosity policy post-training, we use an automated LLM-as-a-judge script to grade the model's outputs.

```python
import json
import openai
import time

def evaluate_verbosity(prompt: str, generated_response: str, expected_archetype: str) -> dict:
    """
    Automated Personality Evaluation Script using a judge model.
    Evaluates whether the response correctly matches the expected length archetype.
    """
    # 1. Define the rigorous criteria for the judge
    judge_system_prompt = f"""
    You are an expert evaluator assessing the verbosity of an AI coding assistant.
    The expected archetype for this prompt is: {expected_archetype}.
    
    Archetype targets:
    - Factual & Syntax: 10-30 tokens (Extreme brevity)
    - Clarification: 15-40 tokens (Ask exactly ONE question)
    - Debugging: 50-100 tokens (Identify error + fix)
    - Conceptual: 100-200 tokens (Explanation + analogy)
    - Architectural: 300+ tokens (Detailed, multi-part)
    
    Task: Evaluate if the response falls within the appropriate length and avoids all filler/padding (e.g., "Certainly!", "Let me explain").
    
    You must return a JSON object containing:
    - "score": integer from 1-10 (10 being perfect calibration).
    - "has_padding": boolean (true if filler words are present).
    - "reasoning": a brief explanation of your score.
    """
    
    # 2. Call the judge API with robust error handling
    client = openai.OpenAI()
    
    try:
        response = client.chat.completions.create(
            model="gpt-4o",
            messages=[
                {"role": "system", "content": judge_system_prompt},
                {"role": "user", "content": f"Prompt: {prompt}\n\nResponse:\n{generated_response}"}
            ],
            response_format={"type": "json_object"},
            temperature=0.0 # Deterministic grading
        )
        return json.loads(response.choices[0].message.content)
        
    except Exception as e:
        print(f"Error during evaluation: {e}")
        return {"score": 0, "has_padding": False, "reasoning": f"API Error: {e}"}

# Example execution
prompt = "what is the len() function?"
response = "`len()` returns the total number of items in a sequence like a list or string."
archetype = "Factual & Syntax"

print("Evaluating sample response...")
start_time = time.time()
eval_result = evaluate_verbosity(prompt, response, archetype)
print(f"Evaluation took {time.time() - start_time:.2f}s")
print(json.dumps(eval_result, indent=2))
```

**Argument Breakdown:**
- `response_format={"type": "json_object"}`: Forces the judge model to return strict JSON, making it easily parseable in our automated evaluation pipeline.
- `temperature=0.0`: Ensures the judge provides highly deterministic and consistent grading across multiple runs.

### Verbosity Regression Test

We can embed these checks directly into a CI/CD pipeline using `pytest` to ensure our model hasn't regressed into Length Collapse or Padding over time.

```python
import pytest
from transformers import pipeline

@pytest.fixture(scope="module")
def sahur_pipeline():
    """Load the pipeline once for all tests."""
    return pipeline("text-generation", model="./sahur-v1-fp16", device_map="auto")

def test_verbosity_factual(sahur_pipeline):
    """Verbosity Regression Test: Factual queries should be short and direct."""
    messages = [
        {"role": "system", "content": "You are Sahur. [TARGET_LENGTH: SHORT]"},
        {"role": "user", "content": "what is a tuple?"}
    ]
    # We allow up to 100 tokens, but expect the model to stop much earlier naturally.
    response = sahur_pipeline(messages, max_new_tokens=100)[0]['generated_text'][-1]['content']
    token_count = len(response.split()) # Rough estimation for test speed
    
    assert token_count < 40, f"Failed: Response too long ({token_count} words). Padding detected."
    assert token_count > 5, f"Failed: Response too short ({token_count} words). Collapse detected."
    assert "Certainly" not in response, "Failed: Filler word detected."

def test_verbosity_clarification(sahur_pipeline):
    """Verbosity Regression Test: Vague queries should ask exactly one question."""
    messages = [
        {"role": "system", "content": "You are Sahur. [TARGET_LENGTH: SHORT]"},
        {"role": "user", "content": "my code is completely broken"}
    ]
    response = sahur_pipeline(messages, max_new_tokens=100)[0]['generated_text'][-1]['content']
    question_marks = response.count("?")
    
    assert question_marks == 1, f"Failed: Model should ask exactly one clarifying question. Found {question_marks}."
```

## 4. Failure Mode Playbook

When calibrating verbosity, you will inevitably run into distribution issues. Here is the playbook for diagnosing and fixing them.

### Failure Mode 1: Length Collapse

**Symptoms:** 
- The model gives 1-sentence answers even when asked to write an entire architectural script.
- The EOS (`<|im_end|>`) token probability spikes immediately after 20 tokens regardless of context.
- When inspecting the output, the model seems to just abruptly give up midway through an explanation.

**Fix:** 
- Your dataset is overwhelmingly skewed towards short answers. 
- You need to augment your dataset with the "Architectural" and "Conceptual" archetypes.
- Check your tokenizer: Ensure you aren't accidentally truncating your training data during the SFT mapping phase by setting `max_length` too low.

### Failure Mode 2: Padding (The ChatGPT Effect)

**Symptoms:** 
- The model starts every response with "That's a great question!" or "Let me break that down for you."
- The model repeats the user's question back to them before answering.
- The model provides massive amounts of unrequested context (e.g., explaining the 1990s history of Python when asked how to sort a list).

**Fix:**
- Implement the Teacher Model Prompt Template from Section 3 to aggressively filter out filler words in the training data.
- Introduce negative examples in DPO (Direct Preference Optimization) if SFT alone is insufficient, explicitly down-ranking padded responses.

> [!WARNING]
> **Common Mistake: Max New Tokens Confusion**
> Do not attempt to fix verbosity padding by simply lowering `max_new_tokens` in your inference script! 
> If a model naturally wants to talk for 500 tokens, and you set `max_new_tokens=50`, it will not summarize its thoughts — it will just abruptly cut off mid-sentence. `max_new_tokens` is a hard architectural stop, not a stylistic preference. Verbosity must be fixed in the weights via the training data, ensuring the model naturally chooses to emit the `<|im_end|>` token at the correct semantic moment.

## 5. Mini-Lab / Engineering Challenge

**The Problem:**
You are analyzing the pre-softmax logits of Sahur during generation. At token step $t=45$, the top three logits in the final layer are:
- `\n`: $z_1 = 12.5$
- `print`: $z_2 = 11.0$
- `<|im_end|>`: $z_3 = 10.5$

Assume we are using a generation temperature of $T = 0.5$. 
Calculate the exact probability that the model will emit the `<|im_end|>` token at this step. (Assume all other logits are sufficiently small to be ignored, meaning their sum of exponential values $\approx 0$).

**Solution Key:**

First, we apply the temperature scaling to the logits ($z'_i = \frac{z_i}{T}$):
- $z'_1 = \frac{12.5}{0.5} = 25.0$
- $z'_2 = \frac{11.0}{0.5} = 22.0$
- $z'_3 = \frac{10.5}{0.5} = 21.0$

Next, we calculate the exponentials for the Softmax denominator ($e^{z'_i}$):
- $e^{25.0} \approx 72.00 \times 10^{9}$
- $e^{22.0} \approx 3.58 \times 10^{9}$
- $e^{21.0} \approx 1.31 \times 10^{9}$

Sum of exponentials (Denominator $\Sigma$):
$$ \Sigma = (72.00 + 3.58 + 1.31) \times 10^{9} = 76.89 \times 10^{9} $$

Finally, we calculate the probability of the EOS token ($z'_3$):
$$ P(\text{<|im\_end|>}) = \frac{1.31 \times 10^{9}}{76.89 \times 10^{9}} \approx 0.017 $$

**Answer:** 
There is approximately a **1.7% chance** that the model will emit the `<|im_end|>` token at this step. The generation is highly likely to continue with a newline (`\n`). 

This mathematically demonstrates how temperature scaling exaggerates differences in logits. By lowering the temperature to $0.5$, we successfully suppressed the stop token when it wasn't the absolute most likely prediction, preventing premature length collapse!
