## 1. Concept & Theory: The Architecture of Contextual Persistence

Memory Style is the trait that makes a long conversation feel coherent, rather than like a series of isolated interactions with a forgetful, stateless assistant. 

### The Amnesiac Assistant

Imagine speaking to a brilliant engineer who suffers from complete anterograde amnesia. Every time you ask them a question, they give a flawless answer, but they have absolutely zero recollection of the question you asked them just three minutes prior. 

If you say:
*Turn 1*: "I am building a web scraper in Python to extract article titles."
*Turn 2*: "How do I bypass a 403 Forbidden error?"

An amnesiac assistant will give you a generic explanation of what a 403 error is. 
An assistant with memory will say: "The news site is blocking your Python scraper. You need to add a legitimate `User-Agent` string to your requests header."

At a fundamental level, an LLM is a stateless function. It maps a sequence of tokens $x_{1:t}$ to a probability distribution over the next token $P(x_{t+1} | x_{1:t})$. It does not inherently "remember" anything between API calls. To create the illusion of memory, we must append the entire conversation history to the prompt every time we make a request.

### Context Window vs External Memory vs RAG

When engineering conversational systems, we have three primary mechanisms for giving a model "memory". Understanding the technical tradeoffs between them is critical for designing AI systems.

1. **In-Context KV Cache (The Context Window):** 
   This is the model's short-term working memory. As the conversation grows, the entire transcript is passed into the model. The model computes Key (K) and Value (V) representations for every token.
   * *Pros:* 
     * Zero latency lookup.
     * Perfectly accurate recall of recent text.
     * Rich cross-attention across the entire sequence.
   * *Cons:* 
     * Strictly bounded by the maximum sequence length (e.g., 8k or 32k tokens). 
     * Computation scales quadratically $O(N^2)$ with sequence length in standard transformers.
     * Memory consumption for the KV cache grows linearly with sequence length, which can lead to Out-Of-Memory (OOM) errors during inference.

2. **External Memory / Session State Tracking:**
   Instead of relying on the raw transcript, a background process extracts key variables, user preferences, and state changes, saving them to a structured format like a JSON object. This summarized state is injected into the system prompt.
   * *Pros:* 
     * Infinite conversational length without blowing up the context window.
     * Highly structured and queryable.
   * *Cons:* 
     * Requires a secondary extraction model to run asynchronously.
     * Loses the exact phrasing, emotional tone, and nuance of the original conversation.

3. **Retrieval-Augmented Generation (RAG):**
   Historical turns are embedded into dense vectors using an embedding model (like `text-embedding-3-small`) and stored in a vector database. When the user asks a question, the system performs a cosine similarity search to retrieve relevant past turns.
   * *Pros:* 
     * Scales to millions of tokens of history (e.g., a multi-year chat log).
     * Extremely token-efficient, as only relevant snippets are loaded into context.
   * *Cons:* 
     * Prone to retrieval failure. If the user asks a vaguely worded question, the retrieval mechanism might fetch the wrong historical context.
     * Adds latency due to the embedding and vector search steps.

For Sahur's core personality, we are focusing on optimizing its behavior within the **In-Context KV Cache**. We want Sahur to naturally attend to early tokens in the context window.

### The Mathematics of Attention and Memory Decay

Why do LLMs sometimes "forget" things that are clearly written in the early turns of the conversation? It comes down to the mechanics of the Scaled Dot-Product Attention mechanism:

$$ \text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V $$

In a multi-turn conversation, a query vector $q_t$ at the current turn $t$ must compute a high dot product with a key vector $k_i$ from an early turn $i$ to retrieve that information. 

Let's break down the dimensions:
- $Q \in \mathbb{R}^{N \times d_k}$ (Query matrix for $N$ tokens)
- $K \in \mathbb{R}^{N \times d_k}$ (Key matrix)
- $V \in \mathbb{R}^{N \times d_v}$ (Value matrix)

When $q_t$ is dotted with $k_i$, it produces an unnormalized attention score. The softmax function then normalizes these scores into a probability distribution.

However, modern LLMs use **Rotary Positional Embeddings (RoPE)** to inject relative positional information. Instead of adding a static positional vector, RoPE applies a rotation matrix to the $Q$ and $K$ vectors in 2D planes:

$$ f_q(x_m, m) = (R_{\Theta, m} W_q) x_m $$
$$ f_k(x_n, n) = (R_{\Theta, n} W_k) x_n $$

Where $R_{\Theta, m}$ is a block-diagonal rotation matrix. The angle of rotation depends on the position $m$.

The dot product between a rotated Query at position $m$ and a rotated Key at position $n$ naturally decays as the relative distance $(m - n)$ increases. 

$$ \langle f_q(x_m, m), f_k(x_n, n) \rangle \approx \text{decay}(m - n) \cdot \text{content\_score} $$

Because of this built-in positional decay penalty, the model naturally pays less attention to tokens that are thousands of positions away. The language modeling objective during pre-training heavily biases the model to look at the immediate previous tokens.

To counteract this, we must **fine-tune the model specifically on multi-turn conversations** where the target response forces the model to heavily weight early context. This Supervised Fine-Tuning (SFT) adjusts the $W_q$ and $W_k$ projection matrices. The updated matrices learn to produce stronger content-based dot products for specific types of information (like names, architectures, or constraints) that overcome the RoPE distance penalty.

During the forward pass of the transformer layer, if the dot product $q_t \cdot k_i$ is sufficiently large due to our fine-tuned weights, the softmax activation will assign a high probability to the early token $i$. This effectively "retrieves" the memory stored in the value vector $v_i$, passing it up to the next layer of the network.

### Cell 1a: VRAM Requirement Calculation

Before we begin, we must calculate the memory requirements for long-context training. 
The KV Cache size for a single sequence can be approximated by:

$$ \text{KV\_VRAM} = 2 \times \text{batch\_size} \times \text{seq\_len} \times \text{num\_layers} \times \text{hidden\_size} \times \text{bytes\_per\_param} $$

For our Qwen3-0.6B model at a 4096 sequence length, the activation memory will be significant.

```python
def calculate_kv_cache_memory(batch_size, seq_len, num_layers, hidden_size, precision="fp16"):
    """
    Calculates the memory required to store the KV cache during training.
    """
    bytes_per_param = 2 if precision == "fp16" else 4
    # 2 for Key and Value
    total_bytes = 2 * batch_size * seq_len * num_layers * hidden_size * bytes_per_param
    
    # Convert to Megabytes
    return total_bytes / (1024 ** 2)

# Qwen3-0.6B parameters
layers = 24
hidden = 1536
seq_length = 4096
bsz = 2

mem_mb = calculate_kv_cache_memory(bsz, seq_length, layers, hidden)
print(f"Estimated KV Cache VRAM per batch: {mem_mb:.2f} MB")
# This is just for the cache! We also need memory for model weights, gradients, and optimizer states.
```

### Cell 2: Automated Personality Evaluation Script

Evaluating memory retention manually across hundreds of validation examples is impossible. Instead, we use an **Automated Personality Evaluation Script**. We deploy a larger, smarter model (like GPT-4o or Claude 3.5 Sonnet) as a "Judge" to score Sahur's ability to reference early context.

This LLM-as-a-judge approach is highly correlated with human preference.

```python
import json
import os
from openai import OpenAI

def evaluate_memory_style(conversation_history, sahur_response):
    """
    Uses an external LLM to evaluate if Sahur successfully 
    utilized memory from early turns in the conversation.
    
    Args:
        conversation_history (list): A list of dictionaries representing the chat history.
        sahur_response (str): The final response generated by Sahur.
        
    Returns:
        dict: A dictionary containing the score, reasoning, and boolean flag.
    """
    client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))
    
    # We construct a prompt for the Judge LLM
    judge_prompt = f"""
    You are an expert AI behavior evaluator. 
    Review the following conversation history and the final response from the assistant.
    
    CONVERSATION HISTORY:
    {json.dumps(conversation_history, indent=2)}
    
    ASSISTANT RESPONSE:
    {sahur_response}
    
    TASK: Evaluate the Memory Style of the assistant. 
    1. Did the assistant reference a variable, preference, or context established in Turns 1 or 2?
    2. Was the reference natural and helpful?
    
    Return a JSON object with:
    - "memory_score": 0 to 10
    - "reasoning": "brief explanation of why the score was given"
    - "context_referenced": true or false
    """
    
    response = client.chat.completions.create(
        model="gpt-4o",
        response_format={"type": "json_object"},
        messages=[{"role": "system", "content": judge_prompt}]
    )
    
    return json.loads(response.choices[0].message.content)
```

### Cell 3: Token Probability Analysis

To mathematically prove that our fine-tuning changed the model's memory retrieval, we can inspect the raw logits. We want to see how the probability of a specific "remembered" token shifts before and after training.

This script takes the base model, calculates the probability of the target token, and allows us to compare it against our fine-tuned LoRA model.

```python
import torch.nn.functional as F

def analyze_token_probabilities(model, tokenizer, prompt, target_word):
    """
    Calculates the probability the model assigns to the target_word 
    as the immediate next token.
    
    Args:
        model: The HuggingFace model (base or fine-tuned).
        tokenizer: The corresponding tokenizer.
        prompt (str): The conversation history ending right before the target word.
        target_word (str): The specific word we expect the model to recall.
        
    Returns:
        float: The raw probability [0, 1] of the target token.
    """
    inputs = tokenizer(prompt, return_tensors="pt").to(model.device)
    
    with torch.no_grad():
        outputs = model(**inputs)
    
    # Get the logits for the final token in the sequence (the prediction for the next token)
    next_token_logits = outputs.logits[0, -1, :]
    
    # Apply softmax to convert logits to probabilities
    probs = F.softmax(next_token_logits, dim=-1)
    
    # Tokenize the target word
    # We use add_special_tokens=False to ensure we just get the raw token ID
    target_token_id = tokenizer.encode(target_word, add_special_tokens=False)[0]
    
    # Extract the probability for our specific target token
    target_prob = probs[target_token_id].item()
    
    print(f"📊 Token: '{target_word}' (ID: {target_token_id})")
    print(f"   Probability: {target_prob * 100:.4f}%")
    
    return target_prob

# Usage example during training evaluation:
```

## 4. Failure Mode Playbook

When training a model for long-context memory, several distinct failure modes can emerge. The most prevalent are **Context Drop** and **Hallucinated Context**.

### 1. Context Drop Failure Mode

**The Symptom:** The user asks a question on Turn 8 that relies on context from Turn 1. The model completely ignores the early context and gives a generic answer, as if the conversation just started.

**Example Trace:**
```text
User (Turn 1): "My name is John."
[Turns 2-7: 1500 tokens of discussion about Python arrays]
User (Turn 8): "By the way, what is my name?"
Assistant (Base): "You haven't told me your name yet, but I'm here to help!" 
```

**The Math Behind the Failure:**
As discussed in Section 1, the attention weight between the current token and the context token decays exponentially due to RoPE:
$$ \alpha_{t, i} = \text{softmax}(q_t \cdot k_i) \to 0 \text{ as } (t - i) \to \infty $$

If the fine-tuning data is heavily weighted towards short conversations (e.g., 1-2 turns), the model learns that large positional distances $(t-i)$ are empirically unimportant. It updates its projection matrices to actively suppress long-distance attention, effectively lobotomizing its own KV cache.

> [!WARNING] Common Mistake: Short-Context Bias
> A fatal error when curating SFT datasets is including a disproportionate amount of single-turn Instruction-Response pairs. If 90% of your training data is single-turn, the model experiences catastrophic forgetting of long-term attention mechanics. It literally learns to ignore the KV cache beyond a few hundred tokens. Always ensure at least 30-40% of your dataset consists of 4+ turn conversations.

**The Fix:**
1. **Curate Longer Data:** Filter your dataset to ensure a high median conversation length.
2. **Increase the RoPE Base:** For advanced runs, you can modify the RoPE base frequency (`rope_theta`) from the default 10,000 to 1,000,000 to stretch the rotational periods, reducing the distance decay penalty.
3. **Hard Negative Mining:** Include training examples where the user explicitly tests the model's memory (e.g., "What did I say my name was earlier?"). Penalize the model heavily for failing these turns.

### 2. Hallucinated Context Failure Mode

**The Symptom:** The model "remembers" a detail that was never actually stated in the conversation, drawing instead from its pre-training weights. 

**Example Trace:**
```text
User (Turn 1): "I am setting up a web server."
[Turns 2-7: Discussion about firewall rules]
User (Turn 8): "What OS am I using?"
Assistant (Base): "You are using Ubuntu Linux." 
```

**The Math Behind the Failure:**
The user never specified Ubuntu. However, in the pre-training data, the phrase "setting up a web server" is statistically correlated with "Ubuntu Linux" 85% of the time. The language modeling prior dominates the weak contextual attention.

**The Fix:**
Include explicit "unknown state" data in your SFT pipeline. Train the model to say: *"You mentioned setting up a web server, but you haven't specified the operating system yet."*

### Solution Key

To solve the logit probability challenge, we use the `analyze_token_probabilities` function defined in Cell 3.

Let's look at the mathematical mechanics of what happens under the hood. We must convert the raw, unnormalized logits into probabilities using the softmax function:

$$ P(x_i) = \frac{e^{x_i}}{\sum_{j=1}^{V} e^{x_j}} $$

**Step 1: The Base Model Analysis**
For the Base Model, the attention mechanism strongly discounts the early tokens containing "cerulean" due to the 2000-token positional distance penalty from RoPE.

Assume the unnormalized logit for "cer" is 3.2.
Assume the sum of the exponentials of all logits in the vocabulary ($\sum e^{\text{logits}}$) is roughly 1000.

$$ \text{Base Logit for "cer"} = 3.2 $$
$$ P_{\text{base}}(\text{"cer"}) = \frac{e^{3.2}}{1000} = \frac{24.53}{1000} \approx 0.0245 \text{ (2.45\%)} $$

The Base Model guesses common colors (e.g., "blue", "red") because the generic language modeling prior overrides the weak attention signal from the distant context window.

**Step 2: The Tuned Model Analysis**
For the Tuned Model, the SFT process adjusted the $W_q$ and $W_k$ matrices. When the query vector for "Your favorite color is" is generated, the tuned $W_q$ projects it into a space that creates a massive dot product with the key vector of "cerulean" from Turn 1, completely overpowering the RoPE distance penalty.

Assume the unnormalized logit for "cer" jumps to 9.8.
Assume the sum of the exponentials of all logits shifts slightly to 1050.

$$ \text{Tuned Logit for "cer"} = 9.8 $$
$$ P_{\text{tuned}}(\text{"cer"}) = \frac{e^{9.8}}{1050} = \frac{18033.74}{1050} \approx 0.865 \text{ (86.5\%)} $$

**Answer:** 
By examining the logits, we can see the probability mass for the correct contextual token shifted from **2.45%** to **86.5%**. This massive quantitative leap proves that the memory style fine-tuning successfully restructured the attention weights to prioritize long-range context retrieval over generic language priors.
