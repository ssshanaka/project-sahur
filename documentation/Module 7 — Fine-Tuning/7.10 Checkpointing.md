# Module 7 — Fine-Tuning
## Lesson 7.10 — Checkpointing

Training a Large Language Model is a precarious, expensive process. 

A fine-tuning run on a 7B model can easily take 12 to 24 hours on a consumer GPU. If you are renting a cloud GPU on a preemptible instance (like Google Colab, RunPod Spot, or AWS Spot instances), the server could be terminated by the provider at any moment to reclaim resources. 

If the server shuts down at hour 11, and you haven't saved your progress to disk, you have permanently lost 11 hours of compute time and the money you paid for it.

To prevent this catastrophe, professional ML engineers use **Checkpointing**. Checkpointing is the process of periodically writing the exact state of the training run to a persistent hard drive.

---

## 1. Concept & Theory: The State of the Model

When the `SFTTrainer` hits a checkpoint step (e.g., Step 100), it pauses the forward and backward passes. It then writes a folder to your hard drive inside the `output_dir`.

What exactly is it saving? A checkpoint is much more than just the model weights. To perfectly resume a training run, you need the entire physical state of the optimizer and the training loop.

### 1.1 Checkpoint Components
1. **The LoRA Adapter Weights:** The actual matrix $A$ and matrix $B$ weights that we have learned so far. Notice that it *does not* save the 600M base model weights. This makes LoRA checkpoints incredibly lightweight (usually 20-50 MB).
2. **The Optimizer State:** The momentum ($m_t$) and variance ($v_t$) history for the AdamW optimizer. If you don't save this, resuming training will cause a massive loss spike because the optimizer has to restart from zero momentum.
3. **The Scheduler State:** Where we are on the learning rate curve (e.g., still warming up, or linearly decaying).
4. **The RNG State:** The random number generator seeds for PyTorch, NumPy, and Python. This ensures that the dataset shuffle continues in the exact same order it would have if you hadn't stopped.
5. **Trainer State:** The current step, epoch, and loss logs.

### 1.2 Safetensors vs PyTorch `.bin` Format

In the early days of Hugging Face, models were saved as `pytorch_model.bin`. You will still see this in older tutorials. Modern checkpoints use `adapter_model.safetensors`. Why the change?

The original `.bin` files were Python `pickle` files. **Pickle is inherently insecure.** Unpickling a file can execute arbitrary Python code. If you downloaded a `.bin` model from a malicious Hugging Face repository, it could silently install malware on your computer the moment you loaded the model.

**Safetensors** (created by Hugging Face) solved this and added performance benefits:
- **Secure:** It is a flat data format, not an executable script. It cannot run code.
- **Zero-Copy Memory Mapping:** It allows PyTorch to map the tensors directly from the hard drive into RAM/VRAM without allocating extra memory for a loading buffer. This means loading a 30GB model requires exactly 30GB of RAM, not 60GB.
- **Language Agnostic:** It can be read by Rust, C++, and JavaScript directly, which is crucial for modern deployment engines like `llama.cpp`.

### 1.3 Gradient Checkpointing (A completely different concept)

There is a parameter in Unsloth that sounds very similar to saving files to a hard drive, but it does something completely different: `use_gradient_checkpointing`.

**Gradient Checkpointing** (also called Activation Checkpointing) is a mathematical trick to save VRAM during the backward pass. 

Remember in Lesson 7.7 (Batch Size) how PyTorch has to save the intermediate outputs (activations) of all layers during the forward pass so it can use them to calculate derivatives in the backward pass? Those activations consume gigabytes of VRAM.

**The Computation Graph Diagram:**
Let's visualize a simplified 6-layer Transformer with Gradient Checkpointing turned ON. Instead of saving all 6 layers of activations, PyTorch only saves a "checkpoint" activation at Layer 0 and Layer 3. 

```text
Forward Pass:
Input -> L0(SAVED) -> L1(Discarded) -> L2(Discarded) -> L3(SAVED) -> L4(Discarded) -> L5(Discarded) -> Loss

Backward Pass (Derivative calculation flowing right-to-left):
[Loss -> L5 -> L4 -> L3] 
  Wait, I need L4 and L5 activations to calculate gradients, but they were discarded!
  ACTION: Re-run forward pass from L3(SAVED) -> L4 -> L5 to recompute them on the fly.
  
[L3 -> L2 -> L1 -> L0]
  Wait, I need L1 and L2 activations!
  ACTION: Re-run forward pass from L0(SAVED) -> L1 -> L2.
```

**The Trade-off:** You trade **Compute** for **Memory**. 
Gradient Checkpointing reduces VRAM usage by roughly 30-50%, allowing you to use much larger batch sizes. However, it makes the training run about 20% slower because it has to recalculate chunks of the forward pass.

Unsloth's custom `use_gradient_checkpointing = "unsloth"` implementation is highly optimized, minimizing this speed penalty by saving and recalculating tensors at the exact optimal layer depths.

## 2. Cell-by-Cell Code Breakdown

Let's look at how file checkpointing is configured, comparing raw Hugging Face with Unsloth.

### 2.1 Raw Hugging Face vs Unsloth Checkpointing

```python
# Cell 1: Checkpointing in the TrainingArguments
from transformers import TrainingArguments

training_args = TrainingArguments(
    output_dir = "./sahur-checkpoints",
    
    # 1. When to save
    save_strategy = "steps",  # Save every X steps
    save_steps = 100,         # We will save at step 100, 200, 300...
    
    # 2. Disk Space Protection
    save_total_limit = 3,     # Garbage collection
    
    # 3. Model Loading Logic
    load_best_model_at_end = True,
    metric_for_best_model = "eval_loss",
    
    # 4. Evaluation coupling
    eval_strategy = "steps",
    eval_steps = 100,         # Must match save_steps if load_best_model_at_end=True
)
```

Notice that checkpointing configuration has nothing to do with the model itself; it is purely a `SFTTrainer` argument. This configuration is identical whether you use Unsloth or raw Hugging Face PEFT.

### 2.2 `load_best_model_at_end` Mechanics

If you are evaluating your model on a validation dataset, you want to ensure that at the very end of training, you possess the model state that achieved the lowest validation loss.

If you train for 1000 steps, the model might have overfit by step 800. The checkpoint at step 1000 is actually worse than the checkpoint at step 500.

When `load_best_model_at_end = True` is set:
1. Every time the trainer evaluates and saves a checkpoint, it writes the `eval_loss` into a file called `trainer_state.json`.
2. It tracks the `best_metric` and `best_model_checkpoint` fields internally.
3. When `save_total_limit` garbage collection triggers, it **will never delete** the checkpoint that currently holds the `best_metric`.
4. When `trainer.train()` finishes, it automatically loads the weights from `best_model_checkpoint` into VRAM. You are left holding the mathematical peak of your model.

## 3. Worked Examples / Data Artifacts

To truly understand checkpoints, we need to look inside the folder.

### 3.1 PEFT Adapter Directory Structure

When `checkpoint-100` is written to disk, the directory structure looks exactly like this:

```text
./sahur-checkpoints/checkpoint-100/
├── adapter_config.json        ← The LoRA hyperparameters (r=16, alpha=16)
├── adapter_model.safetensors  ← The actual A and B matrices
├── optimizer.pt               ← AdamW state (momentum, variance)
├── rng_state.pth              ← Random seeds for PyTorch/Numpy
├── scheduler.pt               ← Learning rate curve state
├── trainer_state.json         ← Step, epoch, and loss history log
└── training_args.bin          ← The exact TrainingArguments used
```

### 3.2 Checkpoint File Inspector Script

Let's write a script that opens a checkpoint directory, inspects the files, loads the JSON metadata, and peeks into the binary PyTorch files to prove what is inside.

```python
# Cell 2: The Checkpoint Inspector
import os
import json
import torch

def inspect_checkpoint(checkpoint_dir):
    print(f"🔍 Inspecting Checkpoint: {checkpoint_dir}")
    print("-" * 50)
    
    if not os.path.exists(checkpoint_dir):
        print("Directory not found!")
        return

    # 1. Print File Sizes
    total_size = 0
    print("📁 Files and Sizes:")
    for file in os.listdir(checkpoint_dir):
        path = os.path.join(checkpoint_dir, file)
        size_mb = os.path.getsize(path) / (1024 * 1024)
        total_size += size_mb
        print(f"  - {file:<25} {size_mb:>8.2f} MB")
    print(f"Total Checkpoint Size: {total_size:.2f} MB\n")

    # 2. Inspect Trainer State (Loss History)
    state_path = os.path.join(checkpoint_dir, "trainer_state.json")
    if os.path.exists(state_path):
        with open(state_path, "r") as f:
            state = json.load(f)
            print(f"📊 Trainer State (Step {state.get('global_step', 'Unknown')}):")
            print(f"  Best Metric: {state.get('best_metric', 'N/A')}")
            print(f"  Best Checkpoint: {state.get('best_model_checkpoint', 'N/A')}")
            
            # Print the last 3 loss logs
            logs = state.get("log_history", [])
            print("  Recent Log History:")
            for log in logs[-3:]:
                if "loss" in log:
                    print(f"    Step {log['step']}: Train Loss = {log['loss']:.4f}")
                elif "eval_loss" in log:
                    print(f"    Step {log['step']}: Eval Loss = {log['eval_loss']:.4f}")
    
    # 3. Inspect Optimizer State
    opt_path = os.path.join(checkpoint_dir, "optimizer.pt")
    if os.path.exists(opt_path):
        print("\n⚙️ Optimizer State (.pt file):")
        # torch.load reads the binary pickle format used for optimizers
        opt_state = torch.load(opt_path, map_location="cpu")
        print(f"  Found state for {len(opt_state['state'])} param tensors.")
        
        # Look at the first tensor's momentum states
        first_key = list(opt_state['state'].keys())[0]
        state_dict = opt_state['state'][first_key]
        print(f"  Example param tracks: {list(state_dict.keys())}")
        if 'exp_avg' in state_dict:
            print(f"  Momentum tensor shape: {state_dict['exp_avg'].shape}")

# Run the inspector on a hypothetical checkpoint
# inspect_checkpoint("./sahur-checkpoints/checkpoint-100")
```

This script reveals that the optimizer file (`optimizer.pt`) is usually the largest file in the checkpoint, as it stores two full copies (momentum and variance) of every trainable parameter, stored in FP32 precision.

## 4. Failure Mode Playbook

What happens when checkpointing fails or is misconfigured?

> [!WARNING]
> **The Dataset Shuffling Trap**
> If you resume a training run from a checkpoint, the `RNG_state.pth` ensures the dataset continues from where it left off. BUT, if you alter the `dataset.jsonl` file in any way before resuming (e.g., adding 50 new examples you just wrote), the original RNG state is now completely invalid for the new dataset structure. The trainer will feed the model data it has already seen, skipping new data, and ruining the epoch distribution. 
> **Never modify your dataset between resuming checkpoints.**

### 4.1 Symptom: Out of Disk Space Crash
- **What it looks like:** Training runs perfectly for 12 hours, then crashes with `OSError: [Errno 28] No space left on device` during a checkpoint save. The current checkpoint folder is half-written and corrupted.
- **Why it breaks:** You did not set `save_total_limit`. By default, Hugging Face saves every checkpoint forever. If you save every 100 steps for 10,000 steps, you wrote 100 folders to disk.
- **The Fix:** Set `save_total_limit = 3`. 

### 4.2 Symptom: Resuming causes a massive loss spike
- **What it looks like:** Your loss was down to `0.85`. You hit `ctrl+c`, and then resume from the checkpoint using `trainer.train(resume_from_checkpoint=True)`. The very next step, the loss spikes to `3.50` and takes hundreds of steps to recover.
- **Why it breaks:** You accidentally deleted `optimizer.pt` or you initialized a new optimizer instance manually instead of letting the trainer load it. The optimizer lost all its momentum history and started taking chaotic, uncalibrated steps.
- **The Fix:** Ensure the full checkpoint directory is intact. The `resume_from_checkpoint` argument handles loading the optimizer automatically.

## 5. Mini-Lab / Engineering Challenge: The Disk Space Calculator

You are training a 7B model using standard LoRA ($r=16$).
A single checkpoint folder (containing `adapter_model.safetensors`, `optimizer.pt`, etc.) is exactly **400 Megabytes**.

Your `TrainingArguments` are configured as follows:
- `max_steps = 5000`
- `save_steps = 250`
- `save_total_limit = 5`
- `load_best_model_at_end = False`

**Question 1:** Over the entire 5000-step run, how many total times will the trainer attempt to write a checkpoint to disk?
**Question 2:** When the training run is completely finished, how many Gigabytes of disk space will the `sahur-checkpoints` folder be consuming?

### Solution Key

**Answer to Question 1:**
The trainer will save a checkpoint every 250 steps. 
Total saves = `max_steps / save_steps`
Total saves = $5000 / 250 = 20$ times.
The trainer will execute the disk-write operation exactly 20 times.

**Answer to Question 2:**
Because `save_total_limit = 5`, the garbage collection algorithm will aggressively delete older checkpoints to maintain exactly 5 folders on disk.
Once we pass step 1250, there will always be 5 checkpoints on disk.
When the run finishes at step 5000, the remaining folders will be:
- `checkpoint-4000`
- `checkpoint-4250`
- `checkpoint-4500`
- `checkpoint-4750`
- `checkpoint-5000`

Total size = $5 \text{ checkpoints} \times 400 \text{ MB}$
Total size = $2000 \text{ MB}$
**Final Answer: 2.0 Gigabytes.**

*(Note: If `load_best_model_at_end = True` was active, and the best model occurred at step 1000, it would be preserved, resulting in 6 total checkpoints on disk and 2.4 GB of space used).*
