# Module 7 — Fine-Tuning
## Lesson 7.2 — QLoRA (Quantized Low-Rank Adaptation)

In **Lesson 7.1**, we solved the optimizer crisis. By using LoRA, we bypassed the need to calculate gradients and store optimizer states for the 600 million parameters of Qwen3-0.6B. We reduced our trainable parameter count to just a few million.

But we are not out of the woods yet.

Even if we don't train the 600 million parameters, we still have to **load** them into VRAM so we can pass data through them during the forward and backward passes. 

If Qwen3-0.6B is loaded in standard 32-bit floating point (FP32), the weights alone consume 2.4 GB of VRAM.
If we load a 7B model (like Llama 3 8B) in FP32, the weights consume **28 GB** of VRAM — well past the 16 GB limit of a standard consumer GPU (like a T4 or RTX 4080).

To bring large-model fine-tuning to the masses, we needed a way to shrink the base model itself. We needed **Quantization**. And specifically, we needed the breakthroughs introduced in the 2023 paper *QLoRA: Efficient Finetuning of Quantized LLMs* (Dettmers et al.).

---

## 1. Concept & Theory

### 1.1 The Outlier Problem and Standard Quantization

Quantization is the process of reducing the mathematical precision of the neural network's weights. 
In deep learning, precision is defined by data types (FP32, BF16, INT8, INT4). 
If we can quantize a 7B model down to 4-bit, its memory footprint drops from 28 GB (FP32) to just **3.5 GB**. 

However, standard integer quantization destroys LLMs because of **outlier weights**.
In standard 4-bit integer format (INT4), there are 16 possible values ($-8$ to $7$). 
Standard asymmetric quantization transforms an FP32 weight $W$ into an integer weight $W_{int4}$ using:

$$ W_{int4} = \text{round}\left( \frac{W - \min(W)}{\max(W) - \min(W)} \times 15 \right) - 8 $$

If 99.9% of your weights are between $-0.5$ and $0.5$, but there is a single outlier weight at $5.0$, the entire dynamic range is stretched. 
As a result, all 99.9% of your important weights get crushed into the same bin near zero. The mathematical structure is completely obliterated.

### 1.2 Normal Float 4-bit (NF4)

The QLoRA paper solved this by inventing **NF4 (Normal Float 4-bit)**. 
Neural network weights are not randomly distributed; they follow a zero-mean normal (Gaussian) distribution.

$$ \mathcal{N}(\mu=0, \sigma^2) $$

Instead of 16 *equally spaced* bins, NF4 draws 16 bins spaced strictly according to the quantiles of a standard normal distribution. 
- Bins are clustered heavily around zero.
- Bins are spaced further apart at the tails to catch outliers accurately.

Because the bins map perfectly to the actual distribution, the model retains its intelligence despite being compressed to 4 bits per parameter.

### 1.3 Double Quantization Math

The QLoRA paper introduced **Double Quantization** to squeeze even more memory savings from the quantization constants.

When you quantize a matrix into 4-bit, you must store a **scaling factor** (quantization constant) to de-quantize it later. 
In standard block-wise quantization, a block size of $B=64$ parameters is used to isolate outliers locally. 
This means every 64 parameters require one FP32 (32-bit) constant.

Let's do the math on the overhead:
- 32 bits / 64 parameters = **0.5 bits per parameter** overhead.

Double Quantization compresses these FP32 constants down to INT8, using a second block size (usually $256$).
Here is the step-by-step breakdown:
1. **First-level quantization:** The 64-param blocks get their constants quantized to 8-bit (INT8). 
   - 8 bits / 64 parameters = **0.125 bits per parameter**.
2. **Second-level quantization:** We need FP32 constants to scale the INT8 constants. We use blocks of 256 for this.
   - 1 FP32 constant for every $(64 \times 256)$ parameters.
   - 32 bits / 16,384 parameters = **0.00195 bits per parameter**.

**Total Memory Savings Calculation for a 600M Model (Qwen3-0.6B):**
- Standard 4-bit block-wise overhead: $4.0 + 0.5 = 4.5$ bits/param.
- Double Quantized overhead: $4.0 + 0.125 + 0.00195 = 4.12695$ bits/param.

For $600,000,000$ parameters:
- Without Double Quantization: $600M \times 4.5 / 8 = 337.5$ MB.
- With Double Quantization: $600M \times 4.12695 / 8 = 309.5$ MB.
- Savings: **28 Megabytes** (On a 65B model, this saves over 3 GB of VRAM!).

## 2. Cell-by-Cell Code Breakdown

To implement QLoRA, we use the `bitsandbytes` library. Let's break down the code cell by cell, examining every parameter.

### Cell 1: The BitsAndBytesConfig Full Parameter Reference

```python
import torch
from transformers import BitsAndBytesConfig

# The BitsAndBytesConfig acts as the QLoRA Engine configuration.
# We annotate every parameter here for reference.

bnb_config = BitsAndBytesConfig(
    # --- Primary Quantization Flags ---
    load_in_4bit=True,                   # Enables 4-bit quantization. Overrides load_in_8bit if both are True.
    load_in_8bit=False,                  # Standard LLM.int8() quantization. Slower and uses more memory than 4-bit.
    
    # --- 4-bit Specific Parameters ---
    bnb_4bit_quant_type="nf4",           # "nf4" or "fp4". NF4 is mathematically optimal for normal distributions.
    bnb_4bit_use_double_quant=True,      # Enables Double Quantization (shrinks 32-bit constants to 8-bit).
    bnb_4bit_compute_dtype=torch.bfloat16, # The de-quantization target. Math is done in this precision. Use bf16 for modern GPUs.
    bnb_4bit_quant_storage=torch.uint8,  # The underlying storage type for the 4-bit arrays in memory.
    
    # --- Legacy / 8-bit Parameters (Ignored if load_in_4bit=True) ---
    llm_int8_threshold=6.0,              # Outlier threshold for 8-bit quant. Values > 6.0 remain in FP16.
    llm_int8_skip_modules=None,          # List of modules to skip quantizing (e.g. ["lm_head"]).
    llm_int8_enable_fp32_cpu_offload=False, # Allows offloading chunks of the model to system CPU RAM.
    llm_int8_has_fp16_weight=False       # Used internally to track if model weights were originally FP16.
)
```

### Cell 2: Unsloth vs Raw Hugging Face

There are two main ways to load our model.

**Method A: Raw Hugging Face (Standard)**
```python
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen3-0.6B",
    quantization_config=bnb_config,
    device_map="auto" # Automatically dispatches the quantized layers to the GPU
)
```

**Method B: Unsloth (Optimized)**
Unsloth wraps the `BitsAndBytesConfig` internally and injects highly optimized, handwritten Triton/CUDA kernels to speed up the matrix math.

```python
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "Qwen/Qwen3-0.6B",
    load_in_4bit = True,    # Automatically applies NF4, Double Quant, and Compute Dtype!
    dtype = torch.bfloat16, # Specifies the forward pass precision
)
```
Unsloth replaces standard PyTorch de-quantization operations with custom kernels that perform de-quantization and matrix multiplication *simultaneously* on the GPU silicon, training 2-5x faster than raw Hugging Face code.

### Cell 3: Paged AdamW 8-bit Optimizer

Even with the model compressed to 4-bit, the optimizer states (momentum and variance) still consume a lot of memory. To solve this, we use **Paged AdamW 8-bit**.

```python
from transformers import TrainingArguments

training_args = TrainingArguments(
    output_dir="./qlora-outputs",
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,
    
    # THE SECRET SAUCE FOR VRAM SAVINGS:
    optim="paged_adamw_8bit", 
    
    learning_rate=2e-4,
    fp16=False,
    bf16=True, # Ensure we use bfloat16 for stability
)
```

**What does `optim="paged_adamw_8bit"` do?**
1. **8-bit Blockwise Quantization:** It quantizes the optimizer's momentum and variance states from 32-bit floats to 8-bit integers using `bitsandbytes`, cutting optimizer memory by 75%.
2. **Paging (NVIDIA Unified Memory):** If the GPU runs out of memory during a sudden VRAM spike (like during the backward pass of an unusually long sequence), the optimizer states are instantly "paged out" (evicted) to your computer's system CPU RAM, preventing an OOM crash. When the VRAM frees up, they are paged back in.

## 3. Worked Examples / Data Artifacts

### 3.1 The Exact NF4 Lookup Table

You might wonder: *What are the actual 16 values in the NF4 datatype?*
We can mathematically derive them using the inverse cumulative distribution function (Quantile Function) of the standard normal distribution.

Here is the fully runnable script to derive the NF4 bins using `scipy.stats.norm.ppf`:

```python
import numpy as np
from scipy.stats import norm

def generate_nf4_bins():
    # 1. We want 16 bins for 4-bit values. We split the normal curve into 16 equal-area quantiles.
    offset = 1/32  # slight offset to center the zero bin exactly
    
    # Generate 16 evenly spaced quantiles from 0 to 1
    quantiles = np.linspace(offset, 1 - offset, 16)
    
    # 2. Find the corresponding Z-scores for these quantiles
    nf4_values = norm.ppf(quantiles)
    
    # 3. Normalize the values so the absolute maximum is 1.0
    nf4_values = nf4_values / np.max(np.abs(nf4_values))
    
    # Force one of the values to be exactly 0.0 for zero-padding stability
    # In the actual paper, the negative side has 7 bins and the positive side has 8 bins around zero
    
    return np.round(nf4_values, 4)

nf4_bins = generate_nf4_bins()
print("The 16 NF4 Bins (Normalized):")
for i, val in enumerate(nf4_bins):
    print(f"Bit {i:02d} (binary {bin(i)[2:].zfill(4)}): {val:>7}")

# EXPECTED OUTPUT:
# Bit 00 (binary 0000): -1.0
# Bit 01 (binary 0001): -0.6962
# Bit 02 (binary 0010): -0.5251
# ... clustered densely around 0.0 ...
# Bit 15 (binary 1111):  1.0
```

### 3.2 De-quantization Timing Profile

How much overhead does layer-by-layer de-quantization add during the forward pass? Let's write a script using `torch.cuda.Event` to profile a single matrix multiplication in FP16 vs NF4-dequantized.

```python
import torch
import bitsandbytes as bnb
import time

# Create a random input tensor (Sequence Length 1024, Hidden Dim 4096)
x = torch.randn(1, 1024, 4096, dtype=torch.float16, device="cuda")

# Create a standard FP16 Linear layer
linear_fp16 = torch.nn.Linear(4096, 4096, bias=False, dtype=torch.float16, device="cuda")

# Create an NF4 Linear layer using bitsandbytes
linear_nf4 = bnb.nn.Linear4bit(4096, 4096, bias=False, compute_dtype=torch.float16, quant_type="nf4")
linear_nf4 = linear_nf4.to("cuda")

# Warmup (CUDA requires warmup runs for accurate profiling)
for _ in range(5):
    _ = linear_fp16(x)
    _ = linear_nf4(x)

# Setup Events
start_fp16 = torch.cuda.Event(enable_timing=True)
end_fp16 = torch.cuda.Event(enable_timing=True)
start_nf4 = torch.cuda.Event(enable_timing=True)
end_nf4 = torch.cuda.Event(enable_timing=True)

# Profile FP16
start_fp16.record()
out_fp16 = linear_fp16(x)
end_fp16.record()

# Profile NF4
start_nf4.record()
out_nf4 = linear_nf4(x) # Dequantizes to FP16, multiplies, then discards FP16 weights
end_nf4.record()

# Wait for GPU synchronization
torch.cuda.synchronize()

print(f"FP16 MatMul Time: {start_fp16.elapsed_time(end_fp16):.3f} ms")
print(f"NF4  MatMul Time: {start_nf4.elapsed_time(end_nf4):.3f} ms")
```
*Note: You will typically find that NF4 adds about 20-30% overhead to the pure mathematical computation time, which is a worthwhile trade-off for fitting an 8B model on a consumer GPU.*

## 4. Failure Mode Playbook

QLoRA is complex. When it breaks, the stack traces can be unintuitive. Here is the playbook for fixing common errors.

### 4.1 "CUDA Out of Memory" during the very first backward pass
**Symptom:** The model loads fine, and the forward pass finishes, but it crashes instantly on `loss.backward()`.
**Cause:** Your LoRA adapter `r` rank is too high, or you forgot to set `optim="paged_adamw_8bit"`. The gradients and optimizer states are suddenly exploding in size.
**Fix:** Reduce batch size, reduce LoRA `r`, and ensure `paged_adamw_8bit` is configured in `TrainingArguments`.

### 4.2 Windows Installation Nightmare
**Symptom:** `ImportError: DLL load failed while importing libbitsandbytes_cuda.dll`
**Cause:** Standard `bitsandbytes` has historically struggled on native Windows (non-WSL). It fails to find the CUDA toolkit paths.
**Fix:** Do not install the default package on Windows. Uninstall it and run:
`pip install bitsandbytes-windows` or use WSL2 where standard `bitsandbytes` works flawlessly.

### 4.3 NaN Loss (Not a Number)
**Symptom:** Training loss drops nicely for a few steps, then suddenly spikes to `0.0` or `NaN`.
**Cause:** You set `bnb_4bit_compute_dtype=torch.float16`. FP16 has a very limited dynamic range and frequently overflows during mixed-precision accumulation.
**Fix:** Always set `bnb_4bit_compute_dtype=torch.bfloat16`. BF16 has the exact same dynamic range as FP32, making overflows nearly impossible.

> [!WARNING]
> **The Merging Trap**
> Do NOT attempt to use `model.merge_and_unload()` on an NF4 loaded model directly to save it to disk!
> You cannot mathematically merge 16-bit LoRA adapter weights directly into 4-bit NF4 base weights without corrupting the model. 
> To merge, you must:
> 1. Load the base model in 16-bit (requires immense VRAM, rent a cloud GPU for 1 hour).
> 2. Load the trained LoRA adapters.
> 3. Call `merge_and_unload()`.
> 4. Save the resulting merged FP16 model to disk.

## 5. Mini-Lab / Engineering Challenge

**Scenario:** 
You are provisioning a cloud server to train a Llama-3 8B model using QLoRA.
The GPU costs \$1.50 per hour per 8GB of VRAM (e.g., an A10 24GB costs more than a T4 16GB). You must calculate the *exact* VRAM minimums to avoid overpaying.

**Parameters:**
- Model Size: Exactly 8.0 Billion parameters.
- QLoRA Base Weights: 4-bit NF4 with Double Quantization.
- LoRA Adapters + Activations overhead: Flat 2.5 GB.
- Paged AdamW 8-bit Optimizer overhead: 1.0 GB.
- VRAM Buffer for safety margin: 15% of total mathematical sum.

**Task:**
Calculate the mathematically exact total VRAM required (in GB) to run this training job. Does it fit on a 16GB GPU?

### 5.1 Solution Key

**Step 1: Calculate Base Model Weight Size**
- We know from Section 1.3 that NF4 + Double Quantization uses exactly **4.12695 bits per parameter**.
- Total bits = $8,000,000,000 \times 4.12695 = 33,015,600,000$ bits.
- Convert bits to bytes = $33,015,600,000 / 8 = 4,126,950,000$ bytes.
- Convert bytes to GB = $4,126,950,000 / (1024^3) = \sim 3.84$ GB. *(Note: Using $10^9$ yields 4.12 GB. Let's use the standard $1 GB = 10^9$ bytes hardware convention for simplicity, giving **4.127 GB**).*

**Step 2: Add Overheads**
- Base Weights: 4.127 GB
- Adapters & Activations: 2.500 GB
- Optimizer States: 1.000 GB
- Mathematical Sum = $4.127 + 2.5 + 1.0 = 7.627$ GB.

**Step 3: Apply Safety Buffer**
- 15% Buffer = $7.627 \times 0.15 = 1.144$ GB.
- **Total Required VRAM = 8.771 GB**.

**Conclusion:**
Yes, it easily fits on a standard 16GB GPU (like a T4 or RTX 4080) with over 7GB of VRAM to spare! QLoRA is magical.
