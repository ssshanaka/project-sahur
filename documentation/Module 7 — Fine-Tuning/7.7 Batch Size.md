# Module 7 — Fine-Tuning
## Lesson 7.7 — Batch Size

In the previous lessons, we established that the **Learning Rate** determines the *size* of the step the optimizer takes down the loss landscape mountain. But how does the optimizer know which direction is downhill? It calculates the gradient by evaluating the training data. The critical question for this lesson is: **How many examples of training data does it look at before taking a step?**

This hyperparameter is known as the **Batch Size**.

Batch size sits at the exact intersection of mathematical stability, generalization performance, and strict hardware limitations. If you set it incorrectly, your model will either learn erratically, memorize noise, or cause your GPU to immediately crash with an `Out Of Memory (OOM)` error.

---

## 1. Concept & Theory

To understand batch size, we must view it through two lenses: the mathematical behavior of the optimizer, and the physical constraints of GPU memory.

### 1.1 The Mathematics of Mini-Batch Gradient Descent

In deep learning, we are trying to minimize an objective function (loss). The true gradient of the loss landscape requires evaluating the *entire* dataset. Since we cannot fit the entire dataset in memory, we estimate the true gradient using a subset of the data called a **batch**.

The update rule for Mini-Batch Gradient Descent is defined as:

$$
\theta_{t+1} = \theta_t - \eta \frac{1}{|B|} \sum_{i \in B} \nabla_{\theta} \mathcal{L}(x_i, y_i; \theta_t)
$$

Where:
- $\theta_t$ represents the model weights at step $t$.
- $\eta$ is the learning rate.
- $B$ is the current batch of training examples, and $|B|$ is the batch size.
- $\mathcal{L}$ is the loss function (e.g., Cross-Entropy).

### 1.2 The Three Regimes of Batching

1. **Stochastic Gradient Descent (Batch Size = 1)**:
   The optimizer calculates the gradient using exactly *one* example. 
   *Analogy*: Imagine taking a step down a mountain based on the slope of a single rock under your left foot. If that rock happens to be tilted backward, you step backward, even if the mountain overall slopes downward. The loss curve is violently jagged.
2. **Full Batch Gradient Descent (Batch Size = $N$)**:
   The optimizer calculates the gradient using the *entire* dataset simultaneously. 
   *Analogy*: Having a perfect topographical map of the entire mountain. The gradient is mathematically perfect, and the loss curve drops smoothly. However, it requires an impossible amount of VRAM.
3. **Mini-Batch Gradient Descent (Batch Size = 4 to 128)**:
   The compromise. We sample a small number of examples, average their gradients, and take a step. This smooths out the worst of the noise while keeping VRAM usage low enough to fit on a consumer GPU.

### 1.3 The Exact Activation Memory Formula

During the forward pass, PyTorch must save intermediate tensor outputs (activations) for every single layer to apply the Chain Rule during the backward pass. The size of these activations is the primary reason large batch sizes cause OOM errors.

The exact activation memory formula for a standard Transformer during mixed-precision training can be approximated as:

$$
M_{act} = 2 \times b \times s \times h \times L \times a \text{ bytes}
$$

Where:
- $b$: Batch size
- $s$: Sequence length (number of tokens)
- $h$: Hidden dimension size
- $L$: Number of transformer layers
- $a$: Architecture-specific activation multiplier (typically between 10 and 15, depending on GQA, SwiGLU, and dropout usage. Let's assume 14 for modern LLMs).
- The factor of $2$ accounts for 16-bit (2 bytes) floating point numbers (fp16/bf16).

**Plugging in Qwen3-0.6B's numbers:**
Let's analyze the memory footprint for Qwen3-0.6B on a 16GB T4 GPU.
- $h = 1024$
- $L = 24$ layers
- $s = 2048$ tokens
- $a = 14$

If we use a batch size of $b = 4$:

$$
M_{act} = 2 \times 4 \times 2048 \times 1024 \times 24 \times 14 
$$
$$
M_{act} = 5,637,144,576 \text{ bytes} \approx 5.64 \text{ GB}
$$

So, with $b=4$, activations alone consume 5.64 GB of VRAM. If we tried $b=16$, activations would require $\sim 22.5$ GB, instantly crashing a 16GB GPU!

## 2. Cell-by-Cell Code Breakdown

When fine-tuning in the real world, batch size and data loading configurations are handled either directly via PyTorch `DataLoader` objects, or abstracted away by the Hugging Face `Trainer`. Here is the deep dive into both paradigms.

### [Cell 1] The Raw PyTorch DataLoader Configuration

Before abstractions like Hugging Face existed, data pipelines were built manually. This gives us the clearest view of how batching actually works under the hood.

```python
import torch
from torch.utils.data import DataLoader, RandomSampler
from datasets import load_dataset

# 1. Load the raw dataset
dataset = load_dataset("json", data_files="sahur_dataset.json")["train"]

# 2. Define the DataLoader
train_dataloader = DataLoader(
    dataset,
    batch_size=4,           # The core parameter: how many examples per step
    shuffle=True,           # Randomizes order every epoch to prevent cyclic memorization
    num_workers=4,          # How many CPU subprocesses to use for data loading
    pin_memory=True,        # Allocates data into page-locked RAM for faster GPU transfer
    prefetch_factor=2,      # How many batches each worker should pre-load in advance
    drop_last=True          # Drops the final batch if it is smaller than batch_size
)

# 3. Iteration Loop (What the optimizer sees)
for batch_idx, batch in enumerate(train_dataloader):
    # 'batch' now contains exactly 4 examples
    inputs = batch["input_ids"].to("cuda")
    labels = batch["labels"].to("cuda")
    
    # Forward -> Backward -> Optimizer Step
    break # Just for demonstration
```

**DataLoader Argument Breakdown:**
- **`batch_size`**: The mathematical core. Defines $|B|$.
- **`shuffle=True`**: Critical for training. If the model sees the data in the exact same order every epoch, it can learn sequential dependencies rather than true features.
- **`num_workers`**: Uses multiprocessing to load data from disk. If your GPU utilization constantly dips to 0% between steps, your CPU is bottlenecking the GPU. Increase `num_workers`.
- **`pin_memory`**: Speeds up the PCIe transfer from CPU RAM to GPU VRAM. Always set to `True` when training on GPUs.
- **`prefetch_factor`**: Tells the CPU workers to load the *next* batches into RAM while the GPU is still computing the *current* batch.

### [Cell 2] The Hugging Face & PEFT Approach

When using `SFTTrainer` or Hugging Face's standard `Trainer`, the `DataLoader` is built automatically based on the `TrainingArguments`.

```python
from transformers import TrainingArguments
from trl import SFTTrainer
```

### [Cell 3] PEFT/Unsloth vs Raw Hugging Face

If you are using **Unsloth**, the memory footprint of activations is heavily optimized using custom Triton kernels and manual backpropagation derivations. 
- **Raw HF**: Activations for a 2048-token sequence might use 5.6GB at BS=4.
- **Unsloth**: Through clever gradient checkpointing and memory offloading, Unsloth reduces activation VRAM by up to 60%, allowing you to push the `per_device_train_batch_size` significantly higher on the same hardware.

## 3. Worked Examples / Data Artifacts

To truly understand how VRAM scales with batch size, we must measure it empirically. 
Below is a full, runnable VRAM Profiling Script. It sets up a mock loop running 10-step mini-training iterations at batch sizes of 1, 2, 4, and 8, and reports the peak VRAM usage.

### 3.1 VRAM Profiling Script

```python
import torch
import gc
from transformers import AutoModelForCausalLM, AutoConfig

def get_vram_usage():
    """Returns the peak VRAM usage in GB"""
    return torch.cuda.max_memory_allocated() / (1024 ** 3)

def run_vram_profiler():
    print("🚀 Starting VRAM Profiling for Batch Sizes...")
    
    # We will use a dummy config similar to Qwen-0.5B to test memory scaling
    config = AutoConfig.from_pretrained("Qwen/Qwen2.5-0.5B")
    
    # Batch sizes to profile
    batch_sizes = [1, 2, 4, 8]
    seq_length = 1024 # Fixed sequence length for this test
    
    for bs in batch_sizes:
        # 1. Clear GPU memory completely
        torch.cuda.empty_cache()
        gc.collect()
        torch.cuda.reset_peak_memory_stats()
        
        # 2. Load model directly to GPU in bf16
        # Note: In a real test, we would use PeftModel for LoRA, but raw model
        # provides a good baseline for activation scaling.
        model = AutoModelForCausalLM.from_config(config).to("cuda", dtype=torch.bfloat16)
        model.train()
        
        optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4)
        
        # 3. Generate dummy data for the given batch size
        dummy_input = torch.randint(0, config.vocab_size, (bs, seq_length)).to("cuda")
        dummy_labels = dummy_input.clone()
        
        print(f"\n--- Profiling Batch Size: {bs} ---")
        
        # 4. Run a 10-step training loop
        try:
            for step in range(5): # 5 steps is enough to capture peak activation memory
                optimizer.zero_grad()
                
                # Forward Pass (Activations are stored here!)
                outputs = model(input_ids=dummy_input, labels=dummy_labels)
                loss = outputs.loss
                
                # Backward Pass (Activations are consumed to calculate gradients)
                loss.backward()
                
                # Optimizer Step
                optimizer.step()
                
            peak_vram = get_vram_usage()
            print(f"✅ Success! Peak VRAM Allocated: {peak_vram:.2f} GB")
            
        except torch.cuda.OutOfMemoryError:
            print(f"❌ OOM Error! Batch Size {bs} exceeded VRAM limits.")
            
        finally:
            # Cleanup for the next iteration
            del model, optimizer, dummy_input, dummy_labels, outputs, loss
            torch.cuda.empty_cache()

# If running this locally, uncomment the line below:
# run_vram_profiler()
```

**Expected Output on a 16GB GPU:**
```text
🚀 Starting VRAM Profiling for Batch Sizes...

--- Profiling Batch Size: 1 ---
✅ Success! Peak VRAM Allocated: 2.10 GB

--- Profiling Batch Size: 2 ---
✅ Success! Peak VRAM Allocated: 3.45 GB

--- Profiling Batch Size: 4 ---
✅ Success! Peak VRAM Allocated: 6.15 GB

--- Profiling Batch Size: 8 ---
❌ OOM Error! Batch Size 8 exceeded VRAM limits.
```
*Note: The exact numbers will vary based on PyTorch version and memory allocator overhead, but the linear scaling property remains absolute.*

## 4. Failure Mode Playbook

Even with mathematical calculations, things go wrong in practice. Here is the definitive guide to debugging batch size failures.

### 4.1 The CUDA Out Of Memory (OOM) Error

**What it looks like:**
```text
RuntimeError: CUDA out of memory. Tried to allocate 2.45 GiB. GPU 0 has a total capacity of 15.75 GiB of which 1.10 GiB is free. Process 15309 has 14.65 GiB memory in use.
```

**Why it happens:**
Your $M_{act}$ exceeded the available free space on the GPU. But why did it happen *suddenly* in the middle of training?

### 4.2 Sequence Length Padding Analysis

In the Sahur dataset, we have conversational examples of varying lengths. Some are quick greetings (20 tokens), while others are long philosophical debates (3,000 tokens).

When you use `DataCollatorForSeq2Seq`, PyTorch cannot pass irregularly sized lists into a matrix multiplication. It must form a perfect rectangle (a tensor). 
To do this, the collator **dynamically pads all sequences in the batch to match the length of the longest sequence in that specific batch.**

> [!WARNING]
> **The Hidden OOM Trap: Dynamic Padding**
> If you have a `batch_size = 4`, and three examples are 50 tokens long, but the fourth example is **4,000 tokens long**, PyTorch will pad the first three examples with 3,950 useless `<PAD>` tokens! 
> Suddenly, your effective tensor size jumps from $4 \times 50$ to $4 \times 4000$. The activation memory formula $M_{act}$ instantly scales by 80x, and your GPU explodes on step 214 of your training run.

**The Fixes:**
1. **Truncation**: Always set `max_length` in your tokenizer. (e.g., `truncation=True, max_length=2048`).
2. **Sorting/Grouping**: Use Hugging Face's `group_by_length=True` in `TrainingArguments`. This groups sequences of similar lengths into the same batches, preventing a single long sequence from polluting a batch of short sequences.
3. **Decrease Batch Size**: Drop to BS=2 and use Gradient Accumulation (Lesson 7.9) to simulate larger sizes.

## 5. Mini-Lab / Engineering Challenge

### 5.1 The Flat Minima Experiment (Hochreiter & Schmidhuber, 1997)

There is a fascinating phenomenon in deep learning known as the **Flat Minima Hypothesis**.

Large batch sizes provide perfectly accurate gradients. This causes the optimizer to dive straight into the steepest, sharpest hole it can find in the loss landscape. If real-world data shifts even slightly, the model falls out of that sharp hole, and the validation loss spikes.
Small batch sizes inject gradient noise. This noise mathematically prevents the model from settling in sharp holes, forcing it to find wide, stable, "flat" valleys. Flat valleys generalize much better.

**The Challenge:**
You have trained Model A with Batch Size = 2, and Model B with Batch Size = 32. Both reached a training loss of 0.5. 
Your task is to calculate the **Hessian Spectral Radius** (the measure of minimum sharpness) for both models at convergence to prove that Model A found a flatter minimum.

You don't need to compute the full Hessian (which is impossible for LLMs). You can approximate the dominant eigenvalue using the Power Iteration method. 

*Implement the Power Iteration metric for sharpness. Fill in the missing conceptual steps below.*

### 5.2 Solution Key

To approximate the sharpness of the minimum, we compute the dominant eigenvalue $\lambda_{max}$ of the Hessian matrix $H = \nabla^2 \mathcal{L}(\theta)$. A larger $\lambda_{max}$ means a sharper minimum.

Here is the mathematical code implementation using Pearlmutter's trick (Hessian-vector products) to avoid explicitly forming the Hessian matrix:

```python
import torch

def compute_hessian_spectral_radius(model, data_loader, criterion, num_iterations=10):
    """
    Approximates the dominant eigenvalue of the Hessian (sharpness of the minimum).
    Uses the power iteration method combined with Hessian-vector products.
    """
    model.eval()
    
    # 1. Initialize a random vector v with the exact same dimensions as the model weights
    v = [torch.randn_like(p).to(p.device) for p in model.parameters()]
    
    # Normalize v
    v_norm = torch.sqrt(sum((x ** 2).sum() for x in v))
    v = [x / v_norm for x in v]
    
    for _ in range(num_iterations):
        Hv = [torch.zeros_like(p) for p in model.parameters()]
        
        # 2. Compute the gradient of the loss
        for batch in data_loader:
            inputs, labels = batch["input_ids"].to("cuda"), batch["labels"].to("cuda")
            loss = criterion(model(inputs).logits, labels)
            
            # First derivative (Gradient)
            grads = torch.autograd.grad(loss, model.parameters(), create_graph=True)
            
            # 3. Pearlmutter's Trick: Compute gradient of (grads dot v)
            # This yields the Hessian-vector product Hv exactly, without building H!
            grad_v_dot = sum((g * x).sum() for g, x in zip(grads, v))
            hv_batch = torch.autograd.grad(grad_v_dot, model.parameters())
            
            # Accumulate Hv across the dataset
            Hv = [hv_acc + hv_b for hv_acc, hv_b in zip(Hv, hv_batch)]
            
        # 4. Rayleigh Quotient to find the eigenvalue
        eigenvalue = sum((hv_i * v_i).sum() for hv_i, v_i in zip(Hv, v))
        
        # Re-normalize for the next iteration
        v_norm = torch.sqrt(sum((x ** 2).sum() for x in Hv))
        v = [x / v_norm for x in Hv]
        
    return eigenvalue.item()

# In a real experiment:
# lambda_max_BS2 = compute_hessian_spectral_radius(model_bs2, dataloader, criterion)
# lambda_max_BS32 = compute_hessian_spectral_radius(model_bs32, dataloader, criterion)
# 
# Result Expected: lambda_max_BS32 (e.g., 14.5) > lambda_max_BS2 (e.g., 2.1)
# Conclusion: Batch Size 2 found a significantly flatter, more robust minimum.
```
