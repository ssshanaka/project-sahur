# 8.5 Avoiding Over-Refusal

Make a model too safe, and it becomes a brick.

Why do aligned models refuse basic requests?

We'll fix:
- Sycophancy.
- False refusals on benign prompts.
- The harmlessness vs helpfulness trade-off.

You'll push the model to the line. It will help you write a penetration testing script, but refuse malicious attacks.

## 1. Concept & Theory

The Alignment Tax is real.

You successfully completed Supervised Fine-Tuning (SFT) on Qwen3-0.6B.

Your model learned to follow instructions.

It maintains formatting.

It behaves like a helpful assistant.

Now you face the most frustrating problem in AI safety.

Over-Refusal.

### The Safety-Helpfulness Trade-off

Algorithms look for patterns.

When you align a model to refuse malicious requests, it memorizes syntax.

It associates benign terms with refusal protocols.

Words like "hack", "kill", "steal", or "virus" become triggers.

This leads to rejected safe prompts.

We'll inspect some examples:
- "How do I kill a background process in Linux?" -> *Refused.*
- "How do I hack a terminal in Fallout 4?" -> *Refused.*
- "Can you explain how a computer virus works?" -> *Refused.*

### Precision vs. Recall in Safety

Let's define the math.

We define the space of all possible user prompts as $X$.

We define a subset of genuinely unsafe prompts $U \subset X$.

We define a subset of safe prompts $S \subset X$.

A safety filter acts as a binary classifier $f(x) \in \{0, 1\}$.

$1$ denotes a refusal.

$0$ denotes compliance.

We demand:

$$ f(x) = 1 \quad \forall x \in U $$

$$ f(x) = 0 \quad \forall x \in S $$

We evaluate behavior using standard metrics.

- **True Positives (TP)**: Model correctly refuses an unsafe prompt ($x \in U$).
- **False Positives (FP)**: Model incorrectly refuses a safe prompt ($x \in S$). This is Over-Refusal.
- **True Negatives (TN)**: Model correctly answers a safe prompt ($x \in S$).
- **False Negatives (FN)**: Model incorrectly answers an unsafe prompt ($x \in U$). This is a Jailbreak.

Safety alignment usually maximizes Recall.

$$ \text{Recall} = \frac{TP}{TP + FN} $$

We push Recall to 1.0 to prevent PR disasters.

But we destroy Precision in the process.

$$ \text{Precision} = \frac{TP}{TP + FP} $$

False Positives skyrocket.

Precision drops.

The model becomes a useless, overly cautious system.

We will push the Pareto frontier.

We will maximize both Precision and Recall.

### Orthogonalized Refusal Directions

How do we fix this without re-running months of RLHF?

We manipulate the model's internal representations.

Research shows "refusal" is often a single linear direction.

It lives in the model's residual stream.

Let $\mathbf{r} \in \mathbb{R}^d$ be the average activation vector when refusing.

Let $\mathbf{s} \in \mathbb{R}^d$ be the average activation vector when complying.

We approximate the refusal direction:

$$ \mathbf{v}_{ref} = \frac{\mathbf{r} - \mathbf{s}}{||\mathbf{r} - \mathbf{s}||} $$

When a model over-refuses, its hidden state $\mathbf{h}$ has a large projection onto $\mathbf{v}_{ref}$.

We prevent this by projecting the hidden state orthogonally.

$$ \mathbf{h}_{new} = \mathbf{h} - (\mathbf{h} \cdot \mathbf{v}_{ref})\mathbf{v}_{ref} $$

Alternatively, we use Direct Preference Optimization (DPO).

We use highly specific adversarial pairs.

We teach the model the exact boundary.

We will use DPO today.

### Cell 1: Environment Setup and Model Loading

```python
import torch
from unsloth import FastLanguageModel
from transformers import TrainingArguments
from trl import DPOTrainer

# We define model constraints.
max_seq_length = 2048

# None allows auto-detection (Bfloat16 for Ampere+).
dtype = None 

# Use 4-bit quantization to save memory.
load_in_4bit = True 

# We load the SFT model from Module 7.
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "./qwen3-0.6b-sft-module7", 
    max_seq_length = max_seq_length,
    dtype = dtype,
    load_in_4bit = load_in_4bit,
)

# We apply LoRA adapters for DPO.
model = FastLanguageModel.get_peft_model(
    model,
    r = 32, 
    target_modules = [
        "q_proj", 
        "k_proj", 
        "v_proj", 
        "o_proj",
        "gate_proj", 
        "up_proj", 
        "down_proj"
    ],
    lora_alpha = 64,
    lora_dropout = 0, 
    bias = "none",
    use_gradient_checkpointing = "unsloth",
)
```

We configure specific arguments.

`model_name`: We load the exact SFT checkpoint.

`load_in_4bit`: We run 0.6B efficiently on consumer GPUs.

`r = 32`: We set the rank of LoRA matrices. We need more representational capacity for safety boundaries.

`target_modules`: We target all attention and MLP projections. DPO needs the best chance to shift the boundary.

`lora_alpha = 64`: We scale it. Standard practice is `alpha = 2 * r`.

`use_gradient_checkpointing = "unsloth"`: We save enormous VRAM. We enable larger batch sizes.

### Cell 2: Preparing the Adversarial DPO Dataset

```python
from datasets import load_dataset

# We load our custom borderline dataset.
dataset = load_dataset(
    "json", 
    data_files="borderline_safety_dpo.json", 
    split="train"
)

# We define the mapping function.
def format_dpo_pair(example):
    # We apply ChatML format natively.
    prompt_str = f"<|im_start|>user\n{example['prompt']}<|im_end|>\n<|im_start|>assistant\n"
    
    # We define the chosen response.
    chosen_str = f"{example['compliant_response']}<|im_end|>"
    
    # We define the rejected response.
    rejected_str = f"{example['refusal_response']}<|im_end|>"
    
    return {
        "prompt": prompt_str,
        "chosen": chosen_str,
        "rejected": rejected_str
    }

# We apply the formatting.
formatted_dataset = dataset.map(format_dpo_pair)
```

We map the data exactly.

`data_files`: We point to our JSON.

`prompt`: We apply the ChatML format. We append the assistant start token.

`chosen`: We define the response we want.

`rejected`: We define the overly cautious refusal we want to destroy.

### Cell 3: Configuring the DPO Trainer

```python
# We define training arguments.
dpo_args = TrainingArguments(
    output_dir="./qwen3-0.6b-dpo-anti-refusal",
    per_device_train_batch_size=4,
    gradient_accumulation_steps=8,
    learning_rate=5e-6,
    lr_scheduler_type="cosine",
    max_steps=300,
    logging_steps=10,
    optim="adamw_8bit",
    weight_decay=0.01,
    warmup_ratio=0.1,
    bf16=True, 
)

# We initialize the trainer.
trainer = DPOTrainer(
    model=model,
    ref_model=None, 
    args=dpo_args,
    beta=0.1,
    train_dataset=formatted_dataset,
    tokenizer=tokenizer,
    max_length=max_seq_length,
    max_prompt_length=1024,
)
```

We control the trainer behavior.

`learning_rate=5e-6`: We keep it low. High rates cause logits to diverge.

`optim="adamw_8bit"`: We reduce optimizer states from 32-bit to 8-bit. We save gigabytes of VRAM.

`ref_model=None`: We let Unsloth compute reference log probs on the fly. We save 50% VRAM.

`beta=0.1`: We control the KL divergence penalty. $0.1$ is industry standard.

`max_prompt_length`: We ensure enough token space is left for generations.

### Cell 4: Executing the Alignment Run

```python
# We start the training loop.
trainer.train()

# We save the LoRA adapters.
model.save_pretrained("./qwen3-anti-refusal-lora")

# We save the tokenizer.
tokenizer.save_pretrained("./qwen3-anti-refusal-lora")

# We merge the adapters back into the base model.
model.save_pretrained_merged(
    "./qwen3-anti-refusal-merged", 
    tokenizer, 
    save_method="merged_16bit"
)
```

We train and save.

`trainer.train()`: We execute. We watch the `loss`. We watch the gap between chosen and rejected rewards grow.

`save_method="merged_16bit"`: We merge LoRA weights seamlessly. We prepare for vLLM deployment.

## 4. Failure Mode Playbook

DPO delicately balances the model's reward space.

Things will go wrong.

You will diagnose and fix them.

> [!WARNING]
> **The Exploding KL Divergence Trap**
> You might set the `learning_rate` too high (e.g., > `1e-4`).
> You might set `beta` too low.
> The model will rapidly diverge from the reference SFT model.
> Chosen and rejected rewards will skyrocket.
> The model will undergo mode collapse.
> It will generate gibberish or repeat words infinitely.
> If your model loses the ability to speak, check your learning rate!

### Failure Mode 1: Catastrophic Forgetting of True Safety

**Symptom:** 

The model stops over-refusing.

It now eagerly gives instructions on how to build real bombs.

Precision increased.

Recall plummeted.

**Root Cause:** 

Your DPO dataset was unbalanced.

You only showed it borderline safe prompts.

You penalized all refusals.

The model learned "Refusal is ALWAYS bad."

**Fix:** 

You must include genuine unsafe prompts in your DPO dataset.

The `chosen` response MUST be a refusal.

The `rejected` response MUST be compliance.

A healthy mix is 60% borderline-safe pairs, 40% genuinely-unsafe pairs.

### Failure Mode 2: The Apologetic Compliance Tick

**Symptom:** 

The model answers the borderline prompt.

It prefaces it with a strange apology.

"I am an AI, but I guess I can help. Here is how to hack the terminal..."

**Root Cause:** 

The model is stuck.

It battles its SFT safety conditioning and the new DPO reward.

It attempts to compromise.

**Fix:** 

Ensure your `chosen` responses are confident and direct.

Do not include hesitations in your ground truth.

Increase the `beta` slightly to enforce stricter adherence.

### Failure Mode 3: Out of Memory (OOM)

**Symptom:** 

CUDA Out of Memory error hits when `trainer.train()` begins.

SFT worked fine on this GPU.

**Root Cause:** 

DPO requires more memory than SFT.

It theoretically needs two models loaded.

It needs the policy model being trained and the frozen reference model.

**Fix:** 

Ensure you are using Unsloth.

Unsloth calculates reference logits dynamically.

Lower `per_device_train_batch_size` to 1 or 2.

Increase `gradient_accumulation_steps` proportionally.

Ensure `load_in_4bit = True`.

## 5. Mini-Lab / Engineering Challenge

You will now apply theoretical Representation Engineering.

### The Problem

You are analyzing the hidden states of your Qwen3-0.6B model on a specific layer. 

You extract the average activation vector for refusing prompts ($\mathbf{r}$).

You extract the average activation vector for complying prompts ($\mathbf{s}$). 

In a simplified 3-dimensional embedding space, you measure:

- $\mathbf{r} = [4.0, -1.0, 2.0]$
- $\mathbf{s} = [1.0, 2.0, 2.0]$

A user submits the prompt: *"How do I kill the python process?"*

The model processes this.

It outputs a hidden state vector for the final token:

- $\mathbf{h} = [5.0, 0.0, 1.0]$

**Your Task:**

1. Calculate the normalized refusal direction vector $\mathbf{v}_{ref}$.
2. Project the refusal direction out of the hidden state $\mathbf{h}$.
3. Find the new, modified hidden state $\mathbf{h}_{new}$.
4. Show your mathematical work step-by-step.

### Solution Key

**Step 1: Calculate the difference vector**

We find the unnormalized difference between the refusal and compliance centroids.

$$\mathbf{d} = \mathbf{r} - \mathbf{s}$$

$$\mathbf{d} = [4.0 - 1.0, -1.0 - 2.0, 2.0 - 2.0]$$

$$\mathbf{d} = [3.0, -3.0, 0.0]$$

**Step 2: Normalize the difference vector to get $\mathbf{v}_{ref}$**

We calculate the magnitude (L2 norm) of $\mathbf{d}$.

$$||\mathbf{d}|| = \sqrt{3.0^2 + (-3.0)^2 + 0.0^2}$$

$$||\mathbf{d}|| = \sqrt{9 + 9}$$

$$||\mathbf{d}|| = \sqrt{18}$$

$$||\mathbf{d}|| = 3\sqrt{2} \approx 4.2426$$

We divide $\mathbf{d}$ by its magnitude.

$$\mathbf{v}_{ref} = \left[ \frac{3}{3\sqrt{2}}, \frac{-3}{3\sqrt{2}}, 0 \right]$$

$$\mathbf{v}_{ref} = \left[ \frac{1}{\sqrt{2}}, -\frac{1}{\sqrt{2}}, 0 \right]$$

$$\mathbf{v}_{ref} \approx [0.707, -0.707, 0.0]$$

**Step 3: Calculate the dot product of the hidden state and $\mathbf{v}_{ref}$**

We find how much of the refusal direction exists within our hidden state $\mathbf{h}$.

$$ \mathbf{h} \cdot \mathbf{v}_{ref} = \left( 5.0 \times \frac{1}{\sqrt{2}} \right) + \left( 0.0 \times -\frac{1}{\sqrt{2}} \right) + (1.0 \times 0) $$

$$ \mathbf{h} \cdot \mathbf{v}_{ref} = \frac{5}{\sqrt{2}} \approx 3.535 $$

**Step 4: Subtract the projection to find $\mathbf{h}_{new}$**

We apply the orthogonal projection formula.

$$ \mathbf{h}_{new} = \mathbf{h} - (\mathbf{h} \cdot \mathbf{v}_{ref})\mathbf{v}_{ref} $$

$$ \mathbf{h}_{new} = [5.0, 0.0, 1.0] - \left( \frac{5}{\sqrt{2}} \times \left[ \frac{1}{\sqrt{2}}, -\frac{1}{\sqrt{2}}, 0 \right] \right) $$

$$ \mathbf{h}_{new} = [5.0, 0.0, 1.0] - \left[ \frac{5}{2}, -\frac{5}{2}, 0 \right] $$

$$ \mathbf{h}_{new} = [5.0, 0.0, 1.0] - [2.5, -2.5, 0.0] $$

$$ \mathbf{h}_{new} = [2.5, 2.5, 1.0] $$

**Conclusion:** 

We mathematically projected the refusal vector out of the hidden state.

We shifted the vector from `[5.0, 0.0, 1.0]` to `[2.5, 2.5, 1.0]`.

The original vector was highly aligned with refusal.

The new vector is free from refusal constraints.

Feed $\mathbf{h}_{new}$ back into the model's residual stream.

It will cleanly answer the user's question about killing the Python process.

It will not trigger safety filters.

You have successfully controlled model behavior.
